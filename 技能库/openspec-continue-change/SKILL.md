# OpenSpec 变更流程接续推进指南（openspec-continue-change）

## 概述

指导接续之前尚未完成全套工件编写的 OpenSpec 变更，按照既定规格流程的阶段顺序，生成下一个缺失的设计工件（如由提议推进至详细技术设计，或由技术设计推进至任务分解清单）。

## 适用场景

- “之前建了变更提议，现在继续补充编写技术设计方案”
- “设计方案已完成，接续生成具体的任务分解清单”
- “继续推进当前处于活动状态但工件未齐备的变更”

---

## 一、 核心操作流程

### 第一步：选择目标活动变更
- 运行列表查询命令，获取按修改时间排序的活动变更：
  ```bash
  openspec list --json
  ```
- 向用户展示最近修改的活跃变更选项（包含变更名称、当前工作流程规范与任务完成状态）；
- 严禁擅自盲猜，必须由用户明确选择需要接续的变更。

### 第二步：分析当前状态与工件进度
运行状态检查命令：
```bash
openspec status --change "<变更名称>" --json
```
- 解析返回的 JSON 数据，检查工件列表中哪些已完成（`done`），哪一个是当前应当生成的下一个目标工件（如 `proposal.md` 已就绪，下一步为 `design.md`）。

### 第三步：生成下一阶段工件
依据上一步的工件内容作为输入，编写当前工件：
1. **编写 `design.md`（若上一阶段为提议）**：
   - 细化技术架构决策、模块交互时序与数据库变更；
2. **编写 `tasks.md`（若上一阶段为技术设计）**：
   - 将设计方案逐条细化为有序的执行任务列表，赋予具体的验证判据。

### 第四步：提示后续进展
工件生成完毕后，向用户汇报当前进度。若全套工件已齐备，提示用户可运行实施命令（`openspec-apply-change`）进入编码阶段。

---

## 二、 检查核对清单

- [ ] 是否准确查询了变更当前所处的阶段，确认了下一阶段的工件目标？
- [ ] 新编写的工件内容是否充分吸收了上一阶段已确立的设计原则？
- [ ] 是否在工件齐备后向用户给出了明确的下一步实施提示？
