# 软件全生命周期质量审查技能（SDLC Review）

## 概述

在软件工程任务由实施人员完成并提交交付前，以独立第三方的客观视角，对交付物及其证明材料开展全流程质量与规格审查。依据初始需求与验收标准，出具确定性的审查结论（通过、要求修改或呈报用户决策）。

**核心铁律**：
```
审查员负责对交付物及其证据链进行独立审阅与判定，严禁越权代替实施人员动手修改代码
```
审查员的职责是指出问题、提供事实证据并给出明确结论；若发现缺陷，必须退回由原实施人员进行修改，避免职责混淆导致质量防线形同虚设。

## 适用场景

- 开发任务完成后，实施人员提交了“请求审查”的交付成果；
- 准备将某项特性分支合并入主干前，需要独立出具质量合格认定；
- 对外部提交的代码差异执行全面的规范、安全与契约核验。

---

## 一、 审查三大确定性结论

审查员在核验完毕后，必须且仅能从以下三种结论中作出明确选择，严禁给出模棱两可的意见：

| 审查结论 | 适用触发条件 | 后续流转动作 |
| :--- | :--- | :--- |
| **通过（Approve）** | 所有验收条件 100% 达成，测试与真实验证全部通过，无任何未解缺陷。 | 允许代码合并入库，任务正式流转至已结项状态。 |
| **要求修改（Request Changes）** | 存在可修复的实现缺陷、遗漏边界处理、单测不达标或缺少必要注释。 | 详细列出缺陷位置与证据清单，退回原实施人员重新修改并再次提交。 |
| **呈报决策（Escalate）** | 涉及底层架构冲突、需求存在重大分歧、或需要更高层级（用户）作出决策。 | 阐明分歧本质与可选路径，将决策权呈报用户定夺。 |

---

## 二、 三重独立审查视角

为了防止审查走过场，必须采用三组相互独立的视角对交付物进行层层透视：

### 视角 1：工件静态审查（Artifact Lens）
- **做法**：在阅读实施人员的自述总结前，先直接通读原始代码差异（`git diff`）；
- **目的**：独立形成技术判断，避免被实施人员的自述叙事先入为主所引导；重点排查逻辑漏洞、死代码与格式规范。

### 视角 2：真实执行验证（Execution Lens）
- **做法**：不能仅看静态代码，必须在宿主环境实际运行构建与测试命令；
- **目的**：亲自验证实施人员声称的“功能已修复”是否能在真实二进制中稳定复现并正常运行，防止虚假自测。

### 3. 需求契约强校验（Contract Lens）
- **做法**：重新调出任务最初的需求规格说明书（Spec）与验收标准条目；
- **目的**：逐条核对每一个细分要求是否均有具体的代码实现对应，严禁暗中缩减需求范围，同时也严禁未经授权夹带无关改动。

---

## 三、 审查标准操作流水线

1. **提取基线证据**：
   - 提取原始任务需求、验收标准条目以及实施人员提交的修改清单；
   - 提取已修改文件的 Git 提交版本号与代码差异。
2. **代码与逻辑核验**：
   - 使用 `read_file` 查阅被改动的文件及其调用方；
   - 检查边界条件是否妥善处理，资源是否正确释放；
   - 确认测试用例是否真正覆盖了核心业务分支，而非仅仅为了覆盖率走形式。
3. **出具正式审查报告**：
   - 明确给出最终审查结论（通过 / 要求修改 / 呈报用户决策）；
   - 若要求修改，必须逐条列出：**文件路径 + 代码行号 + 缺陷事实表现 + 建议修正方向**。
