# OpenSpec 变更任务实施指南（openspec-apply-change）

## 概述

指导从已确立的 OpenSpec 变更中读取具体的实施任务清单，逐步开展代码编写、模块重构与功能实现。确保每一次代码改动均严格限定在预设的任务边界与规格约束之内，杜绝未经规划的盲目修改。

## 适用场景

- “开始执行某个已通过提议的 OpenSpec 变更任务”
- “继续跟进实现尚未完成的代码修改清单”
- “针对特定变更中的某项子任务进行编码与单元测试”

---

## 一、 核心操作流程

### 第一步：选择目标变更
- 若用户在输入中明确指定了变更名称（如 `add-user-auth`），直接使用该名称；
- 若输入模糊或未指定，运行状态查询命令获取当前活跃变更列表，并提示用户明确选择：
  ```bash
  openspec list --json
  ```
- 明确输出提示：“当前正在执行变更：`<变更名称>`”。

### 第二步：检查变更状态与结构规范
运行状态检查命令，解析返回的结构化信息：
```bash
openspec status --change "<变更名称>" --json
```
- 查看 `schemaName` 确认采用的工作流程规范（如标准规格驱动流程 `spec-driven`）；
- 查看 `changeRoot` 与 `actionContext` 明确当前变更允许编辑的文件物理边界；
- 确认包含待办任务的具体工件文件路径（通常为 `tasks.md`）。

### 第三步：任务逐步推进与执行
1. **读取任务清单**：完整读取 `tasks.md`，按从上到下的顺序定位当前未完成的首个子任务；
2. **实施代码修改**：
   - 遵循工程流水线规范，复杂业务逻辑委托沙箱环境编写；
   - 仅修改与当前任务直接相关的源文件，不扩散修改范围；
3. **标记任务完成**：
   - 每完成一项子任务并通过本地测试验证后，立即更新 `tasks.md` 中的复选框状态（将 `[ ]` 更新为 `[x]`）；
4. **循环直到全部任务完成**：全部任务勾选完毕后，提示用户进入下一阶段核验命令（`openspec-verify-change`）。

---

## 二、 检查核对清单

- [ ] 是否在编码前确认了目标变更名称与允许修改的文件边界？
- [ ] 代码修改是否严格对照任务清单逐项展开，未越界修改非相关文件？
- [ ] 任务完成后是否及时将清单中的状态标记为已完成？
