# 技术探针与可行性快速验证指南（Spike）

## 概述

规范在投入正式工程研发之前，设计与执行“用后即弃”的最小化技术探针的标准流程。通过编写高针对性、独立隔离的临时实验代码，在真实运行环境中快速验证核心技术假说、排查未知的底层限制或对比多个候选技术库的实际表现，杜绝在未知风险过高时盲目开工。

**核心准则**：
```
探针代码用后即弃，以获取确凿结论为唯一目的，严禁直接作为生产代码引入
```
探针是探路工具而非正式产品。凡是耗费数天去修饰格式、封装类库的探针都是失败的；探针应以最直接的代码快速碰撞真实环境，一旦得出明确的技术结论并记录在案，其实验代码即可安全清理或归档。

## 适用场景

- “在动手改架构前，写个最小脚本测一下这个库到底支不支持该特性”
- “有两个候选方案，不确定哪个性能更好或配置更简单，需要做个横向对比”
- “涉及底层的网络协议或未经验证的第三方接口，需要验证可行性”

---

## 一、 四步循环验证流程

```
第一步：假说拆解（将复杂诉求拆解为 2-4 个具体的条件-动作-预期判定命题）
  ↓
第二步：方案调研（查阅官方文档与安装环境，确立 1 至 2 种实验路径）
  ↓
第三步：探针实现（在隔离目录快速编写可运行代码，捕捉真实输出）
  ↓
第四步：结论判定（依据真实运行事实出具结论：验证成立、部分成立或证伪）
```

---

## 二、 步骤详细操作规约

### 1. 第一步：假说拆解
将抽象的设想分解为具备明确输入与可观测输出的验证命题：
- **有效探针命题特征**：具备明确的上下文前提、触发动作与判定标准（例如：“给定一个本地 WebSocket 连接，当服务端持续推送数据流时，客户端能否在 100 毫秒内逐块解析”）；
- **排序原则**：按照风险由高到低排序，优先验证最致命、最容易导致整个方案推倒重来的核心风险点。

### 2. 第二步：方案调研与极简设计
- 查阅候选依赖库的官方文档与当前系统环境中的实际安装版本；
- 杜绝过度设计：探针代码中直接硬编码测试参数，严禁引入复杂的配置文件体系、多层依赖注入或打包工具。

### 3. 第三步：独立隔离验证
- 必须在专属隔离目录（如临时目录 `$TMPDIR/spikes/` 或工程根目录下的临时 `spikes/<编号>-<名称>/`）中构建；
- 优先构建具备明确可观测控制台输出的微型测试脚本：
  ```bash
  # 快速构建单项探针
  mkdir -p $TMPDIR/spikes/001-ws-stream
  # 编写单文件验证逻辑并运行
  python $TMPDIR/spikes/001-ws-stream/main.py
  ```
- **双方案横向对照测试**：若需要对比两个候选库（如方案 A 与方案 B），保持相同的测试输入数据并列执行，记录双方的耗时、内存与输出质量。

### 4. 第四步：技术结论判定
每个探针完成后，必须出具结构化结论：
- **`VALIDATED`（验证成立）**：核心假说得到正面证实，并附带确凿的运行输出与数据；
- **`PARTIAL`（部分成立）**：仅在特定参数或前置约束下可行，必须详细记录其触发边界与缺陷；
- **`INVALIDATED`（证伪/不可行）**：方案在当前环境下无法达成目标。**明确的证伪同样属于成功的探针**，它在零技术债务的前提下帮助项目避开了昂贵的错误路线。

## 三、 自检核对清单

- [ ] 探针验证的问题是否具体且具备可观测的明确输出？
- [ ] 探针代码是否在独立的临时目录中运行，未污染正式源码树？
- [ ] 是否在得出明确结论后及时对临时文件进行了清理？
- [ ] 结论判定是否依据真实的终端运行事实，杜绝了凭空推论？
