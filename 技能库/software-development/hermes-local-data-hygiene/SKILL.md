# Hermes 本地运行状态核验与残留清理指南

## 概述

指导在 Windows 操作系统中系统性排查与清理 Hermes Agent 的本地运行状态、历史会话物理残留、依赖组件停放目录与临时缓存，并提供模型路由生效状态核验、数据库物理空间压缩与可用性体检的标准方法。

## 适用场景

- 核实已删除的会话记录与本地缓存是否真正从磁盘物理释放
- 清理已失效的历史会话，回收 `state.db` 占用的磁盘空间
- 版本更新后排查旧版本依赖环境与临时目录是否有残留
- 用户反馈在界面中切换模型后，系统未能成功维持选择，而是自动回退到默认模型或直接连接至官方云端接口，需要排查主模型路由配置
- 执行系统健康体检，输出包含具体测试数据的服务运行状态核验表
- 梳理当前系统配置的网页检索与内容抽取后端，明确底层实际调用的引擎与通道

---

## 核心约束与操作前置红线

1. **数据库操作保护**：Hermes 进程运行期间，严禁使用外部文件工具直接删除或修改 `state.db` 与 `state.db-wal` 文件；预写日志仅允许通过 SQLite 的 `PRAGMA wal_checkpoint(TRUNCATE)` 指令安全截断。
2. **进程管理原则**：结束进程时必须按具体的进程 ID（PID）操作，严禁按进程名称批量结束进程，避免干扰正在运行的正式服务。
3. **只读排查优先**：用户提出“检查”或“核对”要求时，必须保持只读操作。先输出确凿的事实依据与分析结论，待用户明确指示后再执行清理。
4. **保留审计与输入资产**：技能审计记录文件 `skills/.curator_ledger.jsonl` 和操作历史文件 `.hermes_history` 默认予以保留，并在报告中注明保留原因，不执行静默删除。
5. **环境判定依据**：在判定 Python 虚拟环境残留前，先运行 `hermes doctor` 查看 `Runtime venv staged` 提示行确认当前生效的运行环境，不以目录创建时间的新旧进行主观推断。

## 一、 会话同步与清理状态判定（只读）

1. **会话数据核对**：
   - 运行 `hermes sessions list` 与 `hermes sessions stats`，核对有效会话总数是否与预期相符；
   - 检查 `sessions/` 目录，确认其中仅保留当前活动会话的文件。
2. **索引与消息双向一致性检查**：
   ```sql
   -- 检索存在于全文索引中但在消息表中已缺失的孤立记录
   select count(*) from messages_fts where rowid not in (select id from messages);
   -- 检索存在于消息表中但在全文索引中未建立映射的记录
   select count(*) from messages where id not in (select rowid from messages_fts);
   ```
   注意：`messages_fts_trigram` 缺少部分数据属于正常现象，该索引按设计不收录 `role='tool'` 的工具调用明细。
3. **其他数据库中的关联检查**：
   - 检查 `shared-state.db`、`projects.db` 等辅助数据库中是否存在已删除会话的遗留关联。
4. **桌面端不显示但 dashboard 可见的会话（来源过滤规则）**：
   - 两个界面用的是两套过滤条件，不是数据不一致。桌面端会话选择器排除 `INTERNAL_LISTING_SOURCES`（`kanban`、`tool`、`oneshot`）加 `api_server`，并且只保留 `cli`/`tui`/`gui`/`desktop`/`local`/`cron` 六类本地来源（`gateway/session_listing.py`）；
   - dashboard 的会话页默认只排除 `cron`/`tool`/`oneshot`/`api_server`/`acp` 这些“自动化”来源（`web/src/pages/SessionsPage_sources.tsx`），其余都列。
   - **推论**：`oneshot` 会话（图片识别、算式、短文本生成等内部一次性调用）永远不会出现在桌面端，但会在 dashboard 堆积。用户说“desktop 不显示但 dashboard 能看到”时，先按 `source` 分组统计，不要当成数据库损坏。
   - **取证 SQL**：
     ```sql
     SELECT source, COUNT(*) FROM sessions GROUP BY source ORDER BY 2 DESC;
     ```
5. **按来源批量删除前必须做 dry-run 并区分测试残留与有价值记录**：
   - `hermes sessions prune --source <来源> --dry-run` 先看清单，确认条数、时间跨度与标题；
   - `prune` **只删已结束的会话**（`ended_at` 非空），未结束的会自动跳过并在输出里提示。当前活动会话天然安全，但仍需核实；
   - 未结束的会话要单独删，命令是 `hermes sessions delete --yes <完整会话ID>`（不带 `--yes` 会停在交互确认）；
   - **不要按 source 一刀切**：`subagent` 来源里可能混着有价值的审查记录（多路并行审查的原始结论），与测试残留同源。先列标题与消息数给用户确认再动手。
   - **删前必备份**：`cp state.db state.db.bak-$(date +%Y%m%d-%H%M%S)`。

## 二、 数据库存储空间与空闲页判定

SQLite 默认未开启物理安全擦除和自动收缩：删除记录时仅将数据页标记为空闲页，文件体积不会自动缩小。
- **未回收空间计算公式**：未回收空间大小 = `PRAGMA freelist_count;`（空闲页总数） × `PRAGMA page_size;`（单页字节数）。
- **残留物理量化方法**：
  - 在当前已删除会话的场景下，直接在二进制文件中检索会话 ID 并统计行数；
  - 与 SQL 中实际有效行内出现的次数对比，二者的差值即为滞留在空闲页中的历史旧字节。
- **避免将自身回显误判为残留**：
  - 当前会话在执行查询命令时，工具输出结果本身包含被查询的会话 ID，会被记入当前会话的消息记录中；
  - 必须结合 SQL 数据归因核对，避免把当前查询命令的回显误判为清理失败。

## 三、 标准物理清理流水线

彻底释放磁盘物理空间必须按如下顺序执行：

1. **备份当前需要保留的活动会话**：
   ```bash
   hermes sessions export --format jsonl --session-id <会话ID> --yes <备份输出路径>
   ```
2. **清理关联子表中的孤立数据**：
   - 在同一个数据库事务中，清理任务派发表 `async_delegations`、租约表 `session_turn_leases` 和过期心跳记录。
3. **截断预写日志**：
   - 执行 `PRAGMA wal_checkpoint(TRUNCATE);`，将 WAL 文件清零。
4. **执行全库物理重整与空间回收**：
   - 运行 `hermes sessions optimize`，合并全文索引分段并触发底层 `VACUUM` 重整文件。
5. **清理文件级临时副本**：
   - 清理 `logs/process-results/*`、`images/*`、`pastes/*` 和 `spawn-trees/*` 下已失效会话的临时文件；
   - 清理 `desktop/interrupted_turns.json` 和 `runtime/active_sessions.json` 中已经失效的会话记录。
6. **最终强校验**：
   - 执行 `PRAGMA quick_check;` 确认数据库结构完好，核对 `freelist_count` 为 0。

## 四、 版本更新后的环境与依赖残留核验

更新完成后，必须先判定更新流程是否完全走完，再排查依赖残留：

1. **核对更新流程是否完整走完**：
   - 检查 `logs/update.log` 末尾是否记录了配置检查完成与网关服务正常拉起的提示；如果停留在源码准备失败行，说明后续网关重启和配置迁移并未执行；
   - 检查 `logs/update_receipts/` 目录下的执行凭证 JSON，确认退出状态码为 0。
2. **系统服务重启义务文件**：
   - 若系统检测到代码已拉取但服务尚未重启，会在主机状态目录写入 `gateway-locks/host-update-restart.json` 标记；
   - 该文件属于系统层级的待重启凭证，运行 `hermes gateway restart` 重启服务后，该文件会自动解除。严禁手动删除该文件。
3. **定位当前生效的真实运行环境**：
   - 运行 `hermes doctor`，以 `Runtime venv staged` 行输出的绝对路径作为判断当前真实环境的唯一标准。
4. **旧版运行环境清理**：
   - 确认当前生效环境后，已弃用的历史旧版本虚拟环境目录可以安全清理；
   - 删除前必须使用 PowerShell 检索是否有正在运行的旧进程占用该路径，按 PID 结束相关进程后再执行清理。
5. **组件停放目录（`.previous-*`）与长路径处理**：
   - 包管理器在替换旧组件时会将旧目录重命名为 `tools/.previous-<组件>-<版本>/`，如果包含层级极深的深层文件，容易超出 Windows 默认的 260 字符路径限制导致删除报错；
   - **可靠清理方案**：先将该目录整体移动或重命名到根目录短路径下（如重命名为短路径名称），由于移动目录不递归遍历深层文件，不受路径长度限制；随后在短路径下执行删除即可顺利完成。

## 五、 高频重连排查与日志过大分析

当用户反馈界面出现高频刷新或大量输出时，必须区分真实原因：

1. **终端显示刷新与日志文件的区别**：
   - 终端界面中看到的动态内容源自界面的实时重绘或子进程的输出，并不是直接读取日志文件；
   - 日志文件单独写入在 `logs/` 目录下；如果发现 `gui.log` 或 `agent.log` 单日生成数十兆且频繁轮转，说明存在高频异常记录，已轮转的历史日志（如 `.log.1`）可安全清理。
2. **区分正常重绘与连接异常**：
   - 正常的界面重绘在无用户交互时保持静止；
   - 如果网络连接在固定的整数秒周期（例如每次连接恰好持续 60 秒）断开并重新建立，说明触发了固定超时机制，属于连接异常而非正常刷新。
3. **通过连接数精确定位故障来源**：
   - 服务端不同模块可能共用相同的日志记录器名称，不能仅凭日志中的名称判定请求方；
   - 统计当前处于 `ESTABLISHED` 状态的 TCP 连接数量与进程 ID。如果浏览器或前端服务占用了绝大多数连接，即可直接确认重连请求来自对应的客户端页面。

## 六、 模型路由核对：切换模型后自动回退问题的排查

当用户反馈在界面中切换模型后，系统未能维持选择，而是自动回退到默认接口或官方端点时，保持只读进行排查：

1. **核对核心配置文件**：
   - 检查 `config.yaml` 中的 `model:` 段（包含 `provider`、`base_url`、`api_mode`、`key_env`）与 `providers:` 段；
   - 检查 `$HERMES_HOME/.env` 中是否配置了对应的 API 密钥。
2. **日志中服务商标记的生命周期**：
   - 日志中记录的服务商标记是进程启动时加载的快照，不会在运行中动态感知配置文件的变更；
   - 检查新拉起的独立命令行会话输出的标签，确认新启动的进程是否能够正确读取最新配置。
3. **凭据池同名影子条目的鉴别**：
   - 检查 `auth.json` 中记录的端点地址与指纹。若配置了自定义网关，即使服务商名称沿用了官方标识，只要目标服务地址指向本地反向代理，就属于使用自定义接口，并未回退到官方服务。
4. **模型切换逻辑判定**：
   - 通过图形界面明确选择服务商时，系统严格按提交的服务商标识路由，若缺失凭据会明确报错，不会静默改投其他通道；
   - 仅当输入的模型名称不在任何已知列表中时，系统才会维持当前现有的服务商不变。

## 七、 系统运行状态与服务可用性体检

当需要全面核验系统当前运行健康度时，执行只读检查并输出具体数据：

1. **有效会话数**：运行 `hermes sessions list` 查看当前保留的会话总数。
2. **配置文件状态**：核实 `config.yaml` 中配置的默认模型、接口地址与协议模式。
3. **环境密钥检查**：检查 `.env` 文件中各服务商的密钥是否在位。
4. **本地服务端口连通性**：通过本地请求测试自定义网关和仪表盘服务的 HTTP 状态码（返回 200 或 401 均证明底层端口正常处于监听状态）。
5. **最近调用记录取证**：读取 `logs/agent.log` 最近的数条 API 请求记录，核实实际调用的模型名称与接口地址。

---

## 八、 网页检索与内容抽取后端架构梳理

当需要了解系统网络检索与页面抓取的底层通道时，依据以下规则核实：

1. **插件化扩展机制**：所有检索后端均以插件形式存放在 `hermes-agent/plugins/web/<服务商>/` 下，分为搜索（`web_search`）和正文提取（`web_extract`）两类能力。
2. **后端服务商与搜索引擎的区别**：
   - 检索后端名称代表服务提供方接口，而非具体的搜索引擎；
   - 多数提供方基于自建索引或专有检索 API 提供服务。若需要指定使用国内主流搜索引擎，需通过接入专用的检索 MCP 服务实现。
3. **调用记录取证**：从 `logs/agent.log` 中检索包含 `Web search via` 的记录行，直接查证实际使用的底层检索接口。

## 九、 交付汇报规范

1. **结论先行**：首先用一句话明确回答“数据是否已清理”、“是否存在异常残留”。
2. **数据对比表**：提供清理前后的精确数值（物理文件大小、数据库记录行数、空闲页数），数据来源于真实命令输出，杜绝估算。
3. **保留项说明**：列出予以保留的文件路径并逐一说明保留的技术理由。
4. **后续建议**：仅保留一个需要用户决定的确认事项，不提供含混的多选列表。
