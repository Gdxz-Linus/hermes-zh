# 文档与实现对齐：双向清点、三要素联动与反向检索

文档缺陷不会让程序崩溃，但会让使用者按错误的说明配置，并把“配了没反应”归因于产品坏了。这类缺陷的排查有固定程序，不能靠通读。

## 1. 双向清点：文档有的与代码有的

单方向核对只能发现“文档写了但代码不支持”，漏掉“代码支持但文档没写”。两个方向都要跑：

- 从解析器提取全部指令名。Rust 项目里通常是 `config("<name>")` 形式的解析器组合子；`bind`、`server` 这类没有走统一表的名字要单独补上，否则会被误报为“文档有而代码无”。
- **只数 `config("...")` 会漏掉一半指令，必须把 `tag_no_case("...")`、`tag("...")` 一并纳入。** 实测现场：文档 102 项、`config()` 只得 93 项，看上去差了 9 项像真缺陷；把 `tag_no_case` 算上后是 149 项，真正“文档有而代码无”的只剩一个由其它解析器内部处理的组合词。

```bash
grep -oE '(config|tag_no_case|tag)\("[a-z0-9-]+"\)' src/config/parser/*.rs \
  | sed 's/.*("//;s/")//' | sort -u > /tmp/code_cmds.txt
```

  判据：两个集合的差集里如果出现的是 `group-end` 这类“配对词”（由 `group-begin` 的解析器内部消费），不是缺陷，属于提取方法的局限。**下结论前先看差集里剩下的是什么词，不要直接报“文档有而代码无”。**
- 从文档表格提取第一列（指令名列），过滤掉表头、默认值数字、布尔值与 `---`。
- 两个集合相减，分别得到“文档有而代码无”与“代码有而文档无”。

注意：正则提取会混入默认值列的数字与布尔值（`853`、`128K`、`yes`、`no`、`auto`），必须按“只取行首第一列”提取，否则清单里全是噪声。

## 2. 三要素联动：同一配置在文档里的三处呈现

一处配置在文档里通常出现三次，三次都要改，缺一处就是未完成：

1. **配置表格的“默认值”列**；
2. **表格的“示例”列**，以及分步文档里的示例代码块；
3. **代码块行内注释与正文行为描述**。

最常见的漏改位置是第 2、3 处：默认值列改对了，示例列还写着旧端口，示例代码块上方的注释还写着“剩余空间大于 128MB 时才生效”。只比对表格的 diff 看不出这两处。

## 3. 反向特征词检索清零

修改完成后，从被废弃的旧值里提取特征词（旧端口、旧容量阈值、被删除的机制名），在全库无条件检索：

- **通过判据是命中数严格为 0**，不是“主要位置都改了”；
- 检索范围要覆盖整个文档仓库，包括分步文档、首页说明、多语言镜像；
- 命中数大于 0 即阻断交付，逐条确认是残留还是合理引用（例如 `853` 在 DoT 章节里是正确端口，属于合理引用，此时把特征词换成更精确的短语，例如旧示例写法 `bind-https :853`）。

## 4. 行为描述与设计定调相反

比默认值错误更严重的一类：文档描述的行为与代码实际行为相反，而且与项目定调相反。例如文档写“上游故障时用过期数据应急”，而实际实现是“在预取保护期内访问过期记录时立即应答旧数据并在后台刷新”——两者在正常网络下表现相同，只在断网时不同，因此很难被使用者发现，也很难被审查发现。

处理方式：以项目的设计定调文档为准，把文档改写为对可观察行为的直接陈述（“在预取保护期内访问过期记录时立即应答历史数据，并在后台异步刷新”），不要保留旧机制的名字，也不要写“已删除某机制”这类变更叙述——文档描述现状，不描述历史。

## 5. 文档仓库的产物隔离

审查报告、项目基点文档、修改台账属于本地工作产物，不应随文档站一起发布：

- 把它们写进文档站仓库的 `.gitignore`；
- 用 `git status --ignored` 确认四个文件都落在 Ignored 列表里、工作树干净；
- 不要用“提交时不 add”这种依赖人为记忆的方式，那在批量 `git add -A` 时必然失效。

## 6. 交付时怎么陈述

- 先给“改了几处、哪几处、现在是否一致”的结论，再给修改前后对照表；
- 报告里写清每一处的前后值，让使用者能自己核对，不要只写“已校正”；
- 如果上一轮汇报说“已全部修复”而实际有漏改，直接说明漏在哪、为什么漏（只核对了表格主字段、没做反向检索），不要用“已深度校准”这类模糊措辞掩盖。
