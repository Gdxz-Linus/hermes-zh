# 代码仓库缺陷审计（Codebase Defect Audit）

## 概述

对既有代码仓库开展系统性的全流程审计，排查深层缺陷、隐性故障与安全漏洞，交付结构化、具备明确严重等级并包含确凿事实证据的缺陷审计报告。

本技能比单次代码差异审查（Diff Review）范围更广：交付成果是一份经过严格定级、可直接供工程决策与修复执行的完整缺陷清单。

## 适用场景

- “全面分析下这个项目还有什么隐患或问题”
- “对现有系统做一次全面的安全与架构审计”
- 在大版本重构或正式发版前开展全量代码健康体检

## 不可动摇的执行铁律

### 0. 结论先行与使用者视角表达
- 每条回复与报告章节均以明确结论开头（例如“正常/异常”、“存在安全隐患”），先讲用户会碰到什么真实后果，再陈述状态，最后在用户需要时才展开底层机制；
- **逐项分析固定四段，顺序不可换**：① 使用者会碰到什么（讲现象，不先说代码）；② 根因（带文件路径与行号）；③ 影响面（哪些部署会触发、哪些不会）；④ 方案与取舍（可选方案、各自代价、推荐项与理由）。以“文件:行号 + 机制”开篇的条目一律重写——用户读不懂，也判断不了严重性；
- **分析每一条之前先判断是否与其他条目同根**。同根的多条合并成一次修改，并在分析里写明“只修其中一条会留下什么中间状态”；逐条孤立分析、逐条孤立修复，会让用户看到修了一半的系统；
- 严禁堆砌长篇过程叙述（如执行了什么函数、读了哪个文件属于无效冗余）；
- 严格执行本机的《行话参照表》，禁用口语与网络词汇。

### 1. 绝不干扰正在运行的正式系统
- 用户本地可能存在长期运行的生产实例或系统服务，审计测试必须严格执行隔离；
- 测试用例必须绑定未被占用的空闲端口；
- 进程收尾必须精准指定自身拉起的 PID，严禁按进程名称批量结束进程；
- 测试完毕后，必须核验正式实例依然保持健康运行。

### 2. 每项缺陷必须附带确凿证据
- 严禁空泛推测，不写“可能存在问题”或纯粹的代码风格偏好；
- 每项缺陷必须提供：**文件绝对路径 + 代码确切行号 + 源码逐字摘录 + 触发条件与具体影响**。

### 3. 严格标明缺陷来源属性
每项列出的缺陷必须打上明确来源标识，绝不混淆：
- **`[已复现]`**：已在隔离环境中实际运行代码、传入测试用例并真实观察到了异常行为；
- **`[代码核实]`**：已在源代码中完成完整的调用链路推演并确认逻辑存在硬性漏洞。

### 4. 报告先行，未经授权绝不擅自修改代码
- 审计阶段只读排查，未经用户明确决定严禁执行批量写盘修复；
- 提出的每项方案必须经过充分预研：指出不同处理路径的利弊与推荐方案，由用户最终决定；
- 用户要求修复其中某两项时，严格限定只改动这两项，严禁擅自扩大修复范围。

### 4.1 分析与计划必须落成工件，不能只写在对话里
缺陷分析只出现在对话里，用户无法回查、后续阶段也无法引用，等于每一轮都重做一遍分析。固定分工：
- **分析报告**（工件）：每项缺陷一节，按第 0 条的四段式写全。这是问题分析的唯一出处，后续任何阶段只引用编号，不再重复分析；
- **执行计划**（工件）：只写“分几次改、每次改哪几项、动哪些文件、怎么验证、失败怎么回滚”，并引用分析报告的编号；
- **对话回复**：只给分组结论（哪几项一起改、为什么）与需要用户决定的事项，不复述分析全文。

**台账里要记下排查过程中的误判与弯路。** 每条误判写清“当时怎么判断的、错在哪里、正确判据是什么”。这些内容对使用者无用，但对下一轮审查与下一个人价值很高：同一个仓库的同一个机制会被反复踩中（例如“启动日志里缺某字段就判定功能未生效”，实际该字段只在部分日志路径上打印）。不记下来，下一轮会从零重踩一遍。

### 4.2 修复批次按子系统与验证手段分组，不按编号顺序
用户明确要求“每次只改一个问题、可单独编译、单独测试、单独回退”，同时要求“不能为图省事嫌麻烦”。两条并不矛盾，落地方式是：
- **同一子系统 + 同一验证手段的条目合并为一次修改**（例如两个都在监听循环里、都靠同一套真机发包验证的条目），合并的理由必须在计划里写明；
- **改动形态不同的条目必须拆开**（局部加固与跨文件重构），否则失败时无法判断该回滚哪一部分；
- 每次修改给出：改哪几项、动哪些文件、改什么、怎么验证、失败回滚粒度；前一次验证通过才做下一次；
- 用户可能改变分组决定（要求把原本分开的条目合并），照办后必须重新确认“合并后仍能单独验证”这一条是否成立。
- **回到进行中的多批次修复时，先复述批次台账再进入新分析。** 用户隔了若干轮回来问"到哪了""该第几批"，说明进度只存在于对话里、没有可回查的形态。固定做法：批次台账（第几批、覆盖哪些编号、已完成哪些、剩余哪些按级别分组）写进修改台账文档并保持最新；每次接续先给出这张表与下一批的候选编号，再展开分析。让用户自己追问批次号，等于把记忆负担推给了他。
- **用户问“怎么分批”时，先给一张按主题分组的表，再逐批说明理由**。分组依据是三个维度相加：使用者可感知程度、修复风险、验证成本。用户会自己决定从哪批开始（可能不按你推荐的顺序），所以每批必须能单独开工、单独验证、单独回退；批次之间不得有前置依赖。表里只写批次号、编号、主题、涉及文件，详细分析留到该批开工前再做。

### 5. 修复必须执行全流程重新验证
- 每次针对缺陷实施修复后，必须重新编译并运行全量回归测试套件；
- 明确陈述回归测试结果数字；
- 涉及文档与配置修复时，严格执行**三要素联动核验**与**反向特征词检索清零**（全库搜索废弃旧值，命中数必须为 0）。三要素指同一配置在文档里的三处呈现，缺一处即为未完成：① 配置表格的“默认值”列；② 表格的“示例”列，以及分步文档里的示例代码块；③ 代码块行内注释与正文行为描述。双语文档必须成组修改。只改“默认值”列而放过示例列与行内注释，是这类修复最常见的漏改位置。
- 修复声称的加固点必须核对**调用点**：改动落在一个无调用者的函数上等于没有修复。核实方法是对被改动的符号全库检索调用方，确认生产入口真的经过它；同一功能同时存在两份实现（内联循环与独立函数并存）是这类错位的典型现场。
- **修复取值、继承或优先级逻辑时，必须同时清点**绕过该逻辑的直读点**。改好访问器后单元测试全部通过、真机仍不生效，是本类缺陷的固定形态：消费方用 `.as_ref().and_then(|r| r.field)` 之类的写法直接解引用节点字段，根本不经过访问器。核实方法是对该字段名全库检索，列出所有读取点，逐个判断是否走访问器，把仍直读的改成走访问器。这类修复必须以真机行为收尾，单元测试通过不算完成。
- **同一能力在仓库里存在多份独立实现时，先合并再修**。典型现场：同一个底层查询（地址解析、配置读取、缓存命中）在三处各自实现，防护水平各不相同——一处有缓存与并发折叠、一处只有缓存、一处两者都没。只修被报告的那一处会留下分叉，下一个报告又会指向另一处。正确做法是抽出一份带完整防护的共享实现，三处消费方全部迁移过去，并在基点文档里写下“该能力只有一个出口”的不变量。
- **“修复打在了无调用者的代码上”是一类固定缺陷，不是偶发失误**。核实方法：对修复函数名全库检索调用方，确认生产入口真的经过它；同一功能同时存在内联循环与独立函数两份实现时，先确认哪一份在跑，再把两者合成一份。只改其中一份而另一份仍在跑，等于漏洞完好无损。
- **删除“死配置”“死代码”前，先查文档是否承诺过“认得但不生效”。** 一个配置项解析了却无人读取，看起来可以直接删，但文档可能明确写着“本程序仍然认得这两行、不会报未识别配置行、只是提示无需配置”——这是对既有配置文件的兼容承诺。把解析一起删掉，老配置在升级后会冒出“未识别行”告警，属于回归，而且委派代理不会主动发现（它只按任务书删，测试也不会覆盖“老配置仍能加载”）。判据：删除前先用 `search_files` 查文档与 README 里该配置项名，看有没有“仍然接受”“不会报错”“无需配置”“行为不变”这类措辞；有则**只删存储字段**（结构体成员与 `Option<T>`），保留 `ConfigItem` 变体与解析规则，`match` 分支改成只打一次说明日志。真机判据：配置里写上这两行，启动日志“未识别行”告警必须为 0、说明提示为 1。
- **每批修复收尾必须主动核对文档站是否需要同步，不能等用户来问。** 用户会直接问「官方网站文档同步了没有」——这一问出现，说明流程里缺了一个固定动作。代码修复改变的可观察行为有四类，每一类都可能让文档站失效：① 取值范围收紧（文档写「大于 0」而代码已夹到 1~16）；② 默认值变化（文档的默认值列写着旧值）；③ 新增上限或告警（文档完全没提）；④ 删除或保留配置项（文档的兼容承诺是否仍成立）。收尾动作：对这四类逐条检索文档站，改完做反向特征词检索清零；双语文档必须成组修改。判断「这条要不要改文档」的判据是**使用者按文档配置会不会得到与文档不符的结果**，不是「代码里有没有这一行」。
- **删除类改动要在派发任务书里写明文档承诺的核查结果，不能只写在分析里。** 委派代理只按任务书执行，任务书没写「文档承诺这两行仍然认得」它就会连解析一起删掉，测试也不会覆盖「老配置仍能加载」，回归要到真机才发现。任务书里必须显式写出：保留哪些、只删哪些、真机判据是什么（未识别行告警为 0、说明提示为 1）。
- **反向验证跑不出失败时，先怀疑缺陷描述本身，而不是怀疑验证方法。** 反向验证（把修复改回旧行为、重跑同一探针）本应得到失败；若仍然通过，第一反应往往是“探针路径不对”，于是反复改探针、反复重跑。更常见的原因是**缺陷描述从一开始就不成立**：报告写的触发条件在真实解析器上根本不会发生（例如“某分隔符会导致整行丢弃”，而解析器只取前缀、忽略尾部剩余内容，任何分隔符都能解析成功）。判据：写一个最小探针直接调用被怀疑的解析或判定函数，喂入报告声称会失败的输入，看它实际返回什么；返回成功即证伪，此时把条目降级为“原描述有误”，在台账里写清实测输入与返回值。改动若仍有价值（语义更准确、去掉静默跳过），保留但改述理由，**不得继续按“修复了一个缺陷”陈述**。
- **“语义不一致”类发现先验证文档是否已明示该语义**。同一参数在两层取值规则不同，可能是刻意的分层设计并在文档里写明（例如“组里写了统一值，本组的上下限都跟它走”）。文档已明示、代码与之一致，就不是缺陷；按缺陷去“修正”会把正确行为改坏。证伪后回滚改动，并把证伪依据（文档行号、探针结果）记入台账。
- **用户定调写在 README 或基点文档里，分析任何“疑似缺陷”前先把那两句读完。** 一个看起来像 bug 的赋值（例如每次刷新把热度重置为 1）往往正是用户定的策略，README 里写着它的目的与配套阈值。把定调当缺陷去“修正”，等于删掉用户要的行为。真正的缺陷通常在同一处但换了形态——**同一个函数同时承担两种语义**（“预取后重置”与“普通写入”共用一个入口），于是本不该重置的路径也被重置。判据：先确认这段代码的**预期语义**（文档 + 调用方意图），再看它是否被**不该走这条语义的调用方**复用；是则缺陷在“复用”，不在“语义”。修复方向是给入口加区分参数，而不是取消原有语义。
- **判断某个字段的默认值必须看它的 `Default` 是 derive 还是手写 impl，不能从某个构造点的赋值反推。** `#[derive(Default)]` 的 `bool` 是 `false`，但同一结构体在别处可能被显式赋成 `true`；看到一处 `is_x: true` 就认为“默认是 true”，会把整条判据推错（进而误判某段代码永不执行、或误判某次调用属于后台路径）。核实方法：搜 `impl Default for <Type>`，没有则看 derive 列表；再看目标字段有没有 `#[serde(default)]` 之类的属性影响反序列化默认值。
- **改写配置文件的接口必须定点操作，不得整文件重新序列化**。典型现场是“读出整个文件 → 解析成结构体 → 修改 → 重新生成全文 → 覆盖写回”。这条链有两个独立故障点：① 解析器遇到无法识别的行会在该行停止并返回“已解析前缀 + 剩余文本”，调用方丢弃剩余文本就等于删掉该行之后的所有内容；② 结构体到文本的输出实现往往只对少数变体有正确写法，其余变体统一输出占位符，于是文件里每一条其它指令都会被换成占位符。核实方法：先看解析函数的返回类型是否携带剩余输入、调用方是否丢弃了它；再对结构体的文本输出实现逐个分支清点，确认目标文件里可能出现的每种指令都有正确输出。修复方向是按行定位目标规则做定点增删改，保留其余字节与行尾（CRLF 不得被改成 LF），并补一条“文件中含无法识别的行时改写后它仍原样保留”的用例。
- **真机验证脚本自身出错会伪装成被测代码的缺陷**。两个固定形态：① 测试用的配置文本语法写错（漏写参数前导短横线、分隔符不对），程序按设计拒绝该行并告警，脚本却把“行为与预期不符”记成代码缺陷；② 判定阈值凭假设写死（例如以为一次查询只打一次上游，实际双栈查询会并发打两次），基线用例本身就是错的，后续所有对比结论跟着错。防错办法：先跑一个“无规则/无改动”的基线用例，把它的实测值作为判定基准，不凭推测写阈值；每次运行都把被测程序的告警日志抓下来，先确认配置被完整接受，再看行为。
- **验证路径必须先确认“真的走到了被测代码”**。回环地址会走特殊分支（例如 ARP 查询对回环直接返回空、不做系统调用），拿它验证“缓存是否生效”测不到任何东西；服务监听非本机地址时需要口令、否则拒绝启动，也会让探针全程拿不到响应。防错办法：先发一个探测请求并抓服务端日志，确认日志里出现了预期的分支记录（例如“ACL 已启用”），再开始计时与计数。
- **反向验证是判定“探针是否真的在检验该修复”的唯一手段**。把修复临时改回旧行为、重建、重跑同一探针，必须得到失败；恢复后再跑必须通过。只做正向验证时，探针可能因为路径不对、阈值太宽而永远通过，把未修复的代码报成已修复。反向验证完成后必须把代码恢复并重跑一次确认。
- **正向一次、反向一次就够，不要反复重跑。** 探针不稳定时应当去修探针（换判据、加日志、隔离干扰），而不是把同一个场景反复跑十几次直到看到想要的数。用户会明确要求“正向、反向各做一次就行”——这是对验证噪声的容忍上限，不是对严谨性的让步：一次干净的正向 + 一次干净的反向，配上能说清判据的日志，比十次结果不一的重复更有说服力。
- **不得把“我没试”写成“无法验证”。** 宣告某项无法真机验证前，先列出它需要的前提（内核特性、特权、特定协议对端）并逐个确认现有环境是否已具备：Linux 内核特性在 WSL 里通常可用（`wsl -u root` 可直接拿到特权），需要特权的命令往往只是没换用户，需要特定对端的场景通常可以自己写一个最小假服务。只有当前提确实不存在、且构造成本远高于收益时才降级为单元测试，并在台账里写清“降级的是哪一层、为什么、完整验证需要什么条件”。用户会直接追问“为什么不能验证”，把“没试”包装成“不能”会当场被拆穿。
- **修复一个缺陷时，同时检查它是否还有第二个必要条件未被报告**。典型现场：把“表满即清空”改成“淘汰最旧的一条”后，若时间戳只在首次插入时赋值，被攻击者自己的记录永远最旧、每次表满都被优先淘汰，计数照样归零、限流照样被绕过。判定方法：把修复放到最坏输入下推演一遍，看原缺陷是否复发；复发就说明需要补上第二个改动，并在台账里写明它为何必要、副作用是什么。

### 6. 委派结论必须自行探针复核，证伪即降级留证
- 子代理返回的每条 P0/P1 都要回到源码核对行号与调用链；涉及**标准库或运行时行为**的结论（溢出是否 panic、是否饱和、是否阻塞、是否可重入）一律先写最小探针实测，不得凭注释或推理采信；
- 实测证伪的条目必须降级，并在报告中写明“原判定 → 实测结果 → 降级理由”，同时把诱使误判的错误注释本身作为独立条目登记——错误注释会持续误导后续每一轮审查；
- 探针要覆盖实际发布的编译版本与两个平台（Windows 与 Linux），同一表达式在两边的基础表示可能不同。

### 6.1 委派代理会顺手做无关改动，收尾必须逐文件核对范围

**委派任务完成后，代理自述“只改了列出的文件”不可直接采信，必须自己看差异。** 实测出现过两类越界：

- **顺手格式化**：任务只要求改一个函数，代理却把整个文件里无关的 `if/else` 拆行、重排 `use` 顺序、把多行 `assert!` 压成一行。这类改动让差异变得无法审查，也把回滚粒度搞乱。收尾动作：逐个文件看差异，凡不属于本次修复的增删行一律还原；还原后重新编译确认。
- **为了不改某个文件而绕行**：任务限定了可改文件范围，代理于是用类型转换实现（如给 `Result` 加 `From` 实现、在里面直接 `exit(1)`）把失败路径藏起来，从而“不改”那个共用调用点。这种做法能编译、能工作，但把退出逻辑藏进隐式转换里，后来的人读不出来。遇到这类绕行，先判断它是否真的必要（共用调用点是否真的不能动），必要则在注释里写清为何这样绕，不必要则改回直白写法。

**判据：`git status` 里每个改动文件都能对应到本次要修的编号；对不上的一律还原。** 还原后重跑全量测试，测试计数变化必须能解释（少掉的那几项就是被还原的临时测试）。

### 7. 文档分层，严禁混放
一次审计需要三份文档，各自只写自己那一类内容。混放会让下一轮审查照着上一轮的结论走，失去客观性：
- **审查报告**：全部缺陷条目、行号、代码摘录、影响分析与修复方案。新发现的缺陷一律补进这里，包括内嵌第三方副本的缺陷；
- **基点/基线文档**：只写项目现状、设计定调、验证基准与审查范围约束（例如“全量审查必须把四个内嵌副本一并纳入，不得遗漏”）。严禁写入缺陷清单、缺陷数量或修复进度；
- **修改台账**：逐项状态、修改明细、验证数字与结项标记，是唯一随修复推进而持续更新的文档。

### 8. 对外文案面向使用者（提交信息与发布说明）
- 提交信息只陈述“修好了什么问题、用户会看到什么变化”，逐条列出可观察的行为修复；
- 严禁写入内部审查编号（P0/P1/P2/P3、批次序号、“第 N 项”）、审计过程与内部术语——这些对使用者与未来的代码读者都没有意义；
- 审查报告、基点文档与台账属于本地工作产物：放在文档站仓库时必须先加入 `.gitignore`，防止随站点一起推送到远端。

### 8.1 发布说明是面向使用者的文档，不是修复台账的摘要
发布说明随版本对外发布，读者是不看代码的使用者。三条红线，违反任何一条都要整篇重写：
- **不写实现细节。** “侧信道”“整数下溢”“符号链接”“栈回溯”“临界区”“套接字”“夹取”“挂载”“消费”“死配置”这类词一律换成使用者能观察到的现象（“口令比对耗时随长度变化，可被用来推测口令”）。保留项目专有术语与配置参数名（双栈、上游、预取、`domain-rules`、`max-reply-ip-num`），使用者本来就懂这些。
- **不写工程度量。** 测试数量、改动文件数、增删行数、内部编号与批次，与使用者无关，整节删除。
- **术语必须先查项目文档站，不得自创。** 同一概念在项目里已有固定说法（例如域名层级统一写“主域名／子域名”，不写“父域／子域”），自创说法会让文档站与发布说明互相矛盾。

修复数量必须按**版本边界**统计，不能只统计最近一轮审查：上一发布标签之后尚未发布的全部提交，加上工作区改动，逐条对应台账条目，扣除误报不改的条目。统计口径写错会让用户当场发现数字对不上。

凡改变既有配置行为的修复（规则继承范围变化、启动失败条件变化），必须单列“升级须知”，否则用户升级后会把行为变化当成升级故障。

完整结构、禁用词清单、中英文同步要求与自检命令见 `references/release-notes.md`。

### 9. “已知缺陷全部修完”不等于“没有缺陷”
- 一轮全量审查不可能穷尽：同一套切片在修复完成后再跑一轮，仍会稳定找到与原轮同量级的新条目，且集中在三类地方——并发窗口（检查与占用不在同一临界区）、死代码与死配置（解析了但无人读取、修复打在了无调用者的函数上）、静默降级（错误被吞掉、截断不告警）；
- 因此交付“已全部修复”之后，必须主动发起第二轮全量复审，并在派发时把第一轮的结论作为“已知事实、不得重复报告”传入；
- 报告结构要能容纳多轮：每轮新增条目接续编号、单列一节，首节的统计表同时给出“首轮/新增/累计”三个数字，不得用新数字覆盖旧数字。

## 缺陷严重等级标准（P0 - P3）

| 等级 | 含义 | 判定准则 |
| :--- | :--- | :--- |
| **P0** | **严重安全缺陷 / 崩溃** | 远程或本地可触发的程序崩溃、内存死锁、机密泄露、数据丢失、未授权访问。 |
| **P1** | **核心功能失效 / 稳定性** | 业务主干功能逻辑错误、高并发资源耗尽、宣称支持的功能实际无法工作、连接泄漏。 |
| **P2** | **容错与抗异常能力** | 边界输入校验缺失、异常处理不严密、超时未受控、环境不兼容但未致命。 |
| **P3** | **规范性与代码整洁度** | 误导性代码注释、废弃未使用代码、配置文档与代码不一致、无危害的冗余。 |

## 标准审计执行程序

### 第一步：代码资产与基线核验
1. 遍历工程目录，统计各语言代码规模与行数；
2. 识别构建体系、程序入口、测试集目录与持续集成配置；
3. 核验 Git 状态（未提交改动、最新提交版本号与发布标签）。若有基点基线文档，必须核对文档记录的路径与哈希是否与物理磁盘一致。

### 第二步：安全网现状检查（测试有效性评估）
在评价源码质量前，先运行项目既有的测试与语法检查：
1. 测试套件当前是否能正常编译通过？
2. 测试用例是否真正走通了生产核心路径？（警惕测试绕过关键包装层、直接测试底层私有函数而导致的“虚假测试通过”）；
3. 检查环境变量依赖：测试环境缺失时应打印说明并跳过，不得保留硬编码的本机默认地址；
4. 区分“全量并行运行失败、单模块运行通过”的用例：这类失败几乎都是测试隔离缺陷而非代码回归——进程级全局状态（全局计数器、全局日志分发器、全局单例锁）被并行执行的其他用例污染。定位方法是单独运行该模块确认全部通过，再检查校验条件是否依赖全局计数器的差值；修复方向是给该模块加一把串行化互斥锁，或把校验条件改成不依赖全局状态的判据，不得通过放宽校验条件掩盖。

### 第三步：搭建安全的隔离测试环境
1. 建立位于代码仓库外部的独立临时工作区（如 `scratch` 临时目录）；
2. 采用空闲端口配置测试实例，确保与用户运行中的系统相互独立、互不干扰。

### 第四步：逐模块深入排查与链路求证
1. 完整阅读核心模块的业务逻辑流；
2. 针对疑点推演因果链路，锁定触发条件与受波及范围；
3. 对所有 P0 / P1 缺陷，必须在隔离环境中通过测试脚本或构造请求报文完成真实复现。

### 第五步：交付结构化审计报告
在指定基准目录或项目目录下输出审计报告文档，统一包含以下章节：
1. **审计结论与总体质量概览**（结论先行，给出各项缺陷数量汇总）；
2. **安全网与运行环境现状评估**；
3. **分级缺陷详单（P0 至 P3）**：每项均标明 `[已复现]` 或 `[代码核实]`、确切文件行号、代码摘录、触发条件与建议方案；
4. **测试保真度与盲区分析**；
5. **后续推进建议与待决事项清单**。
