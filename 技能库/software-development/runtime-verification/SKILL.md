# 宿主真实环境运行验证规范（Runtime Verification）

## 概述

单元测试仅能证明代码内部逻辑符合强校验预期；软件修改是否真正解决问题、是否引入系统级崩溃，必须在宿主真实的操作系统环境与活动网络中加以检验。

本技能规范跨项目通用的宿主验证工程纪律：涵盖真实二进制构建、双平台（Windows 原生与 WSL Linux）对等验证、真实网络报文交互与严格的进程按 PID 释放生命周期管理。

---

## 一、 不可逾越的验证铁律

### 1. 严格界定“单元测试”与“宿主真实验证”，严禁混淆
- 单元测试（如 `cargo test`、`pytest`）属于沙箱内的逻辑自测，绝不能充当宿主真实验证；
- **标准的宿主真实验证流程必须是**：
  1. 在宿主双平台分别编译出真实独立的物理可执行程序（Windows 的 `.exe` 与 Linux 的 ELF 二进制）；
  2. 启动后台真实运行进程，严格绑定未被占用的空闲端口；
  3. 使用真实外部客户端或测试脚本发送网络请求，验证真实业务功能与极端输入边界；
  4. 验证完毕后，**严格依据进程 PID 彻底释放收尾**。
- 试图以跑单元测试代替宿主真机验证，属于偷工减料的严重流程违规。

### 2. 真实环境测试必须由主助手亲自执行，严禁委托给 Codex 沙箱
- 沙箱环境（如 Codex CLI）处于受限容器或独立工作区中，缺乏宿主操作系统的底层网络调用权限、设备控制能力与 WSL 跨平台环境；
- 针对真实系统 API 的验证、网络收发测试与 WSL 跨平台测试，必须由主助手在宿主环境直接执行。

### 3. 真实环境测试失败必须方案先行，再退回修改
- 若宿主真实测试中发现异常或崩溃，严禁直接把原始错误信息抛给沙箱代理让其盲目试错；
- 必须由主助手完成机理归因，输出明确的修改方案后，再调用委托接续接口退回沙箱定向修改，直至双平台全部通过。

### 3.1 单元测试通过而真机失败，先查“绕过了抽象层”的消费方
- 两者结论相反时，不要把真机结果当偶发，也不要回头改单元测试；先认定：改动落在抽象层（访问器、策略函数、统一入口），而部分消费方用直接解引用字段、内联判断等写法绕过了它；
- 定位方法：对被改动的字段名或函数名全库检索全部读取点，逐个判断是否经过抽象层，把仍绕过的改成走抽象层；
- 这类修复只能以真机行为收尾：单元测试走的是抽象层，天然看不到绕过点，它通过不构成完成依据。

### 3.2 启动实例前先确认测试配置真的被接受
- 配置行缺少必需的标记（规则修饰符漏写前导短横、指令名拼写不符）时，程序只打一条警告便忽略该行，被测功能根本没启用；此时观察到的“修复未生效”是测试自身的假象；
- 必须先运行程序的配置自检子命令，强校验其报告通过且无未识别行，再启动实例；
- 真机结果与通过的单元测试矛盾时，回头读一遍启动日志里的警告行——单元测试通常不经过配置解析器，解析器拒绝对它是不可见的。

### 3.3 安全防护类修复的真机验证，以“目标文件未被改动”为主要判据
验证“拒绝跟随符号链接”“拒绝写入非法路径”这类防护时，只看程序是否报错不够：报错可能来自其他原因。必须同时校验三件事：
1. **受保护的目标文件字节未变**（启动前读一次、启动后读一次、收尾后再读一次，三次一致）；
2. **预置的攻击物（符号链接等）仍然存在且未被跟随**；
3. **程序本身正常启动与正常收尾**（防护不能把正常启动一起拦死）。

预置攻击物时必须确认路径完全匹配程序实际使用的路径：程序可能给文件名加后缀（如 `<锁名>.pid`）或加用户标识（如 `smartdns.<uid>.lock`）。把符号链接建在错误目录或错误文件名上，测试会“通过”但什么都没验证到——必须先看程序启动后实际创建了哪些文件，再按那个名字重做一次。

**「不该产生的产物确实没产生」是同一族判据的另一半。** 修复「静默生成并覆盖用户配置」这类缺陷时（例如只配了证书路径、没配私钥，程序却自动生成一对自签证书并把两个路径双双覆盖），主判据不是「有没有报错」，而是**目录里确实没有出现那个产物**。验证方法：启动前后各列一次目标目录，比对新增文件清单；产物为零才算修复成立。同时要跑正向对照——把配置补全后，程序必须正常加载用户自己的文件、且仍然不生成任何产物。只做正向（配全了能用）而不检查「配一半时不生成」，测不到这条修复。

### 3.4 每条真机探针都要做反向验证：先把修复还原，确认探针会失败

**一个探针通过，只证明「当前行为符合预期」，证明不了「它检验的是这次修复」。** 反向验证的做法是：临时把代码还原成修复前的写法，重新编译，跑同一个探针，确认它**失败**；再恢复修复版本，确认它**再次通过**。两步都成立，探针才算有效。

实测必要性：同一个探针在修复前与修复后都「通过」过——因为探针依赖的机制在临时改动里被绕过，探针根本没碰到被测逻辑。不做反向验证就会把无效探针当成证据交付。

还原手法：整文件备份到临时目录 → 用脚本精确替换回旧写法 → 重新编译 → 跑探针 → 从备份恢复 → 再编译 → 再跑探针。恢复后必须用 `search_files` 确认旧写法痕迹计数为 0，不能只看编译通过。

**半还原会让反向验证假通过，而失败现象看起来像「探针无效」。** 只把代码改得「像旧代码」不够，必须还原到**原缺陷的成因**上。典型现场：原缺陷是「计数器按累计数递减、减到 0 就断开连接」，修复换成「信号量只限制并发数、用完归还」。第一次还原时保留了信号量、只把「拒绝该子流」改成「断开连接」——串行查询下许可每次都归还，永远用不完，探针照样全部通过。此时若下结论说「探针检验不到这个修复」，方向就完全错了，真正的原因是还原不到位、缺陷根本没有被重新制造出来。

**正向与反向各做一次即可，不要反复重跑。** 一次正向（修复版本通过）+ 一次反向（还原后失败）+ 一次恢复后确认，三步构成完整证据链。探针反复跑出不一致结果时，问题在探针或模拟对端（见 3.8），重跑不会让结论变可靠，只会拖长验证时间——应当停下来修探针，而不是重试。

**判定还原是否到位，看原缺陷的症状能否复现，不要看代码长得像不像旧版。** 每个缺陷都有可观测的症状（旧日志行、错误的响应码、超出的计数值、被截断的文件）。还原后先确认这些症状重新出现，再去跑探针；症状没回来就说明还原不完整，继续还原。本例的正确还原是把计数器与递减逻辑整段放回去，之后日志里重新出现那条断开记录，探针才如期失败。

**同一判据在文件里出现多处时，要还原真正生效的那一处。** 修复往往把同一个 `if` 判据在多条路径上一起改掉（删除路径、新增路径、批量路径），但只有其中一条是缺陷的实际触发点。还原时只改了非关键路径，探针照样通过，看起来像“探针无效”，实际是缺陷没被重新制造。做法：先 `git show HEAD:<文件> | grep -n '<判据>'` 列出改动前的全部出现位置，逐个判断哪一处处于实际执行路径上（看调用链，不要看位置先后），优先还原那一处；不确定就全部还原。

### 3.5 验证前先确认被测代码路径真的会被走到

**探针的输入必须能触发被测分支，否则跑通也什么都没验证。** 常见陷阱：

- 被测逻辑对回环地址直接短路（如「回环不做地址解析查询」），此时从本机回环地址发起的探针根本不进入被测路径，耗时稳定只能说明短路生效；
- 被测逻辑按协议协商结果分流（如只接受某个应用层协议标识），用不匹配的客户端连接会在握手阶段就被拒，看不到后续行为；
- 被测逻辑受前置校验拦截（如绑定非本机地址且未设口令时程序拒绝启动），实例根本没起来。

判定方法：先看日志里有没有被测路径的专属记录，或让探针的输入带上可区分的特征（不同源地址、不同协议协商结果），确认分支确实被执行。日志里一条相关记录都没有，说明探针打在了别的路径上。

跨机测试被宿主防火墙拦截时，把服务起在 Linux 虚拟化环境一侧、从 Windows 宿主一侧发请求，源地址自然是非回环的真实地址，既能绕过防火墙又能触发完整路径。

**这个方向只对 TCP 成立，UDP 入站仍被拦。** 实测：服务在 WSL 侧监听 UDP 端口，Windows 侧发包过去收不到任何响应，服务端日志也没有收到连接的记录；同一配置下 TCP 可以正常连通。因此验证 UDP 承载的协议（DoQ、QUIC、裸 UDP 的 DNS）时，要把服务起在 **Windows 侧**、客户端也在 Windows 侧，用回环地址即可——如果被测逻辑对回环有短路分支，改用本机的局域网地址并在服务端配置里显式绑定该地址。判断方向对不对，仍然看服务端日志里有没有收到请求：一条都没有就是包没到，不是被测逻辑的问题。

### 3.5.1 不要预设“某项验证做不到”——先查环境能力，再下结论

**“Windows 上验不了内核接口”“WSL 里没有那个命令”这类判断，必须先实测环境能力再作数。** 把“我没试”说成“做不到”，等于把一项本该完成的验证降级成一句免责说明，用户会直接追问。

实测流程（以 Linux 内核 netfilter 集合为例）：

```bash
wsl -e bash -lc 'id -u; which nft; uname -r'      # 命令在不在、当前是谁
wsl -u root -e bash -lc 'nft list tables'          # 换 root 后能不能真的操作内核
```

三步都能过，就说明这项验证在 WSL 里完全可做。普通用户（uid 1000）操作内核接口会失败，但 `wsl -u root` 直接给 root，不需要 sudo 口令。

**“需要 root”不等于“不能验证”；“Windows 上没有这个接口”也不等于“双平台验证做不了”。** 先跑能力探针，再决定是降级为单元测试还是继续真机验证；确实做不到时，报告里要写明“试过什么、卡在哪一步”，而不是直接写“无法验证”。

### 3.5.2 服务与模拟对端必须在同一侧

**被测服务起在 WSL 里时，假上游也必须起在 WSL 里。** Windows 侧的 `127.0.0.1` 与 WSL 侧的 `127.0.0.1` 是两个不同的回环，WSL 内的进程连不到 Windows 侧监听的回环端口，症状是查询全部超时、服务端日志里连上游请求记录都没有。

同理，客户端也要跟着服务走：服务在 WSL，就用 `wsl -e bash -lc 'python3 -c "..."'` 在 WSL 内部发查询；服务在 Windows，就在 Windows 侧发。跨边界的只有一种组合是通的——服务在 WSL、客户端在 Windows 且走 TCP（见 3.5 节）。

### 3.6 启动日志缺某个字段，不等于该功能没生效

**同一功能往往有多条日志输出路径，只有部分路径会打印该字段。** 典型现场：启动日志里「上游服务器」有两处打印循环——带分组名的一处会附带「经由某代理」的信息，不带分组名的另一处完全不打印代理信息。配置里没写分组名时走的是后者，于是日志里看不到代理信息，据此判断「代理配置没生效」是错的。

**判据：不要用「日志里有没有某字段」推断功能是否启用。** 要么读代码确认该字段在哪几条路径上打印，要么直接观察功能的外部可观测效果（对端有没有收到连接、目标文件有没有变化、报文有没有经中转）。日志只用于定位「走到了哪条路径」，不用于判定「配置是否生效」。

**配置解析链本身正常时，不要再往解析器方向查。** 验证顺序：先用单元测试直接验证解析结果（构造一行配置、验证字段被填充），解析正常就说明问题在读日志或运行路径，而不是解析器。

### 3.7 模拟对端的状态管理缺陷会伪装成被测程序失败

自己写的假服务端往往比被测程序更容易出错，且症状随版本漂移。典型三种：

- **握手时序错**：回完协商应答立刻读下一段，而客户端此刻还没发——报「请求不完整」就断开。症状是「服务端从没收到连接」，实际握手已经成功；
- **每连接独立 socket 抢应答**：为隔离状态让每个连接各开一个 socket 绑同一端口，并发（双栈 A+AAAA 两条关联）时应答被另一个 socket 收走。症状是「偶发拿不到结果」，重跑有时好有时坏；
- **共享状态互相覆盖**：「谁是客户端」这类状态被多连接共享，后到的连接把先到的覆盖掉。症状同上。

**可靠做法：不维护「谁是客户端」这类状态，改用报文自身的可判别特征分流。** 以 SOCKS5 UDP 中继为例，按来源端口判断方向即可——来自上游端口的是应答（加协议头后广播给已登记客户端），其余是客户端请求（剥协议头后转发）。这样双栈并发也不会串。

**判据：探针结果不稳定时，先怀疑模拟对端，不要怀疑被测程序。** 把模拟对端的每次收发都打日志（连接、协商、请求、转发、回送各一行），一眼就能看出是哪个环节吞了包。

### 3.8 探针自身写错会伪装成被测行为异常，先区分“路径错”与“行为错”

**探针返回码全表一致（包括用正确凭据时也一样）时，几乎总是探针打错了地址，不是被测逻辑坏了。** 典型现场：所有请求都返回 404，包括用正确凭据的那一次——鉴权中间件根本没被命中，请求落在了不存在的路由上。判定方法：先用一个已知存在的端点（例如版本接口）验证地址前缀，再开始计时与计数。

**判定阈值要按代码里的实际比较符写，不能按“第几次开始”的直觉写。** `if count >= LIMIT` 是在第 `LIMIT` 次就触发，不是第 `LIMIT + 1` 次；写成后者会让一个完全正常的实现被判为未通过。看到“首次触发位置比预期早一位”时，先回去读比较符，不要当成缺陷。

**报告结论前把探针的输出重新对一遍预期。** 探针打印的“结论：未通过”只代表判定条件不成立，不代表被测代码有问题；两者必须分开判断，否则会把探针自己的错误写进交付报告。

### 3.9 时间窗口类缺陷：最终状态相同，必须抓中间态

**当缺陷是「先用宽松权限或不安全状态创建，再收紧」时，修复前后最终状态完全一样，只看最终值必然误判为「本来就没问题」。** 典型：私钥先用 `fs::write` 创建（权限 0644），再 `chmod 0400`；修复改成 `open(mode=0o600)` 创建、写完收紧到 0400。两种写法的最终权限都是 400，差别只在那段可被同机其他用户读取的窗口。

验证方法：写一个高频轮询探针，在目标文件生成期间持续记录权限（或状态）出现过的**所有取值**，而不是只读一次：

```python
observed = set()
def watch(path):
    while not stop.is_set():
        try: observed.add(oct(stat.S_IMODE(os.stat(path).st_mode)))
        except FileNotFoundError: observed.add("absent")
# 启动被测进程，等目标文件出现后再观察一小会儿，然后按 PID 收尾
```

判据：修复版本不得出现宽松值（如 `0o644`）；反向验证（还原成旧写法）必须出现该值。实测快照对照：修复版本 `['0o400','0o600','absent']`，旧写法 `['0o400','0o644','absent']`。

同类缺陷还包括「先写临时文件再改名替换」「先以默认属主创建再改属主」「先启动监听再收紧限额」——凡属「创建时状态不安全、随后补救」的模式，都要按时间窗口验证，不能只看收尾状态。

### 3.10 临时诊断代码必须在收尾时还原，并核对改动范围

**为定位问题而临时加的诊断测试（打印解析结果、验证某个字段被填充）不属于任何修复，收尾时必须还原。** 这类代码容易在后续批次里被遗忘，混进交付的差异里。

收尾动作：
1. 对只装过诊断代码的文件执行 `git checkout <文件>` 还原（这些文件本来就不该出现在本次改动里）；
2. 重新跑全量测试，**测试计数会比带诊断代码时少**（少掉的那几项就是诊断测试），这个差值必须能解释清楚，不能含糊带过；
3. 差异审查时逐个核对改动文件是否都属于本次修复范围——出现「本该没动的文件」就说明有残留。

判据：`git status` 里每个改动文件都能对应到本次要修的编号；对不上的一律还原。

### 4. 绝不干扰用户正在运行的生产服务
- 启动测试实例前，必须先使用网络命令查询目标端口占用情况：
  ```bash
  netstat -ano | grep :<port>
  ```
- 测试实例必须严格绑定未占用的空闲端口；
- 测试收尾时，**必须且仅能依据测试进程的 PID 执行终止**，严禁依据进程映像名称批量结束进程，防止误杀用户正用的生产实例。

### 5. 零污染铁律：严禁在既有项目中制造残留文件
- 临时测试脚本、构造报文与测试日志必须写入宿主临时目录（如 `%LOCALAPPDATA%\Temp\` 或 `%LOCALAPPDATA%\hermes\cache\scratch\`）；
- 严禁为了测试验证流程而向用户的生产仓库中写入临时脏文件；
- 验证完毕后，必须对临时目录与构建产物执行彻底清理，保持生产工作区绝对洁净。

## 二、 全链路验证标准架构（真实程序 + 模拟对端）

当被测程序依赖外部上游服务时，采用“真实二进制程序 + 本地模拟对端脚本”进行全链路真实验证：

1. **构建模拟对端服务**：
   - 使用 Python 编写轻量模拟对端，精确模拟真实协议交互（例如 UDP 与 TCP 绑定指定端口并记录交互请求计数）；
2. **被测进程标准输出持续排空**：
   - 启动被测后台进程时，必须将标准输出重定向或持续读取排空，避免输出缓冲区写满导致进程停止响应；
3. **真实客户端构造原始报文**：
   - 客户端脚本自行构造原始网络协议报文（如 DNS、HTTP 报文），不依赖自带重试逻辑的高级封装工具，确保测试结果反映单次请求的真实响应；
4. **保留正向对照组**：
   - 验证异常输入是否被正确拦截的同时，必须测试标准合法输入是否依然正常响应，防止“一刀切全部拒绝”的错误修改；
5. **先测出基线计数，再对增量做判定**：
   - 双栈服务每收到一次客户端查询，会向上游发出两次请求（IPv4 与 IPv6 各一次）；按“一次查询对应一次上游命中”写判定，会把正确的实现判成故障；
   - 正确做法：先跑一遍未修改的基线，测出真实的单次查询上游命中数，后续判定以该实测值为基准，不凭猜测的常数。

## 三、 Windows / WSL Linux双平台验证规范

针对跨平台系统软件（如网络底层代理、系统网络守护进程），必须分别在 Windows 宿主环境与 WSL Linux 虚拟化环境中完成对等验证：

### 1. Windows 原生测试规范
- 验证 Windows 系统 API（如 IOCP、Winsock、命名管道）在提权与非提权环境下的行为表现；
- 执行进程管理命令时，参数中的斜杠必须严格依据控制台规范转义，严格按 PID 执行精准终止。

### 2. WSL Linux 跨平台验证规范
- **内核接口验证必须获取 root 权限**：
  ```bash
  wsl -d <distro> -u root -- bash -c "..."
  ```
- **清理进程时严禁 `pkill -f <配置名>`**：`wsl -u root -e bash -lc 'pkill -f "x.conf"'` 会匹配到**自己这条命令行**（命令行里就含该字符串），把整个 `bash -lc` 连同后续命令一起杀掉，症状是命令返回非零且后续步骤全部没执行。改用精确 PID：先 `pgrep -f "x.conf" | head -1` 取号，再 `kill <pid>`，最后 `pgrep` 复查为空。
- **向 WSL 写配置文件不要用内联 heredoc**：`wsl -e bash -lc 'cat > /tmp/x.conf <<EOF ... EOF'` 经多层引号与换行传递后可能什么都没写进去（后续启动报“配置文件不存在”）。可靠做法：在 Windows 侧用写文件工具落到 scratch 目录，再 `wsl -u root -e bash -lc 'cp "/mnt/c/.../x.conf" /tmp/x.conf && cat /tmp/x.conf'` 复制并回读确认内容。
- **文件换行符强制规范**：
  - 传入 WSL 中运行的 shell 脚本必须确保为 **LF 行尾**；若包含 Windows CRLF 换行符，会导致 bash 执行抛出 `\r: command not found` 语法错误；
- **输出编码解码规范**：
  - 读取 `wsl.exe` 的标准错误输出时，必须按 `UTF-16LE` 解码；
  - 读取 Windows 原生命令输出时，按系统实际代码页解码，严禁硬解码为 UTF-8 导致脚本抛出解码异常崩溃。

## 四、 交付与自检核对清单

- [ ] 验证的是否为当次最新源码编译生成的真实物理可执行二进制，而非过期的历史产物？
- [ ] 测试实例是否绑定了独立的空闲端口，没有与用户的正式系统冲突？
- [ ] 验证完毕后，是否已通过进程 PID 彻底终止了所有测试进程，没有产生孤儿僵尸进程？
- [ ] 测试生成的临时文件是否已全部从临时目录清理，代码仓库处于绝对纯净状态？
- [ ] 结论汇报中是否明确给出了测试端口、测试进程 PID 与各项确切的测试数值？
- [ ] 全量测试出现失败时，是否用 `git stash` 做过基线对照，确认失败在改动前就已存在？
  ```bash
  git stash push -u -m tmp && cargo test 2>&1 | grep "^test result"; git stash pop
  ```
  不做基线对照就声称“与本次改动无关”，等于把未验证的推断当成结论交付。
- [ ] 每条真机探针是否做过反向验证（还原修复后必须失败、恢复后必须通过）？正向与反向是否各只做一次，而不是反复重跑？
- [ ] 探针结果不稳定时，是否先检查模拟对端的状态管理（握手时序、每连接独立 socket、共享状态覆盖），而不是怀疑被测程序？
- [ ] 是否用「日志里缺某字段」推断过功能未生效？该字段在哪几条日志路径上打印，是否读过代码确认？
- [ ] 反向验证的还原是否真的重新制造了原缺陷（原症状重新出现），而不是只把代码改成了「像旧版」？
- [ ] 验证 UDP 承载的协议时，服务与客户端是否都在同一侧（跨 WSL 边界的 UDP 入站会被拦）？
- [ ] 修复「静默生成产物并覆盖用户配置」时，是否验证了目标目录里确实没有出现该产物？
- [ ] 探针的输入是否确实触发了被测分支（日志里有无该路径的专属记录）？
- [ ] 报告“某项无法验证”之前，是否跑过环境能力探针（命令在不在、换 root 能否操作），而不是凭印象下结论？
- [ ] 服务起在 WSL 时，假上游与客户端是否也在 WSL 侧（跨回环边界连不通）？
- [ ] 清理 WSL 侧进程是否用了精确 PID，而不是会匹配到自身的 `pkill -f`？
- [ ] 反向验证还原的是否是原缺陷实际执行路径上的那一处判据（同判据多处出现时逐处确认）？
- [ ] 探针返回码全表一致时，是否先核对过请求地址与路由前缀，而不是先怀疑被测逻辑？
- [ ] 验证「创建时状态不安全、随后补救」类缺陷时，是否用高频轮询抓过中间态，而不是只读最终状态？
- [ ] 为排查而临时加的诊断测试与诊断文件，是否已用 `git checkout` 还原？测试计数变化能否解释？
- [ ] 判定阈值是否按代码里的实际比较符写（`>=` 与 `>` 差一位），而不是凭“第几次开始”的直觉？
