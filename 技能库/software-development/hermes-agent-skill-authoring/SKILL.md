# Hermes 技能编写与准入管理规范（Skill Authoring & Ingestion）

## 概述

规范 Hermes 自动化技能（Skill）的创建、外部引入、重构与全生命周期维护。从根本上杜绝“自动生成重复技能”、“随意产生全英文技能”、“未经审查直接安装外部技能”以及“满篇互联网行话套话（如‘对齐’、‘钩子’）”等质量失控问题。

**核心铁律**：
```
只有完成两阶段深层查重且确无重叠才编写新技能；功能重叠必须合并融合，正本必须为纯正书面中文
```

详细的两阶段查重实操、外部技能融合范例与生硬机器翻译纠正对照见 `references/skill-dedup-and-merge.md`。

## 一、 技能创建法定流程（防重复与纯中文保障）

当需要将某项成熟的工程方法或业务流程固化为新技能时，必须严格按顺序执行以下四步：

### 第一步：两阶段深层查重（强制执行）
1. **阶段一（列表粗筛）**：
   - 必须先调用 `skills_list` 提取当前系统全部技能清单；
   - 不仅核对名称，更要逐一检索同分类下各技能的 `description` 功能描述；
2. **阶段二（正文精读）**：
   - 凡发现业务领域存在重叠可能的既有技能，**必须强制调用 `skill_view(name)` 查阅其完整正本与参考目录**，彻底核实其覆盖的步骤与规则；
3. **决策分支**：
   - 若既有技能已覆盖该需求：**坚决不建新技能，直接复用**；
   - 若既有技能覆盖了部分内容：**执行第二节的“技能融合流程”，严禁另立新项**；
   - 只有在既有技能完全空白、且具备高度跨会话复用价值时，才准许新建。

### 第二步：标准元数据（Frontmatter）编写规约
必须以 `---` 开头并闭合，采用规范的 YAML 键值结构：

```yaml
---
name: my-skill-name               # 全小写字母与中划线，长度不超过 64 字符
description: "用于……时，执行……。（严格以触发词开头，前57字符包含场景，总长≤60字符）"
version: 1.0.0                    # 语义化版本号
author: Hermes Agent              # 作者标识
license: MIT                      # 许可证
platforms: [linux, macos, windows]# 适用的操作系统
metadata:
  hermes:
    tags: [准确标签, 纯中文, 不超过6个]
    related_skills: [关联技能名]
---
```

#### `description` 触发词强制规范：
- **前 57 字符决定触发成败**：系统在每次会话开始时会将 description 截断至 57 字符展示给模型。因此，**必须在前 57 个字符内完整交代触发场景**；
- **固定祈使句式**：必须以“**用于……时**”、“**当需要……时**”或“**处理……时**”明确开篇；
- **严禁使用修饰性套话**：严禁出现“强大的”、“高效的”、“完美的”等无意义形容词。

### 第三步：正文纯中文规范
- 技能的全部正文、操作步骤、自检清单与原则说明，**必须使用标准书面中文撰写**；
- 命令行指令、代码字面量、系统 API 参数与文件后缀保留原生英文；
- **坚决杜绝生硬口语与大厂黑话**：
  - 严禁使用“**钩子**”，统一根据其职能表述为 **“拦截机制”**、**“拦截函数”** 或 **“拦截代码”**；
  - 严禁滥用“**对齐**”，必须按真实技术动作拆解为 **“保持严格一致”**、**“严格对照 RFC 表格”**、**“参考官方实现”**、**“如实反映实测”** 或 **“靠左/水平居中排列”**；
  - 严禁滥用“**盘点**”，按真实动作拆解为 **“代码统计分析”**、**“空间占用统计”**、**“查阅支持清单”** 或 **“清点/核对交付成果”**；
  - **代码与底层系统类文档翻译方法论（突破代码翻译难题）**：
    - **真实物理动作优先**：将所有抽象术语还原为底层物理动作与数据流向（如说明 Checkpoint 是“执行检查点操作把临时日志写回主数据文件并清空日志”；说明 WAL 是“临时操作日志保留被删数据镜像”；说明 VACUUM 是“重整数据库文件并将多余空闲页真正归还给操作系统”）；
    - **通俗大白话讲透机理**：杜绝概念堆砌与老旧教材机翻腔，用第一遍就能看懂的自然中文交代因果（如将单步步过/步入/跳出拆解为“执行下一行/跳进函数内部逐行查看/执行完跳出当前函数”；将无头环境改述为“没有图形界面的远程或终端环境”；将调用栈回溯改述为“查看函数调用链路”）；
    - **保留专业英文标识作为精准锚点**：核心命令、系统参数、数据库指令与国际通用协议代号（如 `Checkpoint`、`WAL`、`Backtrace`、`CDP`、`DAP`、`MSIX`）在首次定义或参数对照表中**自然保留括号英文**，严禁简单粗暴删英文来掩盖糟糕翻译，确保排障时能与系统日志和命令行精准交叉验证；
    - 严禁出现口语、大厂套话与生造词（如“卡点”改称“问题/延误原因”；“产出”改称“生成/产物”；“由用户拍板”改称“由用户决定”；“走代理”改称“使用代理”；“产物修改时间正在推进”改称“产物文件修改时间不断更新”；杜绝生造“闭环循环图”等晦涩名词，业界公认术语如“PDCA 循环”无需画蛇添足机械翻译；禁用“卫语句”、“圈复杂度”、“沉淀”等）。

    - **杜绝以“卡片”统揽一切的生硬直译**：凡由 `MEDIA:` 交付的带下载与预览按钮的文件条目，严禁称为“文件卡片”或“交付文件卡片”，统一规范表述为“文件交付附件”或“可下载文件条目”；系统架构图中的容器统一称为“组件节点”；演示文稿排版统一称为“分栏内容区块”或“要点列表框”；模型文档统一称为“模型技术说明文档”；敏捷看板中统一称为“任务条目”；真实支付场景中明确写为“信用卡”或“支付卡”。

    - **高频技术词语境化精准翻译铁律（严禁机械词到词硬套）**：
      - **`hook` 依真实技术动作与语境精准还原**：在命令或工具拦截场景译为“插件拦截”或“拦截代码”；在插件扩展接口计数时译为“扩展点”（如“个扩展点”）；在网关事件生命周期与通配订阅时译为“事件回调”或“订阅……事件”；在 shell 外部脚本时译为“shell 回调脚本”。
      - **`placeholder` 依所指具体对象精准还原**：历史消息或工具输出截断替换时译为“简短提示”或“简短标记”；文件读取去重时译为“一段简短说明，不再重复内容”；环境变量与模板参数替换时译为“变量引用”或“模板变量/变量名”。
      - **`budget` 依计量对象精准还原**：对话轮次上限时译为“最多 N 轮 / 轮次用尽”；迭代限制时译为“迭代上限”；单回合耗尽时译为“迭代次数或成本额度已用尽”；文本压缩篇幅分配时译为“摘要篇幅”；终端资源监控面板（如 TUI 的 token 计数面板）译为“用量”；仅在真实财务收支场景保留“经费开支计划”。
      - **`headless` 依运行形态精准还原**：浏览器后台静默运行场景一律规范表述为“后台运行的浏览器”或“后台运行的 Chromium”。

### 第四步：安全校验与先审后发纪律
0. **写技能正文时，拦截插件会当场拦住你自己的用词**：`skill_manage` 的写入内容同样过行话扫描，命中《行话参照表》词条或黑话时直接拒绝写入并报出命中的词。遇到拒绝不要反复重试同一段文字，按报出的词逐个换成规范表述后重新提交；写完后用同一套词表自查一遍，比提交后被打回快。
1. **自动化质量扫描**：由 `skill-guard` 插件执行语言与触发词强校验，排查全部违规词与机翻行话；
2. **工作区目录层级必须与原版严格对应**：
   - 技能与工具资产在工作区（如 `<工作目录>\中文技能库\`、`<工作目录>\中文工具库\`）的存储结构，**必须与系统原版目录保持 100% 完全一致的分类层级**（如按 `autonomous-ai-agents/`、`software-development/`、`plugins/openspec/skills/` 等分类子目录归档），严禁扁平杂乱散落；
3. **工作区暂存与用户首审铁律（严禁擅自提前转正）**：
   - 技能编写或重构完成后，正本一律首先在工作区完成写盘；
   - 向用户出具结构化的审查报告（包含触发词、核心规则明细与中英文对照），**严格停在“待用户审核”状态**；
   - 绝不允许在未经用户审阅同意前擅自覆盖系统正式目录；
4. **经明确授权后执行备份转正**：
   - 仅在用户明确给出“转正”、“确认发布”等肯定指令后，方可启动转正流程；
   - 转正必须严格执行安全规约：**先将系统原英文目录完整备份至 `<工作目录>\原英文技能备份\`，再覆盖写入系统正式目录，最后调用 `skill_view` 抽检核实生效状态**。

## 二、 外部技能引入与融合规范

从官方 Hub、ClawHub 或第三方仓库获取外部技能时，**严禁在终端直接使用 `hermes skills install` 盲目安装**。必须执行以下融合流程：

### 1. 工作区暂存与审查
- 先将外部技能下载解压至工作区临时目录（如 `<工作目录>\中文技能库\temp\`）；
- 阅读其 `SKILL.md`，提炼其核心能力与依赖。

### 2. 查重比对与宿主定位
- 调用 `skills_list` 和 `skill_view`，在本地技能库中寻找承接该能力的宿主技能：
  - 例如：外部文档排版技能应合并入 `chinese-word-format` 或 `docx`；
  - 外部特定代码重构模式应合并入 `simplify-code`。

### 3. 定向追加与融合
- **绝不另起炉灶新建技能**；
- 提取外部技能中具有实际价值的技术参数、特殊算法或数据表格；
- 使用 `patch` 动作，将其以新的操作小节或参考资料文件（`references/`）形式追加进宿主技能中；
- 在宿主技能的 `tags` 中补充新场景关键词。

### 4. 纯化验收与上线
- 对合并后的文档执行词汇扫描，确认彻底清除了所有口语与生硬直译；
- 将优化后的正式技能部署入系统技能目录，清理工作区临时目录。

### 5. 技能库资产维护的取长补短双向合并原则（区别于核心代码）
- **核心代码与系统配置**：追求严格的字节一致，以版本库主分支为准；
- **技能库完全不同**：技能承载跨会话积累的经验、工作习惯与技术避坑点。不同会话、系统运行环境与工作目录可能各自增补了不同的重要规则；
- **同步技能严禁单向盲目覆盖**：绝不能直接把旧版工作目录覆盖到系统，也不能单纯把系统版直接冲刷工作目录；
- **法定双向合并标准流程**：
  1. 首先备份系统新版（以防丢失最近会话中的微小规则更新）；
  2. 逐文件比对工作目录与系统版本，各取所长、双向合并，保留双方各自的新增有效规则与避坑说明；
  3. 执行严格的书面中文审查，彻底清洗残留行话与生硬机翻；
  4. 将合并优化后的版本同时回写工作目录与系统技能目录，保持双向一致。

### 6. 技能在程序升级时的存活机制是哈希比对，不是「升级不碰」

技能存放在用户层 `$HERMES_HOME/skills/`，但仓库 `skills/` 会定期同步过来，不能简单归为「升级不动」。`tools/skills_sync.py` 的规则：

- 新技能：直接复制并记入 `.bundled_manifest`；
- 已有技能：仅当「仓库版变了」且「用户副本仍与清单里的原始哈希一致」才更新；
- 用户改过的（哈希对不上）：跳过，不覆盖；
- 用户删过的：不重新加回来。

**判定某技能是否属于「用户已改」**：比对它在 `.bundled_manifest` 里记录的哈希与当前目录哈希，不同即已改。

```python
from tools.skills_sync import dir_hash
from pathlib import Path
h = dir_hash(Path('skills/creative/humanizer'))
# 与 .bundled_manifest 里 humanizer:<hash> 对比，不同即用户已改，升级会跳过
```

**推论**：汉化或定制过的 `SKILL.md` 升级后不会被冲掉，但仓库新增的技能会被补装。这意味着技能层是汉化最安全的落点，无需额外覆盖机制。

**但加载优先级不是用户层最高**：`get_skill_search_roots()` 的顺序是项目技能目录 → 用户层 → 创建目录 → 外部目录。项目内的 `.hermes/skills/` 会盖过用户层同名技能。排查「技能改了不生效」时先确认没有项目级同名技能。

## 三、 底层工具、语言包与文档内嵌代码汉化安全防线（动说明不动代码，安全四重防线）

工具与插件是大模型的物理执行器（底层 Python 代码），不同于纯提示词文本的技能。此前曾发生工具被误覆盖为空壳导致功能崩溃的严重事故——根因是 Hermes 启动时仅需读取文件内的静态字典（`*_SCHEMA`）即可完成注册，而被抹空了所有执行函数的空壳文件在 `py_compile` 语法校验下依然 100% 合法，从而瞒过了简单自检。

为彻底杜绝再次损坏代码，工具与插件汉化必须严格遵守以下物理安全边界与四重程序级防线：

1. **绝对禁止触碰的机器红线区**：
   - 工具名（`name`，如 `read_file`、`terminal`）与参数键名（如 `path`、`command`、`tasks`）是机器通信接口，改动会导致系统报找不到函数错误；
   - 机器取值约束（`enum` 数组，如 `["replace", "patch"]`、`["todo", "done"]`）严禁翻译，必须保持原版英文字面值；
   - 所有 Python 函数体（`def handle_xxx`）、类、导入语句与运行时变量分毫不可删改；
2. **仅汉化语义说明区**：
   - 仅将面向模型阅读的工具功能描述（`description`）、具体参数用法说明（`properties.*.description`）与插件清单文件（`plugin.yaml`）改写为通俗规范的工程书面中文；
3. **防线 1：单点精准定向替换，严禁全文件覆盖写盘**：
   - 替换工具 Schema 时，**严禁整文件重写或大段切片覆盖**，防止误伤底层的 CLI 调度器、进程生命周期与关键函数；
   - 必须使用唯一的字面值字符串执行精准单点替换（`replace`），绝不触碰函数声明与上下文结构；
4. **防线 2：代码行数物理熔断守恒校验（防空壳覆盖）**：
   - 写盘前后程序必须自动比对源码行数：修改后行数与原版备份行数必须严格守恒（差值 $\le 2$ 行）；
   - 一旦检测到行数异常缩减，程序立即触发物理熔断，强行中止写盘并恢复原状；
5. **防线 3：符号表 100% 守恒强校验与真实 import 冒烟测试**：
   - 提取修改前后的 AST 符号表（所有 `class` 与 `def` 函数名集合），强校验 100% 完全相同，绝不允许丢失任何一个函数；
   - 写盘后必须编写脚本在独立进程中真实动态 `import` 该模块并反射核验注册变量，彻底杜绝 `NameError` 导致后台服务启动时闪退；
6. **防线 4：汉化后必须与原版生成统一差异比较逐行审查**：
   - 修改完成后，必须调用 `difflib` 生成与原版备份的统一差异比较，逐行核验变动行（`+` 和 `-`）是否全部且仅发生在说明文字内部，确凿证明业务逻辑与代码结构 0 破坏；
7. **语言治理最高原则：在源文件里按语境把翻译做准，优于在下游机械替换**：
   - 严禁在系统提示词与拦截插件中无节制堆砌词到词硬替换规则，避免增加维护成本与无谓的上下文 Token 消耗；
   - 英文技术词汇一词多义，死板替换必然脱离语境；根本办法是：**在技能正本、工具定义、插件说明的源文件里，就对照其真实业务语境翻译得通俗、地道、恰当**；
   - 区分正规工程术语与空泛黑话：正规国家与国际标准技术术语（如独立端口或网络层面的“物理隔离”、数据层面的“执行完整性”）在真实工程场景下属于正规严谨表达，不可盲目扩大化打击；
8. **应急恢复命令优先使用 Python 标准库**：
   - 遇到故障需要向用户出示修复命令时，严禁使用依赖特定终端语法的指令（如 PowerShell 的 copy 实际上是 `Copy-Item` 的缩写，不支持 `/y` 参数，且会把 `HEAD~1` 的波浪号误展开为用户主目录导致命令报错）；
   - 优先出示跨平台跨终端 100% 兼容的 Python 脚本命令（如 `python -c "import shutil; shutil.copyfile(...)"`），彻底避开 CMD 与 PowerShell 的符号和参数差异；
9. **文档内嵌代码与注释修改的零触碰红线（代码完整性保证）**：
   - 修改 Markdown 技能正本或文档内的代码块（如 Python、Shell、HTML 等）时，**仅允许修改代码行内部的自然语言中文注释与说明字符串，严禁改动任何代码变量名、函数名、逻辑结构与调用参数**；
   - 绝不能因清洗文档中文词汇而顺手重命名代码变量（例如：排版代码中的变量名 `card_width`、`card_x` 必须分毫不动，防止代码在执行时因变量未定义抛出异常）；
10. **结构化语言包动态变量完整性守恒**：
   - 修改 `zh.yaml` 等本地化多语言文件时，所有动态变量（如 `{reason}`, `{session_id}`, `{task_id}`）必须 100% 保持与英文原版结构完全一致，严禁遗漏、拼错或破坏变量名；
11. **交付前三层代码完整性强校验流水线**：
   - 任何涉及文档或配置汉化与词汇清洗的任务，交付前必须执行自动化比对校验：
     - **AST 抽象语法树编译校验**：提取 Markdown 中的 Python 代码段运行抽象语法树解析，强校验语法与缩进未损坏；
     - **结构化数据解析校验**：使用专业解析器强校验 YAML/JSON 语法正确、数据层级键值在位；
     - **原版英文双向对照审查**：与原版备份生成差异比较，核验变动行是否全部且仅发生在说明文本与注释内部；
     - **反向特征词检索清零校验**：全库反向扫描被修改或废弃的旧词汇，命中数必须为 0；
12. **系统底层提示词构建模块汉化安全红线与机翻来源阻断**：
   - **从来源切断诱因**：大模型在会话中反复出现生硬机翻，例如“交付文件卡片”，根源往往不是技能正本，而是系统底层平台提示词即 agent/prompt_builder.py 内的 _PLATFORM_HINTS["desktop"] 硬编码了 becomes a card 并每轮注入。必须先汉化底层平台指引，从输入端切断机翻诱因；
   - **提示词来源不止一个文件**：向模型注入顶层指令的源码共十三个，每轮必注入的优先处理。完整清单、各文件生成内容与触发条件、以及定位方法（抽象语法树筛出长字符串常量）见 `hermes-agent` 技能第五节的「提示词来源文件全量清单」，锚点逐项清单见该技能的 `references/prompt-source-localization.md`；
   - **插件工具 Schema 与 `plugin.yaml` 是独立的汉化面**：锚点与禁改边界与提示词源码不同，且同一文件常见「部分已汉化、部分仍是英文」的混合状态，必须用抽象语法树逐项列全而非抽样。完整边界清单与五项校验见 `hermes-agent` 技能的 `references/plugin-schema-localization.md`；
   - **平台指引可汉化范围**：涵盖平台交互提示 PLATFORM_HINTS、终端环境指引 _WINDOWS_BASH_SHELL_HINT、宿主状态提示 _local_host_hints、执行纪律 TASK_COMPLETION_GUIDANCE 与 TOOL_USE_ENFORCEMENT_GUIDANCE 等纯面向模型阅读的文本；
   - **绝对禁止破坏切片锚点常量与协议标记**：系统提示词中的结构化切片常量，例如 RUNTIME_ENVIRONMENT_HEADING = "# Hermes runtime environment"、RUNTIME_ENVIRONMENT_END = "<!-- End Hermes runtime environment -->"、OUT-OF-BAND 等，属于单元测试与外部解析器用来定位和分割上下文的物理锚点，严禁将其翻译为中文；字典键名如 "desktop"、"cli" 与原生工具指令 MEDIA:、::preview、data-hermes-send、skill_view 严禁改动，确保系统底层解析与工具链零故障；
   - **持久化格式常量绝不可汉化**：压缩、摘要、交接类常量会被写入数据库并被其他模块按字面做 SQL 匹配或长度切片，汉化后历史会话无法识别、预览解析失败、旧版本兼容断裂，且不产生任何报错。判别方法：检索常量名，若命中方出现 `hermes_state_common.py`、`SUBSTR`、`INSTR`、`_sql_starts_with`、`_sql_after_marker`、`.split(`、`.startswith(`、`rsplit(`，该常量必须保持英文原样；
   - **汉化会绕过只认英文的正则防护**：源码里存在用英文正则做的语义防护（如检测摘要是否虚构了用户归属）。把被守护的文本改成中文后，这类正则全部失配、防护静默失效。必须同步补上中文分支，并用「中文违规值被拦、英文违规值被拦、合法值不被误拦」三个用例实测；
   - **测试基线必须先量后改**：汉化前先在原版文件上跑一遍目标测试并记录失败数，汉化后失败数必须回到同一水平。原版本就失败的项（常见是测试隔离机制拦截了对真实配置目录的读写）不得误判为汉化引入；改写检查条件时用对应的中文特征词，不删检查、不改成恒真；
   - **翻译质量硬要求**：禁止被动句式与欧化语序。`You are powered by the model named X` 译成「你由名为 X 的模型驱动」是错的，应译成「你实际使用的模型是 X，完整标识为 Y」。禁止机械词到词替换，同一个英文词在不同语境译法不同；
   - **历史会话记忆污染的强制拦截**：对于前文已包含违规旧词的历史会话，大模型受自回归注意力影响会顺势复读；必须在 zh-jargon-guard 拦截插件的输出阶段挂载正则过滤，确保送达用户眼前时被程序强制清洗。
