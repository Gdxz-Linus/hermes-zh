# Hermes MCP 服务器接入与诊断指南（Model Context Protocol）

## 概述

规范在 Hermes 体系下接入、测试与维护各类遵循模型上下文协议（MCP）的扩展服务。涵盖通过本地标准输入输出（stdio）启动的子进程服务，以及通过网络传输（SSE/HTTP）连接的远程服务，并提供针对 Windows 平台下进程停止响应与依赖冲突的系统级修复方案。

## 适用场景

- “接入一个基于 PyPI、npm 或本地自建的 MCP 工具服务器”
- 执行 `hermes mcp add` 时连接失败，或 `hermes mcp test` 报错 `Connection closed`
- 已添加的 MCP 工具在模型工具列表中未列出、调用时报错，或子进程停止响应不退出
- 配置本地检索类 MCP 服务器并确立主备调度策略

---

## 一、 接入前目标判定与分析

1. **官方审定条目（内置目录）**：
   - 随 Hermes 仓库正式发布的推荐服务：执行 `hermes mcp catalog` 可列出目录项，通过 `hermes mcp install <名>` 一键部署；
   - 若本地目录输出 `No MCPs in the catalog or configured.` 属正常状态，仅表示当前未预置审定条目，并不影响通用 MCP 接入。
2. **外部独立条目（PyPI / npm / 自建项目）**：
   - 通用接入一律使用 `hermes mcp add` 指令；
   - **严禁仅凭包名猜测可执行文件入口**：接入前必须查阅官方包主页或元数据，明确其标准的入口命令、所需 Python 版本与底层传输协议。

---

## 二、 stdio 模式标准安装与配置规约

```bash
hermes mcp add <服务名称> --command <解释器或uv.exe绝对路径> --connect-timeout 180 \
  --args tool run --from <包名>==<固定版本> <入口命令>
```

### 关键执行规约：
1. **选项顺序铁律**：`--args` 必须作为整条命令的**最后一个选项**，紧随其后的所有词元均会被原样解析为子进程参数；
2. **连接超时时间合理配置**：首次启动需要从网络拉取依赖包，默认的 60 秒常发生超时，导致报出极具误导性的 `Connection closed` 错误。安装时显式指定 `--connect-timeout 180` 秒；
3. **严格锁定物理版本号**：在 `--from` 中必须明确指定具体版本（如 `<包名>==1.2.3`），杜绝使用动态浮动版本，防止外部上游被动更新引发非预期逻辑变化；
4. **可执行文件使用绝对路径**：必须传入绝对路径（例如 Windows 下使用 `%LOCALAPPDATA%\hermes\bin\uv.exe`），子进程仅继承经过精简的基线环境变量，不依赖终端动态 PATH；
5. **严禁在包装层嵌套中间脚本**：MCP 入口必须为真实的可执行二进制文件，严禁在其外层包裹 `.cmd` 或 `.bat` 批处理脚本，避免引入多余的 `cmd.exe` 进程常驻并引发控制台代码页路径错解。

## 三、 连接异常与环境依赖分层排障

1. **分层探测逻辑**：
   - 在排查故障时，必须严格区分三种状态：“服务端进程无法启动”、“服务端正常启动但 Hermes 协议握手超时”、“服务端正常且内部工具可正常调用”；
   - 可调用内部探测脚本 `scripts/mcp_stdio_probe.py` 绕开上层框架，直接向子进程发送 `initialize` 与 `tools/list` 报文进行底层强校验。
2. **间接依赖破坏性升级隔离**：
   - 当主包仅锁定了自身版本，而其依赖的底层解析库发布了重大破坏性版本时（例如 `selectolax>=1.0.0` 移除了旧解析后端），会导致子进程在模块导入阶段直接崩溃；
   - **修复方案**：在 `--args` 中追加 `--with "<底层依赖><锁定版本>"`（例如 `--with "selectolax<1.0.0"`），强行将其约束在兼容的依赖版本区间内。
3. **工具主备调度策略**：
   - 当系统中配置了高精度的本地检索 MCP 工具时（例如 `search` 提供的 `mcp_search_*`），检索任务应优先调用该工具集；
   - 框架内置的 `web_search` 保持就绪，仅作为备用兜底保障。

## 四、 子进程事件循环未退出问题的工程处理

- **异常现象**：工具调用与数据交互功能正常，但在框架关闭标准输入（stdin）后，后台子进程迟迟不退出，甚至产生数十秒的严重卡顿，最终被超时机制强杀。控制台抛出 `RuntimeError: Event loop is closed`。
- **根本原因**：上游库在执行完业务逻辑后，试图在一个全新创建的事件循环中去异步关闭由原事件循环创建的网络连接池，导致异步任务永远无法被正常等待（await）。
- **工程解决措施**：
  1. 编写独立的进程启动文件（如 `plugins/mcp/<服务名>_runner.py`），由该文件统一掌控唯一的全局事件循环；
  2. 显式完成子连接池的清理，并在完成数据交互后主动平稳退出；
  3. **验收标准**：数据交互后关闭输入流，错误输出（stderr）行数为 0，子进程完全退出耗时小于 2 秒，退出码为 0。

## 五、 自检核对清单

- [ ] 命令参数中 `--args` 是否作为最后一个选项传入？
- [ ] 软件包是否锁定了确切的发布版本号，而非使用通配符？
- [ ] 命令路径是否使用了真实的绝对路径，未包装多余的批处理外壳？
- [ ] 部署后是否发起了一次完整的工具真实调用，验证了子进程的平稳退出？
