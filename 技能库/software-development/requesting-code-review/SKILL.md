# 提交前代码核验与审查准备（Requesting Code Review）

## 概述

在代码正式执行 `git commit` 或合并入库前，强制执行的自动化全流程质量检验流水线。

通过静态安全扫描、基线质量门测试、差异特征审查（Diff Review）与自动化修正流程，确保新提交的代码具备极高可靠性，杜绝将调试残留、硬编码密钥或逻辑缺陷带入主干分支。

**核心铁律**：**任何智能体或开发者均不得充当自身代码的终审者**。必须通过独立的上下文与标准化门禁对改动实施无偏见审查。

## 适用时机

- 完成某项功能新增或缺陷修复后，执行 `git commit` 或 `git push` 前；
- 用户发出“提交代码”、“准备发版”、“完成修改并验收”、“核验一下”等指令时；
- 涉及 2 个以上文件修改的工程任务收尾阶段；
- 软件工程开发流水线（SWE Pipeline）的收尾阶段。

*例外情况：纯文档修改（.md）、无关代码逻辑的非执行说明调整可按需精简安全扫描，但仍需执行三要素联动核验。*

---

## 六步核验标准操作流水线

### 第一步：获取精确的代码差异（Diff）

首先提取所有已暂存的代码改动：
```bash
git diff --cached
```
- 若输出为空但 `git diff` 存在改动，提示将改动文件执行暂存；
- 若差异体积超过 15,000 字符，按文件拆分并逐一进行局部差异审查。

---

### 第二步：静态安全与防错特征排查

针对所有新增加的代码行（`^+` 开头的差异行），执行自动化关键字特征过滤。**任何命中均视为严重安全阻断点**：

1. **硬编码机密与密钥扫描**：
   - 检查是否在代码中直接硬编码 API 密钥、密码、Token 等敏感机密：
     ```bash
     git diff --cached | grep "^+" | grep -iE "(api_key|secret|password|token|passwd)\s*=\s*['\"][^'\"]{6,}['\"]"
     ```
2. **命令注入与执行风险**：
   - 检查非安全的系统命令拼接（如直接使用 `os.system` 或未转义的命令调用）：
     ```bash
     git diff --cached | grep "^+" | grep -E "os\.system\(|subprocess.*shell=True"
     ```
3. **危险动态求值与反序列化**：
   - 检查 `eval`、`exec` 或不安全的二进制反序列化（如 `pickle.loads`）：
     ```bash
     git diff --cached | grep "^+" | grep -E "\beval\(|\bexec\(|pickle\.loads?\("
     ```
4. **临时调试代码残留**：
   - 检查是否残留了临时打印语句（如 `println!`、`console.log`、`print(`）、死代码注释或硬编码的本机临时测试路径（如 `D:/test`、`localhost`）。

---

### 第三步：基线测试与质量门运行

识别当前工程的编程语言与既有构建体系，严格按照项目既有规则执行测试：

1. **测试基线原则**：
   - 只有当前变动新引入的失败才构成阻断；修改前的既有历史失败需单独记录说明；
2. **测试保真度强校验**：
   - 测试必须走生产同一条代码路径，严禁为了让测试通过而绕过生产包装层；
   - 外部依赖与测试地址必须从环境变量读取，缺失时打印说明并优雅跳过，严禁保留不可移植的硬编码默认地址；
3. **质量门命令执行**：
   - 若项目根目录或 `scripts/` 下存在 `quality-gate.cmd`、`quality-gate.sh`，必须直接调用执行；退出码非 0 严禁放行。

---

### 第四步：差异审查（Diff Review）

调用 `diff-review` 原生工具或执行系统级审查，重点核验：
1. **边界条件处理**：空指针、空数组、溢出边界、负数取值是否已设防；
2. **资源妥善释放**：文件句柄、网络连接、临时目录是否均配置了可靠的释放保障；
3. **错误原样向上传递**：是否存在为了让流程顺畅而静默吞掉底层异常（如空的 catch 块）的恶劣实现。

#### 文档类改动的额外门禁

差异中包含 `.md` 等文档文件时，上述三项不足以拦截最常见的漏改。必须额外执行两项核验，任一不过则阻断提交：

1. **反向特征词检索清零**：从本次改动中提取被废弃的旧值或旧表述（旧端口号、旧默认值、已删除机制的描述词），对整个文档仓库执行全词检索，**命中数必须严格等于 0**。仅凭差异比对确认“改过了”不算完成——示例列、代码块与行内注释不在差异里就看不到。
2. **三要素成组核验**：同一配置在文档里有三处呈现，必须同时检查：① 配置表格的“默认值”列；② 表格的“示例”列与分步文档的示例代码块；③ 代码块行内注释与正文行为描述。双语文档必须成组修改，不得只改中文或只改英文。

审查工具可程序化提示这两项（检测到文档改动时输出核验清单），但清单本身不代表已核验，必须实际执行检索并报告命中数。

#### 提交信息面向使用者

提交信息只陈述“修好了什么问题、用户会看到什么变化”，逐条列出可观察的行为修复。严禁写入内部审查编号（P0/P1/P2/P3、批次序号、“第 N 项”）、审计过程与内部术语——这些对使用者与未来的代码读者都没有意义。用户明确要求过这一点，且因违反重写过提交信息。

#### 审查工具的已知盲区

`diff-review` 只看差异文本，不看语义。两类真实缺陷它永远报不出来，必须由人逐条核对：
- **重新序列化破坏内容**：把解析后的结构重新输出成文本时，未实现正确输出格式的类型会变成占位符（如 `[Unformatted Config Item]`），把文件里其它合法内容全部替掉。语法检查拦不住，因为输入本来就是合法的。
- **修复打在无调用者的函数上**：改动落在一个无人调用的函数，差异看起来完美，生产路径根本没经过它。核实方法是对被改动的符号全库检索调用方。

---

### 第五步：缺陷修复与退回重审

1. 若在步骤二至四中发现明确问题：
   - 明确归因并列出具体代码行号；
   - 组织最小化修复方案，修改后必须从第一步起完整重新执行全流程检验；
2. 严禁带病强行交付。

---

### 第六步：交付总结与数据汇报

完成全部审查且全量测试通过后，向用户汇报清晰的交付总结：
- **受影响文件清单**：列出实际修改的文件与变更行数；
- **安全扫描结论**：明确声明已通过机密扫描与命令注入排查；
- **测试验证数字**：明确陈述测试通过用例总数（例如“共运行 42 项单元测试，42 项全部通过，0 项失败”）；
- **结论陈述**：明确确认代码已具备提交入库条件。
