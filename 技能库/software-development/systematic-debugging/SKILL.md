# 系统性根因排查（Systematic Debugging）

## 概述

盲目尝试修改不仅浪费时间，还会引入新的衍生缺陷；仓促的临时补丁往往会掩盖深层设计问题。

**核心原则**：在尝试任何代码修复前，必须先查明根本原因。只针对表面现象进行修补即为失败。

## 铁律

```
未经根因排查证实，严禁编写任何修复代码
```

未完成“阶段一：根因排查”前，不得提出或实施任何修改方案。

## 紧致反馈环规则

构建反馈验证环是排查工作的核心基础。在阅读代码推演理论前，必须先建立或确定一个**紧凑的验证命令**：该命令在当前缺陷状态下必须稳定复现失败（红色），在缺陷修复后必须能立即通过（绿色）。

一个合格的反馈环必须具备四个特征：执行快速、结果确定、智能体可独立运行、且足够精准捕获该缺陷（而不仅仅是不崩溃）。当干净的复现比较困难时，应将主要精力投入到构建该验证环上；脱离确定性验证环去盲目猜测，是本技能坚决禁止的失败模式。

## 适用场景

适用于任何技术缺陷与异常：
- 单元测试与集成测试失败
- 生产环境或运行期异常
- 非预期的逻辑输出
- 性能瓶颈与资源异常
- 编译构建失败与符号未解析
- 跨模块或跨服务集成故障

**尤其在以下情况下必须强制执行**：
- 面对紧急时间压力时（紧急情况下更容易产生盲目碰运气的冲动）
- 以为“只需改动一行代码就能修好”时
- 已经尝试了多次修改但均未奏效时
- 之前的修改方案未能彻底解决问题时
- 对模块底层的流转机制尚未完全理解时

## 核心四阶段

必须严格按顺序完整执行每个阶段，严禁跨越阶段。

---

## 阶段一：根因排查（Root Cause Investigation）

在尝试任何修改前，严格执行以下步骤：

### 1. 仔细阅读完整的报错信息与调用堆栈
- 严禁粗略扫过报错日志或警告提示；
- 报错信息中通常包含精准的定位线索；
- 完整阅读异常调用栈，记录报错的具体文件路径、代码行号与错误代号；
- **具体操作**：调用 `read_file` 查阅涉及源码，调用 `search_files` 在全库搜索错误关键字。

### 2. 构建可稳定复现的紧致反馈环
- 是否能用单条命令稳定触发用户的故障现象？
- 若故障无法稳定复现，必须先补充采样日志或数据，严禁凭空盲猜。
- **反馈环构建推荐顺序**：
  1. **失败的测试用例**：覆盖故障逻辑的最短测试路径（单元测试、集成测试）；
  2. **端点调用脚本**：针对正在运行的开发实例发起特定 HTTP 或 RPC 请求；
  3. **命令行调用**：注入固定的输入用例，核验标准输出与错误输出；
  4. **复现捕获轨迹**：重放导致崩溃的特定请求报文、事件流或队列消息；
  5. **最小可运行隔离载体**：编写最小的单文件隔离脚本，导入并调用失败链路。

### 3. 排查近期的环境与代码变更
- 问题何时首次出现？最近提交了哪些改动？
- 依赖项版本、环境变量、系统配置或操作系统代码页是否发生了调整？
- 借助 `git log` 与 `git diff` 检索最近的代码变动。

### 4. 沿数据流追溯完整因果链路
- 找到触发故障的最初输入源头；
- 沿着调用链逐步向下排查，观察数据在何时、何处脱离了预期轨迹；
- 查明关键变量的真实取值，而不是理所当然地假定它应该是什么；
- 确定是哪个组件产生了无效状态，以及为什么前面的强校验没有拦截它。

### 5. 区分“观测证据”与“推断证据”

**日志、返回值、计数这类观测结果，只能证明“走到了哪条路径”，不能直接证明“配置是否生效”“功能是否启用”。** 同一功能往往有多条输出路径，只有部分路径会打印该字段。典型现场：启动日志里同一项配置有两处打印循环，带分组名的一处会附带额外信息，不带分组名的那一处完全不打印；配置里没写分组名时走的是后者，于是日志里看不到该信息，据此判断“配置没生效”是错的。

**排查顺序：先排除观测手段自身的缺陷，再怀疑被测对象。** 固定三步：
1. 用最小单元测试直接验证配置解析结果（构造一行配置、验证目标字段被填充），排除解析器；
2. 读代码确认该字段在哪几条路径上打印，排除日志误导；
3. 观察功能的外部可观测效果（对端有没有收到连接、目标文件有没有变化、报文有没有经中转），这才是功能的真实状态。

**“自己写的测试工具出错”比“被测程序出错”常见得多。** 探针结果不稳定、时好时坏、与单元测试结论矛盾时，先检查探针：握手时序是否等对端发完、并发场景下状态是否被多连接共享、判定阈值是否按实际比较符写。把探针的每次收发都打日志，一眼就能看出是哪个环节吞了包。

## 阶段二：方案分析与确认（Pattern Analysis & Design）

查明根因后，先进行方案设计，不立即改动业务源码：

1. **推导多场景兼容性**：
   - 该缺陷是在通用场景下触发，还是仅在特定网络拓扑（单栈/双栈）、特定代码页或极端输入下触发？
   - 分析修复方案是否会破坏现有依赖该接口的正常流程。
2. **拒绝表面修补**：
   - 严禁通过简单的“套 try-catch 吞掉异常”或“加特殊 if 判断跳过”来掩盖根因；
   - 必须在产生错误数据的源头纠正逻辑。
3. **禁止把超时、重试次数、等待上限当作修复对象**：
   - 当症状表现为“超时”“等待上限撞车”“重试后偶尔成功”时，被放宽的那个时间参数不是缺陷所在，而是缺陷的**暴露窗口**。把上限从 5 秒调到 12 秒只是把故障窗口后移，代价是下次故障更难复现、更难归因。
   - 正确做法是先测出被等待的操作**实际耗时多少、耗在哪个环节**：在被等待的调用链上逐段计时（对照实测），定位那段本该毫秒级却花了两三秒的环节。
   - 尤其要核查“慢”与“错”是否同源：一次失败的探测往往既拖慢耗时、又让调用方退回猜测值，此时只调超时会让错误数值被静默接受，症状消失而缺陷留存。修复前必须同时记录耗时与返回值两项，确认二者是否由同一根因引起。
   - 若确需调整上限，只能作为**与根因修复配套的次要动作**，并在交付说明中明确区分“根因修复”与“参数调整”，不得以参数调整充当修复结论。
3. **展示方案由用户决定**：
   - 梳理清晰的根因陈述、影响范围与推荐修复路径；
   - 涉及核心业务架构变动时，方案先行，取得用户明确同意后再行实施。

## 阶段三：测试驱动实施（Implementation）

1. **执行最小化变更**：
   - 单次仅修改与查明根因直接相关的代码行；
   - 严禁同时调整与当前缺陷无关的代码格式或重构无关函数。
2. **运行反馈环验证**：
   - 运行阶段一建立的验证命令，确认测试从原本的失败（红色）变为通过（绿色）。
3. **回归验证**：
   - 运行该模块全部既有测试套件，确认未引入任何退化与新缺陷。

---

## 阶段四：收尾总结与防线加固（Review & Fortification）

1. **分析为何前期未能发现**：
   - 为什么现有测试用例没有覆盖到这个边界分支？
   - 是否缺少前置的参数强校验？
2. **补充永久防护措施**：
   - 将验证测试作为永久回归测试用例固化在代码仓库中；
   - 在关键接口入口补齐防御性校验与有明确信息的错误提示；
3. **输出清晰的交付陈述**：
   - 简明说明缺陷根因是什么、修改了哪些具体文件与行号、给出的确切回归测试结果数字。
