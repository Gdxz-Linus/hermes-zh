# 测试驱动开发工程技能（Test-Driven Development）

## 概述

在编写任何业务生产代码前，先行编写测试用例；真实目睹测试运行失败后，编写最小化的业务代码使测试通过；最后在测试防护网的保护下实施重构。

**核心铁律**：
```
只有测试失败才编写修正业务代码
```
如果在编写测试之前已经写好了业务代码，必须坚决将其彻底删除并重新开始。任何试图保留未经测试验证的代码作为“参考”或“就坡下驴适配”的行为，均属于对 TDD 原则的实质违背。

## 适用场景

- 新增业务特性与接口实现；
- 修复已知缺陷（先编写复现缺陷的失败测试用例）；
- 涉及现有行为变更的代码重构。

*需经用户明确同意方可豁免的特例：纯文档修改、一次性抛弃型原型探索、自动生成的框架样板文件。*

---

## 核心“失败 - 通过 - 重构”三步循环

开发过程必须严格以小步快跑的方式遵循以下三步迭代：

### 阶段一：未通过（红 RED —— 编写最小失败用例）
针对需要实现的一个细分行为，编写一个最小化的测试用例。

#### 1. 优秀测试用例的标准：
- **单一职责**：单个测试用例仅验证一项具体的业务行为（若用例名称中含有“并且/and”，必须拆分为两个独立测试）；
- **行为命名**：函数名必须清晰描述业务行为与预期，而非底层实现细节；
- **测试真实代码**：尽量避免使用多层虚假模拟（Mock 对象），优先测试真实的业务流转与真实边界。

```python
# 优秀的规范用例：命名清晰，强校验真实行为，关注明确结果
def test_retry_operation_fails_after_maximum_attempts():
    tracker = CallCounter()
    
    with pytest.raises(TimeoutError):
        execute_with_retry(tracker.failing_task, max_retries=3)
        
    assert tracker.attempts == 3
```

#### 2. 测试失败（Verify RED —— 必须观察到预期失败）：
- **绝对禁止跳过**：在编写任何实现代码前，必须使用 `terminal` 工具运行该测试；
- 确认测试结果确实呈现红色（失败），且报错原因与预期的“功能尚未实现”完全一致，而非因测试用例自身语法错误或环境问题导致的崩溃。

---

### 阶段二：通过（绿 GREEN —— 编写最小代码使测试通过）
编写刚刚好能够使测试用例通过的代码，不多写一行。

#### 核心规范：
- 拒绝提前过度设计：不要在这个阶段顺便实现下一阶段才需要的功能；
- 运行测试套件：确认测试结果从原本的失败变为通过；
- 确认全量回归测试保持全部通过，确认新加入的代码未破坏既有模块。

---

### 阶段三：重构（REFACTOR —— 优化代码结构）
在测试全部通过的安全保护下，审视刚刚写出的代码与测试本身，消除坏味道：

#### 核心规范：
- 消除重复逻辑，提炼公共常量；
- 将过深的嵌套分支通过前置条件检查提前返回展平；
- 重新运行全部测试：确认重构过程中没有引入任何行为偏差；
- 一旦测试出现失败，立即回退或微调直至恢复全部通过。

---

## 常见失误与规避措施

1. **测试逻辑过于臃肿（一次测试太多事情）**：
   - 现象：一个测试函数包含十余项强校验，既测正常流又测异常流；
   - 纠正：坚决拆解，保持“一个测试对应一个前置条件与一项确定强校验”。
2. **测试未失败就直接通过（未真正测到目标逻辑）**：
   - 现象：新写的测试一跑就通过，其实测试的是已经存在的其他代码分支；
   - 纠正：主动注入一个错误的预期值，验证该用例是否具备确切的“捕获失败能力”。
3. **过度依赖 Mock 掩盖了真实集成缺陷**：
   - 现象：把下层所有依赖全部 Mock 掉，单元测试全部通过但实际联调时接口类型完全对不上；
   - 纠正：业务核心逻辑必须真实执行，仅对真正不可控的外部依赖（如第三方支付网关、物理硬件发送指令）保留适度 Mock。

## 自检交付核对清单

- [ ] 是否在编写业务逻辑前，亲眼目睹了该测试用例真实报错失败？
- [ ] 测试函数的失败原因是否与功能尚未实现完全吻合？
- [ ] 编写的业务代码是否严格限制在“使该测试通过”的最小范围内？
- [ ] 重构后是否重新运行了全量测试套件并获得 100% 通过验证？
