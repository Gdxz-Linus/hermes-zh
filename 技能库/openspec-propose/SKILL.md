# OpenSpec 变更提议一步生成指南（openspec-propose）

## 概述

指导将用户提出的新功能需求、架构改造或缺陷修复设想，一次性转化为完整的 OpenSpec 变更全套设计工件。包含“需求背景与目标（proposal.md）”、“技术方案与架构设计（design.md）”以及“分步实施任务清单（tasks.md）”，使变更立即具备可实施性。

## 适用场景

- “为系统新增一个特性，快速生成全套规格设计与实施计划”
- “梳理一个明确的重构诉求，建立包含验收标准的完整任务提议”
- “需要迅速将头脑中的设想整理为标准的规格说明工件”

---

## 一、 核心操作流程

### 第一步：明确变更目标与命名
- 输入必须包含具体的变更描述或英文短横线命名（如 `add-user-auth`）；
- 若用户未提供明确目标，必须主动提问：“您希望实现什么功能或修复什么问题？请简要描述您的目标。”
- 根据描述提炼出短横线命名，并在操作前向用户确认。

### 第二步：初始化变更目录结构
运行新建变更命令：
```bash
openspec new change "<变更名称>"
```
系统会在工作区规格目录下自动创建以该名称命名的独立目录。

### 第三步：一次性生成全套三大核心工件
在新建的变更目录下，完整编写以下三项工件：
1. **`proposal.md`（目标与动机）**：
   - 说明为什么要做这项变更；
   - 明确本次变更的核心目标与不包含的非目标。
2. **`design.md`（技术实现方案）**：
   - 说明系统架构如何调整、接口与数据结构如何设计；
   - 评估对上下游模块与性能的潜在影响。
3. **`tasks.md`（实施任务分解）**：
   - 将工作拆解为有序的独立任务项（使用带复选框的列表）；
   - 每个任务必须具备明确可检验的完成判据。

### 第四步：提示下一步实施
全套工件生成完毕后，向用户出示提议摘要，并提示可随时运行实施命令（`openspec-apply-change`）开始编码。

---

## 二、 检查核对清单

- [ ] 提炼的变更命名是否清晰反映了业务目标，且采用了规范的短横线命名？
- [ ] 是否完整生成了需求提议、技术方案与任务清单三套工件？
- [ ] 任务分解大小是否合理，每项任务都有明确的验证判据？
