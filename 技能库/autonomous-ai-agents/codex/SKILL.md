# OpenAI Codex CLI 智能体调度技能

## 概述

在 Hermes 内部规范化调用本地安装的 OpenAI Codex CLI 独立智能体。将复杂、多文件、长周期的编码任务委托给 Codex 在独立的上下文与专用的 Git 临时工作树中实施，形成主副协同的工程流水线协作机制。

**核心分工准则**：
- **主助手（Hermes）**：担任架构规划师与主审官，负责需求梳理、规格拟定、方案制定、计划门禁、宿主真实验证与代码审查；
- **委托智能体（Codex）**：担任实施人员，负责在隔离工作区中执行多文件代码编写与沙箱基础单元测试。

---

## 一、 委托调用的三大核心模式

在 Hermes 中执行委托时，优先使用原生委托工具（由 `codex-delegate` 插件提供），避免手动拼凑复杂的命令行文本，防止由于特殊字符、空格或换行转义失败导致命令执行异常：

### 1. 任务委托：`codex_delegate`
- **核心参数**：
  - `task`：明确的任务说明、修改边界与验收要求；
  - `cwd`：目标项目根目录绝对路径；
  - `worktree`：可选布尔值。设为 `true` 时，Codex 自动在临时 Git 工作树分支中运行，确保主代码仓库绝对不被污染；
  - `resume`：会话接续选项（设为 `"last"` 或指定会话 ID），接续上轮沙箱上下文，避免多次往返时重复全库扫描；
  - `profile`：指定模型配置文件（如 `'gemini'` 走本地反向代理端口）。
- **执行规范**：
  - 自动注入系统环境变量中的凭据；
  - 自动提取目标工程目录下的 `AGENTS.md` 规范注入任务指令开头；
  - 捕获最终返回信息并输出结构化状态（成功状态、退出码、是否包含工作树隔离等）。

### 2. 对抗式代码审查：`codex_review`
- **核心参数**：`cwd`（项目路径）、`focus`（特定审查重点，如并发安全、内存泄漏、错误处理）；
- **工作机制**：
  - 以独立只读的对抗式审查员视角，全量扫描未提交的 Git 代码差异（`git diff`）；
  - 输出结构化的正式审查结论，指出潜在的逻辑死锁、边界漏洞或未捕获异常。

### 3. 会话延续与退回修改循环
- 当宿主真实验证失败时，主助手分析原因并形成确切修改方案后，调用：
  ```python
  codex_delegate(task="分析方案与具体修改要求...", resume="last", cwd="...")
  ```
- 保持同一条沙箱会话上下文延续修改，直至通过宿主全面验证。

## 二、 Windows 环境异常排查与防错措施

在 Windows 系统下调度 Codex 时，必须严格执行以下防错规约：

### 1. 杜绝命令行换行截断（任务文件传输范式）
- **现象机理**：在 Windows 下若直接调用 `codex.cmd` 传入多行文本参数，`cmd.exe` 会在遇到第一个裸换行符时静默截断后续所有指令，导致 Codex 丢失后续文件清单与修改规范，进而发生盲目修改；
- **防错标准**：
  - 凡涉及多行、代码块或复杂长指令的任务，必须先将完整规范写入临时任务文件（如 `%LOCALAPPDATA%\hermes\cache\scratch\task_spec.txt`）；
  - 向 Codex 传入单行明确指令：“*请立即阅读文件 `<路径>` 中的完整规范与代码，严格仅修改指定的 N 个文件，严禁修改任何其他文件！*”。
- **任务文件必须先写入磁盘再派发**：把写文件与派发放在同一轮里，不要先派发再补文件。文件不存在时 Codex 会回一句「无法执行：指定文件不存在」就结束，这一轮完全白跑，还会让它去全盘搜同名文件。
- **任务书的路径必须落在沙箱允许的范围内，否则 Codex 连读都读不到。** 沙箱策略按「工作区根」判定可访问路径，任务书放在工作区外（例如 Hermes 的 `scratch` 缓存目录）时，`Get-Content`、`type`、`pwd` 这类只读命令也会在进程启动阶段被拒，报 `CreateProcess ... rejected: blocked by policy`。Codex 的回复会写成「请把会话切换为允许命令执行」，看着像权限配置坏了，实际只是路径越界。

  两种触发形态：
  1. `sandbox=workspace-write` + 任务书在 `cwd` 之外；
  2. `worktree=true` + `sandbox=workspace-write`：工作区根被换成临时工作树路径（`~/.codex/worktrees/<id>/<仓库名>`），与传入的 `cwd` 不再一致，同样被拒。

  最稳的做法是**把任务书全文直接内联进 `task` 参数**，不依赖任何外部文件；任务书确实很长时，改写进目标仓库内的临时路径（用完删除）。判定依据：报错文本里出现 `blocked by policy` 且被拒的是只读命令，就是路径越界，不要按凭据或权限问题排查。
- **Windows 上 `worktree=true` 与 `workspace-write` 组合基本不可用**，需要工作树隔离时配 `danger-full-access`，或干脆放弃工作树、靠白名单与逐行 diff 核对来控制范围。

### 2. 严格限制沙箱内的测试范围
- **现象机理**：Codex 在沙箱内若执行全量测试（如 `cargo test --all`），会频繁触发内嵌第三方库的耗时编译，极易超出命令执行时限发生超时中断；
- **防错标准**：
  - 派发任务时必须显式约束：“*仅运行当前修改模块的定向单元测试，严禁执行全量格式化或全库回归测试*”；
  - 全量回归测试必须在阶段四由主助手在宿主环境统一调度。

### 3. 严格遵循修改白名单强校验
- 接收到 Codex 返回的代码改动后，主助手必须以任务前批准的文件清单为基准，严格核对 `git diff --name-only`；
- 一旦发现 Codex 触碰了清单之外的任何文件，必须立即使用 `git restore <超出文件>` 执行还原，恢复原状，严禁将未批准的修改带入报告。
- **签名变更会波及消费者，白名单必须预先包含这些消费者并写明允许的改动形态。** 例如把某个访问器的返回类型从 `Option<&Path>` 改成 `Option<PathBuf>`，调用方必须补 `.as_deref()`，否则根本编译不过。任务文件里只写「只改 A 文件」会让 Codex 要么擅自改 B、要么交出一个编译不过的版本。正确写法是列出 `A` 与 `B`，并对 `B` 给出明确边界：「仅在两处调用点补 `.as_deref()`，不得做其它任何改动」。接收后按这个边界逐行核对 `B` 的 diff。

### 3.1 白名单只管文件，管不住文件内部的无关改动

**接收改动后必须逐行读 diff，不能只看 `--stat` 的文件清单。** Codex 会在完成任务后顺手跑格式化工具，把同一个文件里与任务无关的代码重排（拆开单行 `if/else`、调换 `use` 顺序、把多行 `assert!` 压成一行）。文件清单完全合规，`cargo check` 也照样通过，但 diff 里混进了几十行噪声，审查时真正要看的改动被淹没。

判定方法：把 diff 的 `+`/`-` 行按「是否属于任务要求」分类，凡分不进去的一律视为越界。

**但越界不等于一律回退——先判断它是不是该修复成立的必要条件。** 实测出现过这种情况：任务要求「表满时不整表清空、改为淘汰最旧的一条」，Codex 额外加了一行「每次失败刷新时间戳」。这一行不在计划里，但缺了它修复就不成立——时间戳只在首次插入时赋值的话，攻击者自己那条记录永远是最旧的，每次表满都被优先淘汰、计数反复归零，限流照样被绕过。判断方法：把那一行去掉，按最坏输入推演一遍，看原缺陷是否复发；复发就是必要条件，保留并在台账里写明它为什么必要、副作用是什么（本例副作用是窗口语义从「首次失败起算」变成「最后一次失败起算」）。只有推演后确认「去掉也不影响正确性」的改动才回退。

```bash
git diff <目标文件> | grep -E '^[-+]' | grep -vE '^(\+\+\+|---)'
```

处理办法：派发时在任务文件里写明「不要运行任何格式化工具，不要改动任务范围之外的任何行」；接收后若已发生，用 `resume` 退回让它逐项还原，并在任务文件里列出要还原的具体位置（函数名 + 原写法），比笼统说「还原无关改动」有效得多。

**同一份任务文件里复制的注释要按文件改写。** 从 A 文件复制到 B 文件的说明性注释，往往带着 A 才成立的前提（例如把「TLS 握手有超时」的注释抄进明文监听文件）。这类错误不影响编译，但会把错误的机理留在代码里误导下一个维护者；派发时明确要求「每个文件的注释按该文件的实际路径重写，不得直接复制」。

**它可能靠收窄泛型或收紧签名来绕过约束，接收后必须确认所有调用方仍然成立。** 实测现场：任务要求「用已建立的 TCP 对端地址兜底」，但泛型流类型没有取对端地址的方法；Codex 的解法是把 `impl<S> Foo<S>` 的关联函数收窄成 `impl Foo<TcpStream>`。编译通过、测试通过，但这是**公开 API 的收窄**——任何用非 `TcpStream` 实例化该类型的调用方会直接编不过。接收时用 `grep -rn '<类型名>' --include=*.rs src/` 列出全部使用点，逐个确认实际类型；确认只有生产路径那一种类型时才接受，否则退回让它保留泛型并加显式约束。

### 4. 异常与超时首句主动披露
- 若委托子进程发生超时、执行中断或生成未授权改动，主助手必须在下一轮回复的首个句子向用户完整披露异常情况与处理方案，严禁因单测通过而心存侥幸瞒报。

### 5. 工具调用超时：先搞清是哪一层超时，再查现场

**两层超时，`timeout` 参数只控制内层。** 这是最容易误判的一处：

| 层 | 位置 | 由什么决定 | 后果 |
| :--- | :--- | :--- | :--- |
| 内层 | 插件里的 `subprocess.run(timeout=...)` | 调用时传的 `timeout` 参数 | 到点杀掉 codex 子进程，返回「执行超时（超过 N 秒）」 |
| 外层 | Hermes 通用工具截止时间 | `timeouts.tools.sequential_call`，默认 **420 秒** | 到点工具调用返回超时，**但子进程不受影响、继续跑完** |

外层截止时间由 `tool_executor` 的 `_SEQUENTIAL_DEADLINE_EXEMPT_TOOLS` 名单决定是否豁免。插件注册接口 `ctx.register_tool` 不暴露 `execution_timeout` 参数，因此**插件工具无法自行声明更长的等待时间**，`_extend_tool_timeout` 拿不到值就回落到默认 420 秒。

⇒ **只把 `timeout` 参数调大没有用**：外层 420 秒先到，工具照样返回超时。要真正放宽，只有两条路：把工具名加进 `_SEQUENTIAL_DEADLINE_EXEMPT_TOOLS`，或给插件注册接口补上 `execution_timeout` 透传。两者都属 Hermes 产品源码改动，须提交产品仓库主分支才不被升级覆盖。

**本机已按第一条路改定**：`codex_delegate` 与 `codex_review` 已进豁免名单，插件默认 `timeout` 同步从 600 秒提到 1800 秒。判定依据是「工具自己管存活」——两者都用 `subprocess.run(timeout=...)` 管着 codex 子进程，外层再套一层只会互相打架：外层先放弃等待，子进程仍在后台改文件，调用方误判失败后重派，两个进程同时写同一批文件。新增同类插件工具时照此办理，不要逐个调参数。

**豁免之后，插件自己的 `timeout` 成为唯一上限**，默认值必须按真实任务时长定，不能沿用「比 420 大一点」的思路。跨文件重构常要 5 至 15 分钟，大的能跑一小时。

**改完必须重启网关与桌面进程才生效。** 运行中的进程早已 import 了旧模块，磁盘上的名单更新对当前会话无效。验证办法是在新进程里读一次 `_SEQUENTIAL_DEADLINE_EXEMPT_TOOLS` 常量，确认名单内容——读源码文件只能证明改动写入了磁盘，证明不了它在生效。

**证明豁免真的生效，必须做反向验证。** 只检查「名单里有这个名字」，测的是常量而不是机制。正确做法分三步：① 把截止时间设成 1 秒、让工具跑 2.5 秒，确认拿到真实结果而非超时；② 同一截止时间下跑一个普通工具，确认它仍然超时——证明这是定向放宽而不是把机制整体关掉；③ 临时清空豁免名单重跑场景 ①，确认这次被判超时。三步都成立，才说明测试检验的是豁免机制本身。

**判定是哪一层超时：看耗时是不是整数秒。** 外层截止时间到点即切，返回值精确落在 420.1s、300.4s 这类整数秒上；内层子进程超时同理落在传入值上。真实任务耗时几乎不可能凑巧是整数。看到整数秒就是某一层的时间上限，不是任务本身太慢。

**用会话库反查历史调用耗时，不要凭印象判断「以前能跑多久」。** 印象会错，数据不会：

```python
# 结果消息按 tool_call_id 反查调用消息，两者 timestamp 之差即真实耗时
cur.execute("SELECT tool_call_id, timestamp, content FROM messages WHERE tool_name='codex_delegate' ORDER BY timestamp")
```

配对后能直接分出三类：成功、插件内层超时（消息里有「执行超时（超过 N 秒）」）、Hermes 外层超时（消息里有 `timed out after 420.0s`）。**若历史里早就有外层超时记录，说明这不是新问题，只是以前没深究**——不要把它当成「这次才出现」来解释。

**用户说「以前跑过半小时」时，先确认那次是不是走插件跑的。** `~/.codex/sessions/` 里时长很长的会话可能是直接跑 `codex exec` 产生的，与 Hermes 会话库对不上时间戳即可证明。混淆两者会把「CLI 能跑半小时」误当成「插件会等半小时」。

**超时返回后必须先查现场，不能立即重派。** 重派会让两个进程同时改同一批文件。

1. **读 Codex 自己的会话日志判定是否真的完成**（最可靠，优于看进程）：
   ```bash
   ls -lt ~/.codex/sessions/$(date +%Y/%m/%d)/ | head -5
   ```
   取最新 `rollout-*.jsonl`，逐行解析 JSON，检查末尾是否存在 `payload.type == "task_complete"`。有则任务已跑完、只是总结没来得及回传；无则被中途杀掉。同一份日志还能算出实际耗时（首行与末行 `timestamp` 之差），用于判断该任务需要多长等待时间。
2. `git diff --stat <目标文件>` 看改动是否已写入文件。
3. `tasklist | grep -i codex` 看进程是否仍在运行；仍在时等待并周期性复查（间隔 2 至 3 分钟）。
4. 日志有 `task_complete` 且改动完整时，直接进入验证，不必重跑。

**判定改动是否完整不能只看文件有没有变。** 逐项核对任务清单里的每个改动点是否都已实现——实测出现过「测试已加、实现未改」的半成品状态，也出现过「三处要求只改了两处」。

**测试也要逐个点名核对，不能只看「全部通过」这个结论。** 任务要求写 N 个测试时，接收后按函数名逐个检索确认都存在。Codex 会漏写其中一两个，而全量测试照样全部通过——漏掉的那个测试根本没被创建，自然不会失败。

**它报告的测试数字不可采信，必须自己复跑一遍核对。** 实测出现过「共 677 项测试，673 passed，0 failed，4 ignored」这种自相矛盾的表述：673 + 4 = 677 看似自洽，但复跑发现真实数字是 675 passed / 0 failed / 4 ignored，总数与通过数都对不上。原因通常是它把中途某次运行的数字与最终一次混着写。做法：接收后自己跑一次 `cargo test --offline`（或对应命令），以自己跑出的数字为准写进台账；发现它报的数字与实测不符时，不要当成小事略过——数字不符意味着它对自己做过什么并不清楚，同一份报告里的其它结论也要重新核对。

**派发粒度**：单次任务包含的文件越多、要求越复杂，超时概率越高。多个文件的修改拆成多次派发，每次只改一个功能点，既降低超时概率，也让失败时能只回滚当次。

## 三、 自定义模型通道配置与元数据目录

Codex 可接入任意兼容 OpenAI 接口的服务。配置分三层：顶层默认通道、通道定义、模型元数据。三层缺一则出现告警或运行异常。

### 1. 三层配置的确切写法

```toml
# 第一层：默认使用哪个通道与模型
model = "deepseek-v4.1-flash"
model_provider = "jk-deepseek"
model_context_window = 1048576
model_catalog_json = "C:/Users/<用户名>/.codex/model-catalogs/jk-deepseek.json"
model_reasoning_effort = "high"

# 第二层：通道定义
[model_providers.jk-deepseek]
name = "JK DeepSeek (H200)"
base_url = "http://10.118.70.129:30000/v1"
wire_api = "responses"
env_key = "JK_DEEPSEEK_API_KEY"
```

- `wire_api` **当前版本只接受 `responses`**：写 `chat_completions` 或 `chat` 会直接报 ``wire_api = "chat" is no longer supported`` 并拒绝加载配置。对话接口已被上游彻底移除，不要再按旧文档写双选一；实测 `chat`、`chat_completions`、`completions`、`response` 四个取值全部拒绝加载，只有 `responses` 通过。
- 顶层 `model_provider` 的值必须与 `[model_providers.<名称>]` 的方括号内名称逐字一致。

密钥有两种供给方式，二者的取舍决定 codex 是否与调用方解耦：

| 方式 | 写法 | 依赖 | 适用 |
| :--- | :--- | :--- | :--- |
| 环境变量 | `env_key = "XXX_API_KEY"` | 启动时必须存在该变量 | 与其他工具共用同一套凭据 |
| 文件自带 | `experimental_bearer_token = "<密钥>"` | 无，完全不读环境 | **codex 需独立于其他工具时用这个** |

**要求「密钥与调用方解耦、自己单独保存」时，用 `experimental_bearer_token`，并把 `env_key` 整行删掉。** 两者不能并存：同时存在时 `env_key` 优先，`experimental_bearer_token` 被静默忽略；把 `env_key` 写成空字符串也不行，会变成 ``Missing environment variable: `` `` 直接失败——空值不等于省略。

解耦是否真的成立只能这样验证：把调用方相关的密钥环境变量全部清空后运行，能正常返回才算通过。

```bash
env -u JK_DEEPSEEK_API_KEY -u OTHER_API_KEY codex exec --skip-git-repo-check -s read-only "只回复 OK"
```

未清空变量就验证，测的是环境变量那条路，证明不了解耦。

### 2. 陷阱：写入不存在的键会被静默忽略

**在配置里加任何自认为合理的键之前，必须先用 `codex exec --strict-config` 校验一次，确认该键被当前版本识别。** 根因是 Codex 对未知配置项只打印一行 ignored 告警后继续运行，配置看似生效实则完全没起作用。

典型例证：`model_max_output_tokens` 在多处第三方文档里出现，但当前版本并不识别它，写入后每次启动都告警且输出上限不受控。输出长度改由模型元数据目录的 `truncation_policy` 管理。

校验命令：

```bash
codex exec --strict-config --skip-git-repo-check "test"
```

该命令遇到未知字段直接报错退出并指出文件与行号，比逐条读告警快得多。

### 3. 模型元数据缺失告警的消除

接入自定义模型后，Codex 每次启动都打印 `Model metadata for <模型名> not found. Defaulting to fallback metadata`。根因是 Codex 内置的模型清单里没有这个模型，只能退回保守的默认值，上下文窗口与推理挡位都不准确。

消除办法是建一个模型目录 JSON，并用 `model_catalog_json` 指向它。该文件的字段结构、各字段含义与完整可用模板见 `references/custom-model-provider.md`。

模型目录 JSON 里三个容易写错的字段：

- `apply_patch_tool_type`：**正解是整段删掉这个字段**。写 `function` 会在解析阶段直接失败拒绝启动（只接受 `freeform`）；写 `freeform` 则能让客户端启动，但客户端会据此向请求体发送一个 `type: custom` 且 `format.type: grammar` 的补丁工具，而 vLLM 的 Responses 接口在请求校验阶段明确拒绝该形态（`Custom tools with a grammar format are not supported; only free-form text custom tools are accepted`），导致每次调用在发出第一个请求时就失败。删掉该字段后客户端改用普通命令行写文件，任务正常完成。
- `shell_type` 取 `default` 或 `shell_command`，取错会导致工具调用报 `incompatible payload`；
- `supported_reasoning_levels` 里列出的挡位必须上游真的支持。服务端只认 `low` / `high` / `xhigh` / `max` 四个具名档位时，表里写了 `medium` 会让客户端把该值原样发出去并被拒；档位表要与服务端实际接受的值逐个核对一致，并补上服务端支持但缺省的档位（漏写 `max` 会让用户选不到最强档）。

上述三个字段的验证都不能靠读取配置文本，必须发真实请求看服务端是否接受。`--strict-config` 只校验字段名与取值枚举，不校验上游是否接受最终发出的请求体。

### 4. 陷阱：Codex 运行时会自动改写配置文件

**每次运行 Codex 后，必须重新比对工作目录备份与 `~/.codex/config.toml`，不能假定两者仍然一致。** 根因是 Codex 会在运行中回写配置文件：统一行尾为 LF，并自动追加 `[projects.'<工作目录>'] trust_level = "trusted"` 记录。

后果有两个：一是备份与系统配置的哈希值对不上，误判为配置被篡改；二是临时测试目录被写进信任清单，长期残留。

处理办法：同步前先删掉指向已删除目录的 `[projects.*]` 条目，再以系统版为准回写工作目录。

### 5. 验证顺序：先配置后能力

新增通道后按以下顺序验证，任一步失败就停在该步排查，不要跳步：

1. `--strict-config` 校验：确认无未知字段、模型目录 JSON 能被解析；
2. 简单问答：确认通道连通、密钥有效、模型名被上游接受；
3. 实际编码任务：确认工具调用链路正常，模型能读写文件并运行命令。

第 2 步通过而第 3 步失败时，问题在工具调用协议而非通道本身。此时**必须换一个已知可用的通道跑同一个任务做对照**，确认故障属于该模型通道还是 Codex 沙箱层。不换通道对照就下结论，会把沙箱问题误判成模型不兼容。

### 6. Windows 沙箱模式的选择

在 Windows 上以 `-s workspace-write` 运行 Codex 时，模型发起的命令可能被系统策略整体拒绝，报错形如 `rejected: blocked by policy`。这是 Codex 在 Windows 上的沙箱策略表现，与模型通道无关。

验证 Codex 行为时使用 `-s danger-full-access`，并在隔离的临时目录中进行。`codex_delegate` 插件在 Windows 上默认即采用该模式，通过插件调用不受影响。

#### 6.1 安装位置必须与升级无关

**Codex 只能装在用户级独立目录，严禁装进任何会整目录替换的位置。** 两类位置最容易被顺手选错，后果都是升级后客户端直接无法启动：

| 禁止位置 | 被替换的时机 | 典型后果 |
| :--- | :--- | :--- |
| 其他工具的运行时目录（如 `~/.dsh/runtime`） | 那个工具升级时整目录替换 | 包装层还在、平台二进制包丢失，报 `Missing optional dependency @openai/codex-win32-x64` |
| Hermes 自身的 tools 或 bin 目录 | `hermes update` 升级时重装 | 同上，且不易发现，因为文件已经不在了 |

正式采用的位置是 `~/.local/codex`，用本地 `package.json` 加 `npm install` 安装（不依赖全局前缀）。

安装前先测 registry 连通性，两个源都测，取先返回的那个。网络不通时 `npm install` 会卡在重试上很久才报错，先测能立刻判断是网络还是包的问题：

```bash
curl -s -o /dev/null -w "官方源: %{http_code} %{time_total}s\n" --max-time 20 https://registry.npmjs.org/@openai%2Fcodex
curl -s -o /dev/null -w "国内镜像: %{http_code} %{time_total}s\n" --max-time 20 https://registry.npmmirror.com/@openai%2Fcodex
```

```bash
mkdir -p ~/.local/codex && cd ~/.local/codex
printf '{\n  "name": "codex-standalone",\n  "private": true\n}\n' > package.json
npm install --no-audit --no-fund @openai/codex@latest
```

安装后必须确认平台二进制真实存在，不能只看 `npm` 退出码为 0。包装包与平台包是两个独立包，只装上包装包时命令会报缺依赖：

```bash
find ~/.local/codex/node_modules -name 'codex.exe'          # 必须能列出路径
~/.local/codex/node_modules/@openai/codex-win32-x64/vendor/x86_64-pc-windows-msvc/bin/codex.exe --version
```

`npm config get prefix` 会指出当前默认全局目录。它在其他工具的目录下时，直接 `npm install -g` 就装错地方了；改用上面的本地 `package.json` 方式可以绕开这个全局前缀配置。

#### 6.2 插件里的二进制路径必须按优先级探测

`codex-delegate` 插件曾把二进制路径写死成一个绝对路径，且路径里多写了一层 `@openai/` 目录，指向一个从不存在的位置；它同时也把旧运行时目录压进了代码，迁移后必须先试旧路径才回落到 PATH。两条合起来使得即使重装好客户端，插件仍然起不来。

正确写法是按优先级探测，且**独立位置排在旧位置前面**：

```python
vendor_tail = "node_modules/@openai/codex-win32-x64/vendor/x86_64-pc-windows-msvc/bin/codex.exe"
for candidate in (Path.home() / ".local/codex" / vendor_tail,
                  Path.home() / ".dsh/runtime" / vendor_tail):   # 旧位置仅作兼容兜底
    if candidate.exists():
        codex_bin = str(candidate.resolve())
        break
if not codex_bin:
    codex_bin = shutil.which("codex") or "codex"
```

顺序不可颠倒：旧位置若排前面且残留半套文件，会优先命中一个跑不起来的入口。修改后**必须重启网关**，运行中的进程已缓存旧模块，磁盘上的改动对当前会话无效。

验证插件真的解析到了新位置，不能只看代码改动：驱动一次真实的 `codex_delegate` 调用，看返回里是否还有 `Missing optional dependency` 或旧路径的堆栈。

#### 6.3 上游 Responses 接口的两类残缺，必须先分离再归因

**同一批部署的不同实例，Responses 接口的完整度可能不同；codex 在客户端无法绕过，因此上线前必须先测出每个实例缺什么。** 两条互相独立的能力不能放在一起测：

| 能力 | 缺失时的报错原文 | 含义 |
| :--- | :--- | :--- |
| 工具形态 | `Custom tools with a grammar format are not supported; only free-form text custom tools are accepted` | 服务端拒绝 `format.type = grammar` 的自定义工具 |
| 输入形态 | `supports text and image content only; got 'input_text'` | 服务端只收纯字符串，拒绝标准 content 数组 |
| 输入形态（另一变体） | 报大量 `validation errors` 且均指 `body.input` 应为字符串 | 同上，但驱动层更早拦下 |

区分方法：固定其中一项、只改另一项，四次组合就能定位到底缺哪一项。两批请求必须分开跑，合在一起时会互相掩盖：

```text
工具用无 format 自定义工具、输入用标准数组  -> 能过 = 只缺工具形态
工具用 grammar      、输入用纯字符串    -> 能过 = 只缺输入形态
```

**命令行的 `ERROR:` 行里那条具体报文是唯一可靠的归因依据。** 两类残缺都会让 codex 在发出第一个请求时就失败，现象完全一样（退快、无工具调用、stderr 两行重复的 `ERROR:`），只能靠报文正文区分，不能靠「哪个端口正常过」推断。

输入形态残缺的服务端并未失效——把 content 数组压成纯字符串后就能正常返回。需要长期用它时，在中间加一层格式转换（本地反向代理改写请求体再转发），不要试图用 codex 配置绕过，客户端已无此开关。

**失败排查时倒查会话日志比反复试配置快。** `~/.codex/sessions/*/*/*/rollout-*.jsonl` 里既记了每次请求的 `input` 项类型，也记了服务端回复；一次失败能看到客户端发了什么、服务端回了什么，不必再起抓包代理。

### 7. 陷阱：声明图片输入前必须先确认上游如何推算输出上限

**在模型目录里把 `input_modalities` 改成 `["text", "image"]` 之前，先用非流式请求实测一次带图请求，确认上游在未收到输出上限时如何处理。**

根因：Codex 当前版本不向请求体发送输出上限字段。部分推理服务（SGLang 一类）在收到未指定输出上限的请求时，把「上下文窗口减去输入占用」的全部剩余空间当作输出上限。纯文本请求输入占用小，剩余空间加进去仍在窗口内，能正常返回；带图片的请求输入占用更大，加上被放大的输出上限后总数超出窗口，服务端直接拒绝。

现象具有误导性：流式响应在 `response.created` 与 `response.in_progress` 之后紧跟 `response.failed`，而该事件的 `error` 字段为 `null`、`incomplete_details` 也为 `null`，从流式响应里读不出任何原因。**必须改用非流式请求复现，才能拿到写明「请求了多少 token、上限是多少」的完整报错。**

诊断顺序：

1. 非流式请求复现，读出完整报错文本；
2. 同一请求分别带与不带输出上限各发一次，确认差异只在输出上限；
3. 抓包确认客户端实际发出的字段清单，不要凭配置项名字推断它发了什么。

抓包方法：起一个本地反向代理转发到上游并逐条记录请求体，然后用 `-c model_providers.<名称>.base_url="http://127.0.0.1:<端口>/v1"` 临时把通道指向它。抓到的请求体顶层字段清单一目了然，比反复试配置快得多。

配置项陷阱：`output_token_limit`、`truncation_policy`、`model_max_output_tokens` 这三个键都**不控制**请求体里的输出上限，写入后抓包可见请求体里依然没有该字段。要让客户端发送它，只能改上游服务端的默认值，客户端侧改配置无效。

判定边界：这个问题只在「客户端不发输出上限」与「服务端按剩余上下文推算输出上限」两个条件同时成立时触发，且只对多模态请求显形。纯文本请求不会暴露它，因此不能靠纯文本通道测试通过就认定图片通道可用。

#### 7.1 图片必须用 `-i` 显式附加，且必须核验它真的发出去了

**在 `codex exec` 里只写在提示词里「请查看当前目录的某图」不会附带图片。** 客户端不会主动读取工作区图片，模型只会调 shell 命令去读像素或元数据，然后给出一个看似正确的颜色或尺寸。回复正确不代表它真的看见了图。

正确做法分两步：

1. **显式附加图片，并且用 `--` 终止选项解析后再跟提示词。** 参数顺序写错（如 `-i 图.png "提示词"`）时客户端会把提示词当成图片位置或反过来，表现为反复输出 `Reading prompt from stdin...` 且 `No prompt provided via stdin`。稳定写法：

   ```bash
   codex exec --skip-git-repo-check -s danger-full-access -i pic.png -- "这张图是什么颜色？只回答颜色名称"
   ```

2. **核验图片真的进入了请求体，而不是靠回答结果倒推。** 读本次会话日志统计两个关键字：

   ```bash
   LATEST=$(ls -t ~/.codex/sessions/*/*/*/rollout-*.jsonl | head -1)
   grep -o 'input_image' "$LATEST" | wc -l   # 大于 0 才说明图片真的发出去了
   grep -o '"type":"function_call"' "$LATEST" | wc -l  # 同时为 0 才排除「靠命令行读文件蒙对」
   ```

   判定标准：`input_image` 命中数大于 0 **且**工具调用数为 0，才能确认是模型看图作答。两段都满足才算验证通过。把提示词写成「不要用任何工具或命令去读文件」并不能阻止它读，只能靠日志判定。

3. **插件链路传不了图片。** `codex_delegate` 工具没有图片参数，`handle_codex_delegate` 构造命令行时不带 `-i`。需要图片能力时用命令行直接调用；要长期支持则得给插件补参数，属插件代码改动。

## 八、 MCP 服务器集成：配置正确不等于模型能用

### 1. 三步分离开验证，缺一步都会误判

**`codex mcp list` 显示 `enabled` 只证明配置被读到，不证明工具进入了模型的工具清单。** 这两件事必须分开验证，前三步全部通过而最后一步失败，就是「装了但模型用不到」。

| 步骤 | 做法 | 通过标准 |
| :--- | :--- | :--- |
| ① 服务器自身健康 | 手动发 JSON-RPC：`initialize` → `notifications/initialized` → `tools/list` → `tools/call` | 正确返回 `serverInfo` 与工具名数组 |
| ② codex 识别 | `codex mcp get <名字>`、`codex doctor` 的 mcp 段 | 显示正确的 `transport` / `command` / `args`，`disabled servers 0` |
| ③ 模型真拿到工具 | 单独跑一次 `codex exec`，直接问「你有哪些 mcp 工具，只列出名字」 | 工具名出现在清单里 |

第 ① 步用 `scripts/mcp_handshake_probe.py` 做，改开头两个常量指向目标脚本即可，不要每次手写 JSON-RPC。

第 ③ 步也可以用会话日志判定，与核验图片是否真的发出同一套方法：

```bash
LATEST=$(ls -t ~/.codex/sessions/*/*/*/rollout-*.jsonl | head -1)
grep -c 'viking_search' "$LATEST"   # 0 就说明工具没进模型工具集
```

### 2. 模型拿不到 MCP 工具时不会报配置错误，而是自行绕路

这是最容易误判成功的一处。**它会写一个脚本直接向 MCP 服务器发 JSON-RPC 拿数据，然后把结果正常交付，还会主动说明「工具列表里没有这个工具，所以我用脚本调了协议」。** 结果正确、数据真实，但集成是坏的。

判定依据在它自己的自述里：出现「当前会话中不存在 X 工具」「我通过手动发起了 initialize / tools/list / tools/call」这类句子，就是工具没暴露。**不要因为拿到了正确数据就判定集成通过**——沿着这条路，沙箱一收紧就彻底失效，且每次多消耗上万 token。

沙箱级别直接决定这条绕路能否走通，也决定失败时的现象：

| 沙箱 | 现象 |
| :--- | :--- |
| `read-only` | 连脚本都写不了，直接回复「当前没有配置任何 MCP 服务器」 |
| `danger-full-access` | 能写脚本绕路，拿到正确数据，但工具清单里依然没有该工具 |

两种现象都指向同一个根因，不要因为 `danger-full-access` 下「能用」就当它正常。

### 3. 插件实体与客户端程序是两套数据

**客户端二进制损坏或重装，不影响插件与配置。** 排查「插件是否丢失」时不要从客户端状态推断：

| 数据 | 位置 | 权威判据 |
| :--- | :--- | :--- |
| 客户端程序 | 安装目录（`~/.local/codex`） | `codex.exe --version` |
| 插件实体 | `~/.codex/plugins/cache/` | `codex plugin list` 的 STATUS 列 |
| 通道与 MCP 配置 | `~/.codex/config.toml` | 配置文本 |

`codex plugin list` 会同时列出市场里未安装的条目，只看名字会以为都装了；**以 STATUS 列 `installed, enabled` 为准**。插件版本号形如 `b767f8fa`，市场刷新后这个指纹会整批变化，不代表插件被替换或损坏。
