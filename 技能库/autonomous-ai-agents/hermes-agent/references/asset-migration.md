# 汉化资产的三态基线校验与迁移

本文件说明把汉化后的配置、插件、技能、工具迁回 Hermes 系统时，如何避免把旧汉化稿盖到已升级的新文件上。直接覆盖的后果是官方修复被静默回退，且不产生任何报错。

## 一、 三态判定

每项资产都涉及三个文件：

| 文件 | 含义 |
| :--- | :--- |
| 系统源文件 | Hermes 安装目录里的当前文件，可能已被官方升级 |
| 英文基线 | 当初汉化所依据的英文原版，单独备份在工作目录 |
| 中文汉化稿 | 工作目录里维护的中文版本 |

对每个文件算 SHA-256 指纹，按下列顺序判定：

| 条件 | 判定 | 动作 |
| :--- | :--- | :--- |
| 系统里没有该文件 | 新增 | 直接写入 |
| 系统 == 中文稿 | 已汉化在位 | 跳过 |
| 自研资产（白名单） | 无英文原版 | 直接写入 |
| 系统 == 英文基线 | 官方未升级 | 写入中文稿 |
| 其他 | 官方已升级或基线缺失 | 拒绝写入，转重新汉化 |

判定顺序不能调。先查「系统 == 中文稿」再查基线，否则已汉化在位的文件会被当成待导入反复处理。

## 二、 基线缺失时必须拒绝

拿不到英文基线时，无法判断系统文件是否仍是当初汉化所依据的那一版。此时默认放行等于把旧汉化盖到可能已升级的新文件上，官方修复被静默回退。

自研资产（自己写的插件、防护脚本）确实没有英文原版，但必须靠显式白名单区分，不能靠「找不到基线」自动归入。白名单与「基线缺失」是两件事。

## 三、 基线的两个来源

按优先级依次尝试：

1. 工作目录下的英文原版备份；
2. 系统目录若是 Git 仓库，取 `HEAD` 版本（官方发行版，天然可信）。

第二条能大幅减少「基线缺失」的误判，尤其是从官方仓库安装的插件。取法：

```bash
git -C <仓库根> show HEAD:<相对路径>
```

## 四、 官方升级后的处理流程

判定为「官方已升级」时，脚本自动完成前三步，第四步交给助手：

1. 旧英文基线归档到 `_归档基线/<时间戳>/`，保留追溯依据；
2. 升级后的系统文件覆盖英文基线，形成新的比对基准；
3. 失效的中文稿移入 `_待重新汉化/`，仅作参考，不再参与导入；
4. 助手按新基准重新汉化，生成新中文稿覆盖原位置后重跑导入。

第 3 步必须真的把文件移走。留在原位会导致下次导入时它又被当作有效中文稿参与判定。

## 五、 系统中文稿比工作目录新

还有一种情形：系统文件是中文，但与工作目录的中文稿不同。这说明两边各自改过，内容已经分叉。

不能反向覆盖。判定时用中文密度（中文字符占非空白字符的比例，阈值取 0.05）区分「英文新版」与「中文新版」：前者是官方升级，走重新汉化；后者是两边分叉，按资产类型分别处理。

用「是否含中文字符」判断会误判——英文原版里常有中文示例与注释，密度极低但确实存在。

### 分叉后的处理按资产类型分开

配置、插件、工具这三类以系统版为准：它们的结构由代码约定，版本号与函数签名决定哪边是正本，不需要人工判断内容优劣。

**技能类不同，必须逐文件合并，不能按新旧选一边。** 技能是纯文本知识载体，两边改的往往是不同章节：一边可能补了新规则，另一边可能修了笔误或清了行话。直接选一边会丢掉另一边的内容。

合并步骤：

1. 先把系统版备份到工作目录的 `中文技能库/_系统新版备份/<时间戳>/`，保留回退依据；
2. 逐文件比对，先看结构完好度：章节编号是否重复、代码块围栏是否成对、版本号是否落后。结构已损坏的一边不能作为合并基底，即使它行数更多；
3. 以结构完好的一边为基底，把另一边独有的实质内容并入。判据是「这一行是不是另一边真的没有」，不是「行数谁多」——行数多可能只是重复段落或未闭合的代码块；
4. 合并后清行话。两边都可能带着未清洗的旧译法，合并会把它们聚到一起；
5. 校验：YAML 头能解析、代码块围栏成对、关键章节与特征串逐项在位；
6. 写回系统，再核字节一致。

合并完成后删掉 `_系统新版备份/` 目录。留着会让下次导入把已合并的旧稿当成有效中文稿参与判定。

## 六、 语言包不走三态校验

中文语言包（`zh.yaml` 一类）本身就是中文正本，它的英文对照是 `en.yaml`，两者内容天然不同，套三态校验会全部判为「已升级」。语言包直接覆盖，只比较系统文件与中文版是否一致以决定是否跳过。

## 七、 自研配置文件覆盖前先备份系统版

`config.yaml`、`.env`、`SOUL.md` 这类用户自维护文件不做三态校验，工作目录版本即正本。但系统版本可能比工作目录新（例如在系统里改过模型配置），覆盖前先把系统版本备份到 `_系统旧版备份/<时间戳>/`，避免改动丢失。

## 八、 沙箱验证

迁移脚本的判定逻辑必须在隔离的临时目录中验证，不碰真实安装目录。需要覆盖的场景：

1. 系统 == 基线 → 导入；
2. 系统 == 中文稿 → 跳过；
3. 系统已升级 → 拒绝 + 基线归档 + 基线刷新 + 中文稿移入待重新汉化；
4. 基线缺失 → 拒绝；
5. 自研白名单 → 导入；
6. 系统无此文件 → 新增；
7. 系统中文稿更新 → 跳过并提示回写；
8. 目录树混合三态 → 各文件独立判定，互不影响。

验证时把路径探测函数替换为指向沙箱的桩函数，再调用脚本的 `main()`，比只测单个函数更能发现路径拼接错误。

## 九、 目录布局

```text
工作目录/
  核心配置与防线/          自有配置、规范、插件全集、插件补丁
    说明.md                本目录各文件的用途与升级注意事项
    安装部署.py            只负责本目录内容的部署脚本
    config.yaml / SOUL.md / .env
    codex-config.toml / codex-model-catalog.json
    plugins/
      自定义插件/          9 个，无 .git，源码即最终版
      外部安装插件/        5 个，有 .git，可独立升级
      插件补丁/            对该插件源码的本机改动，.diff 形式
  汉化覆盖层/              工具与提示词映射表、语言包差异键、汉化技能
    汉化库.py / 汉化维护.py / 语言包差异.py
    核心/ 工具/ 插件/ 语言包/ 技能库/
  部署.py                  总部署入口（包含以上两部分）
  说明.md                  总说明
```

备份目录与资产目录必须平级分开。混在一起会让迁移脚本难以判断哪些是资产、哪些是历史备份。

### 插件目录按来源分三类，不要平铺

| 子目录 | 判据 | 汉化落点 | 升级方式 |
| :--- | :--- | :--- | :--- |
| `自定义插件/` | 无 `.git` | 直接写在源码里 | 不受升级影响 |
| `外部安装插件/` | 有 `.git` | 在映射表里，源码保持官方原版 | `git pull` 后必须重跑映射差异对比 |
| `插件补丁/` | — | 以 `.diff` 保存对插件源码的本机改动 | 升级后若官方未修则重打 |

平铺混放会让「这个插件能不能 `git pull` 升级」「改动在哪一层」每次都要现查。分开后目录结构本身就是答案。

**安装脚本不自动应用插件补丁**，只打印 `cd <插件目录> && git apply <补丁路径>` 供人判断。原因是补丁改的是外部插件源码，官方新版结构可能已变，自动应用失败时难以回退。

### 部署脚本按范围分层

| 脚本 | 范围 |
| :--- | :--- |
| 根目录 `部署.py` | 总入口：配置 + 插件 + 汉化 + 技能 |
| `核心配置与防线/安装部署.py` | 只管本目录：配置 + 插件，不碰汉化 |
| `汉化覆盖层/汉化维护.py` | 只对比差异，不部署 |

同一批文件有两个命令都能部署会造成困惑。分层后各目录自带入口，根目录只留总入口。

## 十、 移植到新电脑时的资产清单

移植的目标是「新电脑上装好 Hermes 后，一条命令恢复全部定制」，不是「把旧机器的一切原样搬过去」。按下面的分类取舍，多带只会增加判断成本。

### 必带：自定义插件

判据是插件目录下**没有 `.git`**。这类插件不在任何外部仓库里，源码本身就是汉化正本，新电脑上没有别的来源。

### 仓库插件：重新备份一份带 `.git` 的干净副本

判据是插件目录下**有 `.git`**。这类插件有自己的官方仓库，汉化不在源码里而在映射表里，因此源码本身不必保留汉化。

但**备份目录里那份不能直接用**，三个理由叠加：

1. **常是脏状态**——游离 HEAD 加未提交改动，是当初做汉化时留下的中间态，不是可用的原版；
2. **版本可能比运行目录还旧**。实测某插件备份停在 0.4.4，运行目录已是更新的提交。带过去等于把插件降级；
3. **缺 `.git` 就只能重装**，新电脑上无法 `git pull` 升级，也看不出当前是哪个版本。

正确做法：把旧备份整个删掉，从运行目录 **`cp -a` 一份带 `.git` 的干净副本**（运行目录此时已解耦回官方原版，状态干净）。带 Git 的差别是：

| 带 Git | 不带 Git |
| :--- | :--- |
| 新电脑可 `git pull` 升级 | 只能 `hermes plugins install` 重装 |
| 保留提交历史 | 只有源码快照 |
| 能查当前版本 | 看不出 |

备份后逐个 `git -C <目录> status -sb` 与 `git log -1` 核对：状态应为 `## main...origin/main`（无本地提交），版本应为运行目录当前版本。

**例外**：仓库插件若含本地功能补丁（不是汉化），那部分单独备份在补丁目录，装完官方版后按补丁重打。判据是「新增行含中文的比例」——零中文即纯功能改动。

### 不带：原生自带插件

Hermes 仓库 `plugins/` 下已有的名字，新电脑装完自带。备份目录里那份是多余的。

### 不带：完整语言包副本

备份目录里若存着完整语言包（几百 KB 一份），那是早期方案的遗留，会盖住官方更新。移植只需带**差异键**（几 KB 一份），由抽取脚本生成。

### 不带：英文原版备份

系统本身就是英文原版，`hermes update` 或仓库随时可取回。另存一份只增加迁移体积。

### 移植后的落地顺序

```text
1. 装好 Hermes
2. 复制工作目录（汉化覆盖层、核心配置与防线）
3. 改公共库里的 HERMES_HOME 绝对路径（用户名不同时）
4. 跑部署脚本（先 --check 看计划，再实际执行）
5. 启用汉化覆盖层插件
6. 重启网关
7. 查网关日志确认「已加载 N 个工具」的 N 等于映射表条目数
```

第 3 步容易漏：路径写死在公共函数库里，用户名不同则全部指向不存在的目录，部署脚本会静默跳过所有文件而不报错。

部署脚本应自动探测 `HERMES_HOME`，探测顺序为：环境变量 → `hermes config path` → 默认路径，并支持 `--target` 手动指定。不要只写死一个绝对路径。
