# 本地 `local:` 补丁跨版本升级的判定、恢复与重放

本文处理一类反复出现的故障：升级完成后，磁盘上的本地定制全部不在运行代码里，表现为若干功能突然回到旧行为，且不产生任何报错。

## 何时适用

- 升级后某个已修好的问题重新出现，且现象与修复前完全一致；
- 桌面端或网关的行为与源码目录里读到的逻辑对不上；
- 准备基于当前代码排查缺陷，需要先确认当前代码到底是不是自己以为的那份。

## 一、失效机制

`hermes update` 走发布版本通道时，目标是一个发布提交而不是分支顶端。更新流程对发布提交的处理与分支更新是两条不同路径：

- 分支更新（`target_ref` 为 `origin/main`）会走本地改动暂存与恢复流程，本地提交仍在分支上；
- 发布更新（`target_ref` 为发布标签）直接 `git checkout --detach <release_sha>` 落在发布提交上，**跳过本地提交恢复**。

因此升级后出现两个事实，必须分开陈述：

1. 补丁本身没有丢，仍完整保存在本地分支上；
2. 当前运行的代码不包含这些补丁。

汇报时说「补丁丢了」是错的，会让用户以为需要重写代码。

## 二、只读判定流程

按顺序执行，全部只读，不改动工作区。

### 0. 先读升级日志，确认本次落在哪种路径

`logs/update.log` 里每次升级的收尾行带分支形态，直接给出结论：

```bash
grep -n 'Update complete' logs/update.log | tail -10
```

行尾形如 `[main @ <sha>]` 说明这次走分支更新，本地提交仍在；形如 `[detached @ <sha>]` 说明走发布更新，本地提交已离开运行代码。**同一台机器上连续多次 `detached` 说明这是常态而非偶发**，前几次没暴露只是因为事后手动切回了分支。

这一步比任何代码检索都快，应作为排查入口。

### 1. 确认是否游离

```bash
git rev-parse --abbrev-ref HEAD      # 返回 HEAD 即游离
git log -1 --format='%h %s' HEAD     # 当前落在哪个提交
git branch -vv                       # 本地分支及其领先/落后情况
```

### 2. 列出全部本地提交

```bash
git log --oneline --all | grep -i 'local:'
```

### 3. 逐个判定是否在当前代码里

```bash
git merge-base --is-ancestor <local_sha> HEAD && echo 在位 || echo 失效
```

### 4. 判定能否干净重放（决定恢复工作量）

对每个本地提交涉及的每个文件，比较「该提交的父版本」与「当前检出里的版本」是否相同：

```bash
A=$(git rev-parse <sha>^:<file>); B=$(git rev-parse HEAD:<file>)
[ "$A" = "$B" ] && echo 可干净应用 || echo 上游已改动需手工合并
```

父版本与当前版本相同，说明上游没动过这个文件，补丁可以无冲突重放；不同则说明上游改过同一文件，必须人工合并。

### 5. 检索补丁特征字符串，确认运行代码的实际状态

不要只信 git 结论。挑每个补丁里独有的字符串，在磁盘文件里检索：

```bash
grep -c '<补丁特征字符串>' <目标文件>
```

命中数为 0 即确认失效。这一步能同时发现「git 说在位但文件被后续改动覆盖」的情形。

## 三、前端补丁要额外查安装包

桌面端界面代码在打包时被压进 `apps/desktop/release/win-unpacked/resources/app.asar`。源码目录里补丁在位，不代表用户看到的界面带着补丁——安装包可能是升级时重新构建的，也可能是上一次构建的残留。

```bash
cat apps/desktop/release/win-unpacked/resources/install-stamp.json   # 记录构建时的提交
cat apps/desktop/dist/hermes-build.json                              # 记录 sourceHash 与 stampClock
```

**不要在 `app.asar` 里检索补丁特征字符串，检索命中 0 不能证明补丁缺失。** 实测补丁确实已编译进产物时，`grep -c '<特征串>' app.asar` 与 Python `data.count(b'<特征串>')` 都返回 0——连 `function`、`const` 这类必现的 JS 关键字都命中 0，说明 asar 里的内容不是可直接按明文检索的形态。据此判定「补丁没进安装包」会得出完全相反的结论。

**正确落点是 `apps/desktop/dist/assets/` 下的构建产物，且要检索字符串字面量而非标识符**：

```bash
grep -rl 'connection:local' apps/desktop/dist/assets/
```

压缩会把变量名与函数名改掉（源码里的 `isLocalUpgrade` 在产物里已不存在），但**字符串字面量原样保留**。所以特征串要挑代码里的字符串常量（如 `'connection:local'`、提示文案片段），不要挑标识符。命中后把产物里那一段读出来，确认判断逻辑完整（形如 `t.startsWith(\`connection:local\`)`），而不是只看命中数。

**不要用源码时间戳推断产物是否过期**：`find . -newer app.asar` 这类全仓扫描在带 `node_modules` 的检出上会跑满工具超时。判断产物是否对应当前源码，看 `install-stamp.json` 与 `apps/desktop/dist/hermes-build.json` 里的 `sourceHash` 与 `stampClock`，不看文件修改时间。

## 四、恢复策略的取舍

### 直接切回本地分支（看似最省事，通常不可取）

`git checkout <本地分支>` 能让补丁立刻回来，但前提是该分支基于的提交不比发布提交旧。实际情形常是分支停在若干次升级之前，切回去等于把上游这段时间的修复全部倒退。执行前必须先比较：

```bash
git rev-list --count <本地分支>..HEAD    # 分支落后当前检出多少个上游提交
git rev-list --count HEAD..<本地分支>    # 分支上有多少个本地提交
```

落后数量大时，切分支是倒退，不是修复。

### 把本地提交重放到发布提交之上（正确做法）

按第 4 步的判定结果分两类处理：可干净应用的批量重放，需手工合并的逐个处理。重放后本地分支应指向新的发布提交，下次升级的基准才是最新的。

### 建立自动重放机制（根治）

同一类事故重复出现时，人工重放不能算解决。机制要点：升级落在发布提交后，自动把 `local:` 前缀的本地提交重放到新提交之上；冲突时停止并明确报出是哪个补丁、哪个文件。

## 五、与 Git 解耦：把补丁存成仓库外的普通文件

分支保存补丁对发布通道无效。源码注释原文（`hermes_cli/update_cmd.py`）：

```python
# A release lands detached at its exact commit, never merges into or
# rewrites the user's branch. Branch-policy machinery is main-only.
```

按发布版本号升级时，分支策略机制整个不参与。所以长期策略不是「把补丁提交到哪个分支」，而是：**补丁内容存成仓库外的普通文件，升级后按需重打**。

### 1. 备份两种形式

| 形式 | 用途 | 代价 |
| :--- | :--- | :--- |
| `.diff` | `git apply` 应用，体量小 | 官方改过同一处会冲突 |
| 补丁后的完整文件副本 | 直接复制，不依赖 Git | 覆盖会连带丢掉官方在同一文件上的其他改动 |

两者都存。完整文件副本只在确认官方未改该文件时使用。

### 2. 导出 diff 的坑

未跟踪的新文件不出现在 `git diff` 输出里，而补丁常带新增测试文件。导出前：

```bash
git add -N <新增文件路径>          # 让新文件进入 diff
git diff <基线提交> > 全部补丁.diff
git reset                          # 撤销临时索引
grep '^diff --git' 全部补丁.diff   # 数文件数，与预期核对
```

漏了 `add -N` 表现为 diff 里文件数偏少而脚本不报错。

### 3. 验证可应用性

必须在独立克隆里验证，不要在活动检出上 stash 或切分支（会被拦截，也会影响运行代码）：

```bash
git clone --shared -q <仓库> <临时目录>
cd <临时目录> && git checkout -q <基线提交>
git apply --check <全部补丁.diff>   # 退出码 0 即可干净应用
```

验证完删除临时目录。

### 4. 清掉本地提交但保留补丁

用 `git reset --mixed <基线>`，不用 `--hard`：

- `--mixed` 只清提交与索引，工作区文件全部保留，补丁继续作用于当前运行的版本；升级时由 update 的暂存流程处理；
- `--hard` 会连工作区补丁一起抹掉，等于当场丢失功能。

执行前打备份标签并打印回退命令。基线是本地安装版本的起点（第一个本地提交的父提交），**不是 `origin/main`**。

### 5. 升级后的处理顺序

```text
1. 正常升级
2. 跑 git stash list，确认补丁被自动暂存在哪里
3. 在新版本里逐条对照补丁要点，判断官方是否已修复
4. 判定当前环境是否真会触发该问题
5. 三条任一为真 → 不重打，备份可删；全都为假 → 从备份取补丁重打
```

**默认假设官方已修**。本地安装版常落后上游数千个提交，这些缺陷往往早已修好；不先查就重打，会把旧实现盖到已重构的新代码上。

#### 5.1 补丁去哪了：先看 stash

`hermes update` 会先把工作区改动自动暂存，升级完成后工作区必然干净：

```bash
git stash list
# stash@{0}: On main: hermes-update-autostash-<时间戳>
git stash show --stat stash@{0}     # 文件清单，应与补丁涉及的文件一致
```

**工作区干净不代表补丁丢了**。报告「补丁全部丢失」之前必须先跑这一步，否则会把「已安全暂存」误报成「已丢失」，让用户白担心一轮。

确认不需要重打后，删补丁备份时**必须连带 `git stash drop`**，否则 stash 成为一份无人知晓的残留副本。

#### 5.2 判定「官方已修」：对照要点，不靠特征串

**grep 补丁的特征标识符会得出完全相反的结论。** 官方修复常常是重构：原标识符消失，但功能等价甚至更严谨。

正确做法是读官方新实现，把补丁的每个要点逐条对照，全部覆盖才算已修。两个实测例子：

| 补丁要点 | 官方新实现 | 判定 |
| :--- | :--- | :--- |
| 线程池执行、超时上限、超时降级返回 0、不阻塞响应 | `_bounded_context_length_probe` 四项全中，注释思路一致 | 已修 |
| 允许本地连接标识平滑升级 | 原 `isLocalUpgrade` 已不存在，但新增的 `connectionCacheKey` 把「配置档属于注册连接、注册标识即隔离边界」写进注释 | 已修，且更完整 |

特征串命中 0 只说明实现变了，不说明问题还在。

#### 5.3 「官方未修」不等于「需要重打」

还要判定当前环境是否真会触发。先看补丁针对的前提是否存在于本机配置里，再看实测返回值是否已经正确。

典型情形：某补丁修的是「探测不携带密钥，认证端点返回 401」。官方确实没修，但本机四个自定义端点全是内网无鉴权，实测无密钥探测返回 1048576（正确值）——不需要重打。只做源码判定会把「当前无影响」误报成「必须重打」。

#### 5.4 配置已规避的问题，补丁可直接删

若某个阈值配置已经使原问题不再触发，补丁失去意义。典型情形：补丁要把某长任务工具豁免于通用截止时间，而 `timeouts.tools.sequential_call: 3600` 已大于该工具自身超时 1800，通用截止时间不会先触发。

判定顺序固定为：**官方是否已修 → 配置是否已规避 → 是否仍需要补丁**。三条任一为真都不重打。

### 6. 重打后必须验证

补丁带的测试要逐个跑；没有测试的补丁（例如前端改动）需手工验证对应现象。跑之前先记录基线失败项，区分「本来就失败」与「补丁引入」。

## 七、汇报口径

- 先给结论：当前运行的代码是否包含本地补丁，一句话说清；
- 用表格逐项列出「补丁文件 / 应有内容 / 当前实际」，每行带文件与行号证据；
- 把「补丁丢失」与「本次升级造成」区分开：升级是触发器，本地补丁提交在发布提交之外才是原因；
- 方案给两到三条，标明哪条治标、哪条治本，并给出推荐与理由，由用户决定。

## 六、用户要求“把版本升到官方最新”时，先核清版本再动手

用户提出这类要求时，不要直接开始升级。先做一次版本对照，因为很可能已经是最新：

```bash
hermes --version                      # 运行版本
git rev-parse --short HEAD            # 当前提交
git tag --list 'v0.*' | grep -vE 'canary|rc' | sort -V | tail -5   # 稳定版标签
git rev-list -n1 <最新稳定标签>        # 稳定版指向的提交
hermes update --check 2>&1 | tail -5  # 官方更新器自己的判断
```

若当前提交就是最新稳定标签的提交，则代码与桌面端产物都已是发布版，**没有旧内容需要升级**——此时要如实说明并停下，不要为了“有动作”而改走测试通道。

真正需要用户决定的是另一件事：稳定通道之后官方主干又推进了大量提交（只在 canary 通道），要不要切过去。这时给出两侧代价（测试版无稳定性保证对比拿不到新修复），并明确推荐留在稳定通道——尤其当本次故障的根因是本地补丁失效、而非官方代码陈旧时，切测试通道引入的风险与收益不匹配。
