# Hermes Agent 核心框架配置与运维指南

## 概述

规范 Hermes Agent 自身架构的配置、多运行形态调度、多模型提供方切换、多平台网关接入与系统故障排查。

## 适用场景

- 用户需要配置、修改、扩展或排查 Hermes 本体（包括桌面端、命令行、网关、插件、技能库）；
- 模型输出出现机械直译、行话、英文思考链，需要定位并汉化注入给模型的提示词源码；
- 需要判定某项汉化改动到底该落在哪一层（语言包、提示词源码、技能、工具、插件），或判断它会不会被官方升级覆盖；
- 系统提示词、工具描述或技能库需要全量中文规范化，且不得损伤代码；
- 图片能否直接送进主模型、思考链到底开没开这类「配置写了但没生效」的判定。

**核心分工准则**：
- **主助手（Hermes）**：担任系统运行与任务调度中心，协调本地工具、持久记忆库（OpenViking）、MCP 协议扩展以及外部委托实施助手；
- **配置一致性与安全纪律**：严禁手动随意编辑 `config.yaml` 配置文件，必须统一调用 `hermes config set <key> <value>` 官方配置命令修改，避免格式错位或缩进错误破坏配置文件结构，导致网关服务停止响应；机密密钥仅允许存放在 `.env` 文件中。
- **写入成功不等于生效**：`hermes config set` 对已被官方移除的键会**正常返回成功并写入文件**，但运行时根本不读取它。改完任何配置项，必须再做两步：在源码里检索该键名确认有代码读取，以及发一次真实请求确认行为改变。只凭命令回显就宣称已修复，是本类任务最常见的误报。
- **已定的事项不要重复征询**：用户对同一取舍表达过明确决定后，后续按该决定执行，不再逐次确认，也不再把已被否决的方案重新端上桌。反复询问已定事项会被视为没有记住上下文。只有出现新事实（原方案在新版本下失效、前提条件变了、产生副作用）时才重新提出，且要说明「变了什么」而不是重问一遍。
- **用户给出的是通用原则时，后续每个具体对象都按该原则执行，不要再逐个确认**：例如「汉化与仓库解耦」「技能放用户层」「Git 提交对升级无效」这类原则一旦定下，后续遇到任何插件、任何补丁、任何技能都直接套用，不要拿「这个插件的改动要不要保留」「这些技能放哪」逐个去问。逐个确认会让用户重复说同一条原则，属于严重摩擦。拿不准时按已定原则处理并在汇报里说明「按某原则这样处理了」，而不是先问再做；
- **不要拿「A 还是 B」的空问题占用用户的决策精力**：真正需要用户决定的只限于影响方向且我查不出依据的取舍。凡是我能查证（官方是否已修、代码里怎么写的、哪个方案可行）的，自己查完给结论；凡是有已定原则可套的，直接套。
- **Git 提交不是保存本地定制的有效手段，不要再提议**：按发布版本号升级时源码检出会切到游离 HEAD，分支上的本地提交整体失效（源码注释原文 `A release lands detached at its exact commit, never merges into or rewrites the user's branch. Branch-policy machinery is main-only.`）。用户对此已多次明确表态。定制一律按普通文件备份到仓库之外，或做成用户层插件；只在确实必须改框架源码才能生效时，才把改动作为补丁备份并接受升级后重放的成本，且要主动说明这是例外。
- **「覆盖文件」与「提交仓库」是两件事，`git status` 显示 `M` 不代表与仓库绑定**：把补丁后的完整文件直接覆盖到插件或仓库目录里，只要**不执行 `git commit`**，仓库仍停在官方原版，`git checkout -- <文件>` 一条命令即可还原，这不算绑定仓库。判定是否绑定的唯一标准是有没有产生本地提交，不是工作区有没有改动痕迹。因为看到 `M` 就判定为「违反解耦原则」并要求回退，属于把工作区状态误读成仓库状态，用户会直接斥责。相关纪律只有一条：不要提交，覆盖本身是允许的；
- **说明文档里的数字必须用程序核对，不能手工改一遍就宣称同步**：工具条目数、提示词段数、语言包键数这类统计会随每次维护变化，文档极易滞后。做法是写一段脚本读实际映射表与语言包、算出真值，再用正则扫文档里出现的每个对应数字逐项比对，输出不一致清单。手工替换容易漏改（同一数字在目录树、正文、日志示例里各出现一次），也容易改错口径（语言包写的是差异键数还是完整键数）；
- **数字变了就是文档该改了，直接改，不要问用户「要不要同步」**：映射表条目数、插件版本、目录结构、脚本名称一旦变动，所有提到它们的文档（根说明、子目录说明、脚本注释里的示例输出）都在过时。把「要不要更新文档」当成一个选项向用户征询，属于把本该自查的工作丢回去，用户会直接斥责。自查口径：本轮改了哪些数字与路径，就把全库 `*.md` 里出现这些数字与路径的位置全部找出来改完，再报告「已同步哪几处」；
- **文档章节按读者问题组织，不按文件存在顺序平铺**：判断章节划分是否合格的标准是「这一章回答读者哪一个问题」，不是「目录里有几个文件就写几节」。合格的六段式是：概述（有什么）→ 核心机制（怎么生效）→ 数据（存在哪、什么结构）→ 维护（日常怎么改）→ 移植（换机器怎么做）→ 附录（清单与排障）。把「语言包」「技能」这类同属「怎么生效」的内容拆成独立章、却让「核心机制」与「维护」各占一大章，是典型的平铺罗列；
- **章节数不是目标，内容量与章节重要性匹配才是**：先统计每章行数，失衡明显（最大 98 行对最小 7 行）就说明分组错了。7～20 行的小节不该独立成章，应并入相邻章作为子节；60 行以上的核心章才配独立。用户看到「重构完 12 个章节」这种以数量交差的说法会直接质疑能力；
- **总说明只给索引、入口与指针，细节一律下放子目录说明**：同级存在多个资产目录时，根说明写「这个目录有什么、用哪个脚本部署、详细说明见该目录的 `说明.md`」，不要把插件清单、汉化机制逐条复述一遍。三处维护同一个事实，改一次要同步三次，迟早对不上；
- **标题去掉修饰语，只留名词**：「映射表即基线」→「映射表」，「汉化怎么生效」→「汉化机制」，「提示词锚点：不能翻译的部分」→「提示词锚点」，「插件构成（14 个，不含内置）」→「插件分类」。括号里的解释、破折号后的补充都应移到正文，标题只承担定位作用；
- **文档结构重构先交大纲等确认，不要直接重写**：用户提出「重构一下」时，先输出「当前结构的问题（含各章行数与占比）+ 新章节大纲（每章写什么、预估多少行、由哪几章合并）+ 章节对照表 + 需要用户决定的具体问题」，得到确认后再动笔。直接改完再汇报结构，用户会先问「为什么是这个章节数」而不是看内容；一次重写后又推翻重来，浪费的是用户审核的精力；
- **小节层级同样要控数量，一件事一个小节就是罗嗦**：把同一主题拆成「是什么／为什么／怎么装／网络要求／手工做法／版本说明」六小节，读者要跨六次跳转才拿到完整做法。合格形态是二到三小节：**是什么（含位置与来源）＋怎么做（命令与失败分支）＋边界（网络或版本这类单列提示）**。写完数一遍小节数，超过三节先合并；
- **不写版本对比说明**：「本机 0.14.1 / 最新 0.18.0」这类对照在文档里没有信息量——新装自然拉最新版，版本号本来就由配置文件决定。文档只需一句「版本由 `<配置项>` 决定」，升级方法写进操作步骤即可。用户看到这种对照会直接说「新安装肯定按最新的呀，还罗嗦什么版本」；
- **配置里用 `==` 精确锁版本的外部包不会自动更新，用户问「为何没自动更新」时要先说清机制再给升级路径**：这是刻意的锁定设计，不是漏了自动更新。回答顺序固定为「是 `config.yaml` 里的 `==` 锁死的 → 好处是避免上游不兼容 → 要升就改版本号再跑安装命令」；同时主动查一次 PyPI 最新版，不要等用户催；

## 一、 系统架构与三大运行形态

Hermes 框架由底层统一的核心运行引擎驱动，向上支持三种主要交互形态，彼此共享会话数据与配置：

1. **原生桌面客户端（Desktop App）**：
   - 基于 Electron 构建的跨平台图形交互界面，支持流式对话渲染、工具调用状态追踪、实时可视化文件浏览器与侧边栏项目导航；
   - 启动命令：`hermes desktop`。
2. **终端交互界面（CLI & TUI）**：
   - 终端轻量对话界面（`hermes`）与基于全屏字符界面的终端控制台（`hermes --tui`）；
   - 适用于纯命令行服务器环境或轻量化即时交互。
3. **Web 集中管理看板（Web Dashboard）**：
   - 提供基于浏览器的后台管理面板，用于管理会话路由、监控运行状态与配置 Webhook 触发器；
   - 启动命令：`hermes dashboard`。

## 二、 核心路径与配置规范

宿主环境关键目录分布（Windows 环境下位于 `%LOCALAPPDATA%\hermes\`）：

| 物理相对路径 | 用途说明与维护规约 |
| :--- | :--- |
| `config.yaml` | 系统全局配置（仅存放非机密配置项，严禁存放 API Key 等私密凭据）。 |
| `.env` | **机密凭据唯一存储文件**（存放各类 API 密钥与第三方连接令牌）。 |
| `skills/` | 本地已安装的自动化技能正本目录。 |
| `plugins/` | 运行期代码拦截插件目录（如 `zh-jargon-guard`、`script-guard`）。 |
| `state.db` | 会话状态数据库（SQLite 存储历史会话元数据）。 |
| `logs/` | 运行时系统日志与网关通信报错记录。 |

## 三、 外部智能体多进程派发规范

当面临长周期、复杂编译或需要完全隔离运行环境的任务时，主助手可直接在后台派发独立的 Hermes 进程执行：

### 1. 单次非交互式指令派发（One-Shot Mode）
```bash
# 启动后台单次任务（输出写入指定报告）
hermes chat -q "请对 ~/research 目录下的文献开展结构化分析并输出报告"
```

### 2. 交互式会话恢复与接续
```bash
# 恢复并接续最近一次的活动会话
hermes --continue

# 指定具体会话标识接续运行
hermes --resume <session_id>
```

## 四、 核心运行期铁律

1. **严禁破坏提示词缓存机制（Prompt Caching Invariant）**：
   - 在单次会话过程中，不得动态随意更迭系统提示词、工具集合定义或上下文基础规则，确保服务商的“提示词缓存机制（Prompt Cache）”保持高命中率，降低首字响应延迟与计算开销；
2. **严格遵守消息角色交替规约**：
   - 严禁连续发送两个用户消息或两个助手回复，必须严格保持 `user` 与 `assistant` 的交替节奏（仅工具结果 `tool` 允许连续返回）；
3. **环境隔离与路径规范**：
   - 涉及多任务并行时，必须使用临时工作区或 Git 工作树隔离，严禁多个任务直接在同一个工作目录中并发写入，防止代码状态发生冲突。
4. **图片直接送进主模型的配置必须两处同时改**：
   - 只设 `agent.image_input_mode: native` 不够，图片仍会被替换成文字描述；必须在 `providers.<名称>.models.<模型名>.supports_vision: true` 一并声明，把 `models` 从列表改成字典形式；
   - 判定链路有两次独立查询：`decide_image_input_mode` 决定发原图还是发描述，`_lookup_supports_vision` 决定图片是否被从消息里剥离。两处都通过才会真正把原图送进模型；
   - 改完用 `decide_image_input_mode(provider, model, cfg)` 与 `_lookup_supports_vision(provider, model, cfg)` 各查一次，两个返回值必须分别是 `native` 与 `True`；
   - 详细判定分支与实测方法见 `references/image-and-reasoning-routing.md`。
   - **声明一个模型支持视觉之前，必须先实测该模型真的能看图。** 视觉能力不能靠模型名或厂商推断：生成一张写着固定数字或纯色的图片发给它，看它能不能准确读回。读不回就不能声明，否则图片直传会被上游拒绝或得到胡猜的结果；
   - **`image_input_mode` 是全局开关，会对所有模型生效。** 明确不支持视觉的通道需要单独排除，否则图片直传会被拒。
5. **思考链开关由 `reasoning.effort` 决定，`chat_template_kwargs.enable_thinking` 对 Responses 接口无效**：
   - 在 `providers.<名称>.extra_body` 里写 `chat_template_kwargs.enable_thinking: false` 不会关闭思考链，该参数只对 `chat/completions` 接口起作用；`/v1/responses` 接口只认 `reasoning.effort`，取 `none` 才真正关闭；
   - 全局 `agent.reasoning_effort: high` 会让每个请求都带上 `reasoning.effort: high`，此时无论 `enable_thinking` 写什么，思考链始终开启。看到桌面端出现思考窗口就是这一条在起作用，不是配置写错了；
   - 只关某一个模型时用 `agent.reasoning_overrides: {<模型名>: false}`，不要动全局挡位，否则会连带关掉其他模型的思考链；
   - 判断某个参数是否真的生效，必须做对照实测：同一问题分别发送「只带该参数」与「带该参数加 `reasoning.effort`」两组请求，比较响应里有无 `reasoning` 输出项。只读配置推断会得出相反结论。
6. **超时类故障必须先证明被调用路径带着正确凭据，再谈阈值**：放宽阈值属于掩盖症状：被调用方若是因为缺少凭据、缺少参数而反复走无效请求，放宽后只是让错误结果更晚出现；
   - 定位顺序固定为三步：① 读后端日志里与超时同一时刻的记录，确认是哪个函数、哪个上游地址在耗时；② 直接调用该函数做「带凭据／不带凭据」对照实测，比较耗时与返回值；③ 只有确认凭据与参数齐全、耗时来自对方合法响应时，才讨论阈值；
   - 对照实测要同时看两项：耗时是否下降，以及返回值是否改变。返回值改变说明原来拿到的是猜测值而非真实值，属于结果错误，比超时更严重；
   - 具体案例与复现方法见 `references/troubleshooting.md` 的「模型上下文窗口探测」一节。
7. **汉化资产导入前必须先做三态基线校验，不得直接覆盖**：
   - 每项汉化资产都涉及三个文件：系统源文件、英文基线、中文汉化稿。导入前逐一比对指纹，只有「系统 == 英文基线」才允许导入中文版；
   - 「系统 == 中文稿」说明已汉化在位，跳过即可；两者都不相等说明官方已升级，汉化失效，必须拒绝导入并触发重新汉化流程；
   - 拿不到英文基线时一律拒绝导入，不得默认放行。缺基线的「放行」会把旧汉化盖到已升级的新文件上，造成静默回退；
   - 重新汉化流程：旧基线归档到带时间戳目录 → 升级后的系统文件覆盖基线形成新基准 → 失效中文稿移入待重新汉化目录（仅作参考，不再参与导入）→ 助手按新基准重写；
   - 自研资产（无英文原版、中文即正本）需显式白名单，不能靠「找不到基线」自动归入；
   - **系统与工作目录都是中文但内容不同时，按资产类型分开处理**：配置、插件、工具以系统版为准；技能必须逐文件合并取长补短，不能按新旧选一边——两边改的常常是不同章节，选一边就会丢掉另一边的内容；
   - 完整判定分支、目录布局、技能合并步骤与沙箱验证方法见 `references/asset-migration.md`。
8. **语言包的用户层覆盖优先级高于仓库层，汉化改仓库版可能完全不生效**：
   - `agent/i18n.py` 的加载顺序从高到低为：插件语言包 → 用户层 `$HERMES_HOME/locales/<lang>.yaml` → 仓库内 `locales/<lang>.yaml` → `en` 层 → 裸键；
   - 用户层若放的是完整语言包副本，会把仓库里的新版整体盖住，改仓库版等于白改，且不产生任何报错；
   - 验证方法：`from agent.i18n import t` 后取一个刚在仓库版改过的键，看返回的是新译法还是旧译法；返回旧译法即证明用户层在覆盖；
   - 正确用法：用户层只放需要覆盖的少数键，其余全部回落仓库版；汉化已提交仓库时，用户层文件可直接删除。**不要把完整语言包复制到用户层当备份**——那不是备份，是覆盖；
   - 四个变体 `zh.yaml`、`zh-hant.yaml`、`zh.tui.yaml`、`zh-hant.tui.yaml` 是四份独立文件，必须同步改，改完对四个文件同时做反向检索。
9. **设计汉化在官方升级时的存活方案前，先分清哪些资产本来就不受升级影响**：
   - `SOUL.md`、`config.yaml`、`.env`、插件目录都在用户层 `$HERMES_HOME`，升级动不到；仓库里的 `SOUL.md` 是模板，与用户层那份内容不同，不要混淆；
   - **技能也在用户层 `$HERMES_HOME/skills/`，但由同步脚本管理，保护机制是哈希比对而非「升级不碰」**：`tools/skills_sync.py` 把仓库 `skills/` 同步过来时，只有「仓库版变了」且「用户副本仍与原始哈希一致」才更新，用户改过的直接跳过。所以改过 `SKILL.md` 的技能升级后不会被覆盖，但仓库里新增的技能会被补装；
   - 受升级影响的只有两类：仓库内 `locales/` 语言包（有用户层可覆盖）与 `agent/` 下的提示词源码（无官方覆盖机制）；
   - **语言包只能覆盖核心界面文案，覆盖不了技能、工具、插件与提示词正文**：只有代码里写了 `t("键")` 的字符串受语言包控制（约 3486 个键、分布在 96 个源文件，集中在命令行、网关、平台适配器）；技能的描述直读 `SKILL.md` 头、工具的 schema 描述硬编码在 `tools/*.py`、插件的 `plugin.yaml` 直读原文、六个提示词模块的正文同样是硬编码。因此「模型说话像不像人话」取决于提示词正文，恰是语言包覆盖不到的那一层，不要指望改语言包能调整模型措辞；
   - 提示词源码的三条存活路线各有硬约束：插件段落接口只有 `after_memory` 一个位置且单段上限 4000 字符（六个文件合计约 7.9 万字符，装不下，也无法替换原有英文）；`llm_request` 中间件能真正替换但需维护完整映射表且依赖未公开的请求结构；Git 本地提交零运行时开销但升级时要解冲突；
   - 取舍按注入频率排序：`prompt_builder.py` 与 `system_prompt.py` 每轮必注入，映射表优先覆盖这两个，收益最大；其余四个按触发条件（工程目录、会话压缩、每轮结束、空闲）逐步补充；
   - **用户端不得与主仓库绑定，汉化一律不落主仓库 Git 提交**：主仓库的 `local:` 提交会在升级时因检出切到游离 HEAD 而整体失效，且每次升级都要人工解冲突。用户对这条路明确表达过拒绝。正确落点全部在主仓库之外的用户层：语言包走用户层差异键，工具与提示词走 `llm_request` 中间件插件，技能与插件直接改用户层文件。只有确实无法用用户层承载的改动（必须改框架源码才能生效的缺陷修复）才考虑 Git 提交，并接受升级后重放的成本；
   - **中间件插件天然不受升级影响**：插件目录在 `$HERMES_HOME/plugins/`，不在 `hermes-agent` 仓库内（`Path.is_relative_to` 实测返回 False），`hermes update` 只动仓库目录。承载汉化映射表的插件无需任何 Git 操作，升级后照常生效；
   - **插件放进目录还不够，必须登记进 `plugins.enabled`**：未登记的插件在发现阶段被跳过，日志只有一行 `Skipping '<名称>' (not in plugins.enabled)`，不报错、不影响启动。另，`plugin.yaml` 不认 `provides_middleware` 字段，中间件靠 `register(ctx)` 里的 `ctx.register_middleware("llm_request", 回调)` 注册；
   - **映射表一旦生成，它自己就是基线，日常维护不再回看 Git**：升级到哪个版本，那个版本就是新基线。维护脚本对比「当前仓库源码」与「映射表」，只报告三类变化——新增（仓库出现了映射表里没有的英文）、删减（映射表里的英文在仓库中已消失）、修改（同一个键的英文原文变了）。只处理有变化的条目，未变化的原样保留。**升级成本与「官方改了多少」成正比，而不是与「汉化了多少」成正比**。把维护脚本写成「每次都要从 Git 找英文基线重新配对」，等于把映射表重新绑回仓库，升级后必然失效；
   - **只有首次生成映射表时才需要英文基线**，且只做一次。此时可以用「沿 Git 历史回溯找中英切换点」的办法（该版本含中文、其更早版本不含中文，那个更早版本即基线），兜底顺序为中英切换点 → 历史最老英文版 → `origin/main` → 跳过并报告，不得静默取空。工具与提示词的汉化往往不在同一个提交里，用统一基线会出现「工具映射 0 条」而提示词正常；
   - **语言包差异键用脚本自动抽取，不要手工挑**：对比「仓库版」与「官方 `origin/main` 版」，逐键取差异，写入用户层。实测四个文件合计 169 个差异键，`zh.yaml` 从完整副本 255 KB 降到差异键 7 KB。抽取脚本要能处理嵌套 YAML（摊平成 `a.b.c` 键再还原），并优先用 `ruamel.yaml` 保序，缺失时退回 PyYAML；
   - **映射表维护脚本改完后必须手工同步到插件目录**：`maintain_maps.py --apply` 只改工作目录里的映射表，插件运行时读的是 `$HERMES_HOME/plugins/<插件名>/` 下的副本。忘了复制会表现为「脚本报告已补齐 N 项，但中间件仍只替换旧条目数」，不报错；
- **映射表有两个位置，正本在工作目录、运行副本在插件目录，两处必须字节一致**：正本放仓库外的工作目录（可备份、可版本化，例如 `D:\Hermes\汉化覆盖层\`），运行副本在 `$HERMES_HOME/plugins/<插件名>/`。改完用 `sha256sum` 比对两者前 16 位确认一致，不要假定复制步骤一定执行过；用户问「映射备份在哪」时，答工作目录那份并给出校验值，而不是只说插件目录；
- **改完映射表后，桌面端重启不等于网关重启，必须单独重启网关**：网关是独立常驻进程（`python -m hermes_cli.main --profile <档> gateway run --quiet`），关闭重开桌面端不会连带重启它。实测桌面端已重启、网关仍停在映射表更新之前的时刻，网关加载的是旧表。表现为「核心工具汉化正常、插件工具全是英文」，不报错、不告警，极易误判成映射表没写对；
- **验证映射表实际加载条目数只看网关日志，不看文件也不看进程存活**：`grep zh_localization_overlay logs/gateway.log | tail -3`，日志会打印「已加载 N 个工具的中文映射」，N 必须等于映射表实际条目数；不等即说明网关未重启。再用 `Get-Process`（PowerShell）比对网关进程启动时间与映射表文件修改时间，启动时间早于文件修改时间就是没重启。`ps aux` 在 git-bash 下看不到 Hermes 的 Windows 原生进程，要走 `powershell.exe -NoProfile -Command "Get-Process"`；
- **`hermes plugins list` 会把长插件名截断成 `zh-localizatio…`，用全名 grep 会误判为「插件不存在」**：核对插件是否启用时用短前缀匹配（`grep -E "^│ zh"`），或改用 `--plain` 输出；
- **插件自带技能与用户层同名技能可以共存，不冲突**：插件技能以限定名 `插件名:技能名` 注册（`hermes_cli/plugins.py` 的 `_plugin_skills`），用户层技能用裸名，两者互不覆盖。因此把仓库插件的技能汉化放用户层后，插件内那份英文技能仍在、仍可被限定名调用，这是预期行为，不是「汉化没做干净」；
   - **从源码提取工具 schema 必须先解析模块级常量引用**：描述常写成 `TERMINAL_TOOL_DESCRIPTION` 再被字典引用，直接取字典值得到的是 `ast.Name` 节点，提取结果为空。先收集模块顶层常量表，再对字典值做一次 resolve；
   - **提取提示词常量时，AST 求值会漏掉两类写法，必须改用导入方式**：提示词常量有三种形态——字面量拼接（`("...", "...")`，AST 能求值）、f-string 拼接（`("...", f"{HEADING}", "...")`，AST 求不出）、函数调用（`build_memory_guidance(True)`，AST 求不出）。只用 AST 会静默漏掉后两类，表现为映射表条目数偏少但脚本报告成功。正确做法是 `importlib` 加载模块后从 `vars(module)` 取全部大写字符串常量，导入失败才退回 AST；
   - **导入方式会把从别的模块 import 进来的常量也算进去，必须用 AST 收集本文件定义的名字做白名单**：`system_prompt.py` 从 `prompt_builder.py` 导入了十几个常量，导入后它们都出现在 `vars(module)` 里。不过滤会让映射表出现「同一段中文挂在两个模块名下」，且其中一份的英文侧为空、替换永远不命中。白名单取「本文件模块级 `Assign` 与 `AnnAssign` 的目标名」，只保留这些；
   - **映射表只覆盖模块级常量，函数内提示词会漏**：六个提示词模块的中文长字符串共 127 处，模块级常量只占 31 个，其余 96 处在函数体内。汇报覆盖范围时要说明这层缺口，不要把「已生成映射表」等同于「已全覆盖」；
   - **官方删掉或合并工具后，映射表里的旧条目必须删除，不能留着当历史**：条目对应的工具在源码里已不存在，替换永不命中，但每次差异对比都会把这批条目报成「删减」，淹没真正需要处理的变化。更危险的是旧中文描述里写着「需先调用 browser_navigate」这类已失效的操作顺序，一旦被误引用就得出错误结论。删除前不必留情——官方确实不再提供该工具时，映射里留着它就是垃圾；
   - **官方用「一个统一入口 + 代码脚本」取代多个细分工具时，要重做那个入口的映射，而不是只删旧的**：实测某个开头的浏览器系列从十个工具合并为一个脚本入口（写一段 Python 代码，一次性完成打开、点击、输入、截图），此时若只删掉十条旧条目、不动新入口的映射，能力说明就断了。新入口的中文描述要完整覆盖：执行模型、首行注释要求、状态保持边界、多任务分文件汇总的做法、分批策略、预置辅助函数全清单、异常场景处理；
   - **描述在运行时拼装的工具，扫描器取不到英文侧，映射条目会只有中文或英文侧为空**：这类工具的 `description` 写在代码里是「静态回退文本 + 运行时拼接」，扫描到的是拼接结果而非模块级常量。此时要直接读源码里的字符串常量（例如 `_HEADER_BASE`、`_HELPERS_DIGEST` 这两个变量）按实际拼接顺序拼出完整英文，再据此重译并手写 `en` 侧。英文侧为空会让维护脚本永远无法判断官方是否改过描述，也是一个「已接入映射」的假象；
   - **映射表按「工具名 + 参数名」索引，不要存全文替换对**：工具 schema 是结构化数据，每个描述有唯一路径；按路径查表命中才替换、未命中保持英文。官方新增工具或参数自动走英文不会出错，官方改动某条描述只需更新那一条，维护量从「全量几百处」降到「每次几条」；
   - **走中间件不等于放弃汉化**：把中文文本从 `tools/*.py` 挪到插件映射表，模型收到的仍是中文。用户若担心「工具描述不汉化影响中文效果」，要说明这是存放位置变化而非取消汉化，汉化质量与覆盖面不变；
   - **撤回主仓库汉化提交前，必须先把汉化文本导出成映射表**：撤回会让源码回到英文原版，映射表没建好就撤回等于丢失全部汉化成果。顺序固定为「导出映射表 → 验证中间件生效 → 再撤回提交」；
   - **撤销本地汉化提交不能用 `git revert`，撤销动作本身不该成为新提交**：revert 会在历史里留下成串的 `Revert "..."` 记录，与原始汉化提交两两抵消，净效果为零却把历史搅乱。用户对这类历史明确表达过不满。正确做法是把这些提交从历史里去掉（`git reset --soft` 到汉化开始前的提交，再按目标状态重新提交），而不是在顶部追加反向提交。执行前先打备份标签，且需在 Hermes 停机的终端里做——运行中在活动检出上改写历史会被拦截；
   - **梳理历史时先算净效果，别按提交数统计**：一串汉化提交加一串 revert，净差异可能只剩几个文件。用 `git diff --stat <汉化开始前的提交> HEAD` 看真实净效果，再决定保留哪些、丢弃哪些。汇报时给净效果而不是提交条数；
   - **压缩历史前逐个核验要保留的补丁是否真在当前 HEAD 里**：净效果只说明「哪些文件不同」，不说明「该保留的补丁都在」。分支分叉后某个功能补丁可能只提交在 `backup/*` 分支上、从未进入当前分支，它不会出现在净效果里，压缩后永久丢失。做法是用每个补丁的特征标识符在目标文件里 `grep`，而不是看提交标题；发现丢失就从备份分支 `git show <sha>:<路径>` 取回。先 `git log HEAD..<备份分支>` 看备份分支多出哪些提交；
   - **改写历史被拦截时，写脚本交给用户在停机终端跑，不要降级成追加 revert**：脚本用 Python 写（`.cmd` 只能纯 ASCII，写不进中文提交信息，且会被 `script-guard` 拦截）。脚本必须自带四道措施：自动打备份标签并打印回退命令、用 `reset --soft` 而非 `--hard`、提交信息逐条说明每个补丁解决什么、任一步失败立即退出。**重置目标绝不能硬编码 `origin/main`**，必须是本地安装版本的起点（第一个本地提交的父提交）；
   - **取「英文原版」的参照点只能是本地安装版本自己的历史，绝不能用 `origin/main`**：本地安装版是某条稳定发布线，`origin/main` 是开发主线，两者常差数千个提交。实测差距 2688 个提交时，`origin/main` 上的 `tools/browser_tool.py` 只有 11 行废弃存根（`warm_agent_browser_npx_cache` 恒返回 False），而本地版是 1376 行完整实现——用 `git show origin/main:<路径>` 覆盖回去，等于把整套工具换成不兼容的新版代码，Hermes 直接无法启动。正确参照点是**汉化提交的父提交**（`<汉化提交>^`），或本地 `HEAD` 自身；判定方法：`git rev-list --count HEAD..origin/main` 与 `git rev-list --count origin/main..HEAD`，任一不为 0 就说明 `origin/main` 不是本地的原版；
   - **恢复文件优先用 `git show HEAD:<路径>`，其次才是父提交**：`HEAD` 是当前检出的完整状态，只要该文件没有未提交改动，`git show HEAD:<路径>` 一定拿到与运行代码一致的版本。用父提交前先确认那个提交里该文件确实是英文版（`git show <sha>:<路径> | grep -c '[\u4e00-\u9fff]'`），不要假定「父提交就是英文原版」；
   - **批量覆盖文件前先抽查一个文件的规模是否合理**：把 39 个文件一次性覆盖后才发现 `browser_tool.py` 从 1376 行变成 11 行，说明缺少前置校验。覆盖前对每个文件比对「目标版本行数」与「当前行数」，差异超过 50% 就停下来查原因，不要整批执行；
   - **回答「现在某层汉化还在不在」这类状态核查，逐层用各自判据实测，不要凭印象概括**：提示词源码看中文字符数与常量取值、工具看 `tools/*.py` 含中文的文件数、语言包看 `t()` 返回值、技能看 `SKILL.md` 头的 description 语言、插件看 `plugin.yaml` 的 description 语言（多行 `>` 写法要读正文，按行首 `description:` 判断会误判成英文）。五层结论可能各不相同，笼统答「都是中文」或「都是英文原版」都会错；
   - **回答「某层是本地汉化还是官方原版」时，必须拿三个版本对照（官方 `origin/main`、仓库工作区、用户层），不要只比两个**。语言包尤其容易答错：官方仓库自带的中文语言包本身就是中文，本地做的是清洗润色而非英译中。只比「仓库 vs 用户层」会得出「仓库新版是本地汉化」这个不完整结论，漏掉「官方本来就是中文」这一层；
   - **统计本地提交性质时逐个看提交的改动文件，不要只看提交标题就归类**。标题写着功能修复的提交可能同时改了语言包，标题相近的相邻提交可能一个是汉化一个是修复。用 `git show --stat --format="" <sha>` 逐个核对，再按改动文件归类；
   - 完整对比、用户层覆盖验证方法与提交陷阱见 `references/upgrade-survival.md`。
10. **工具调用的“超时”分两层，调大工具参数改不了外层**：
   - 外层是 Hermes 自己的通用工具截止时间：`tool_executor` 的 `_resolve_sequential_tool_timeout()` 读 `timeouts.tools.sequential_call`，未配置时默认 **420 秒**；
   - 豁免名单 `_SEQUENTIAL_DEADLINE_EXEMPT_TOOLS` 由官方维护，官方发布版只含 `delegate_task`、`manage_connections`。名单外的工具（包括其他插件注册的工具）到点就被判超时，**子进程不受影响、会继续把活干完**；
   - **判断某工具是否会被外层切断，先读配置里的 `timeouts.tools.sequential_call`，再决定要不要动豁免名单**：把该值调到大于工具自身超时（例如 `sequential_call: 3600` 配 Codex 自身 1800 秒默认超时），外层永远不会先到点，豁免名单就不是必需项。为这个问题长期维护一个本地补丁，属于用改源码解决一个配置能解决的事；
   - **本地补丁与官方同名常量冲突时，以「当前磁盘上的常量值」为准判断，不要引用补丁时期的值**：官方后续会把这个名单收进自己的代码，此时本地补丁要么被升级清掉、要么与官方版并存造成误判。核验方法是直接读 `agent/tool_executor.py` 里该常量的实际内容，再对照 `git log -S '<常量名>' -- <文件>` 看这一行是谁引入的——官方引入的话，本地补丁就该弃用；
   - 豁免名单的改动只在重启后的网关与桌面进程生效：运行中的进程早已 import 旧模块，磁盘更新对当前会话无效。验证要在新进程里读常量，不要读源码文件；
   - 判定豁免是否真的生效要做反向验证：清空名单后同一场景必须重新被判超时，同时普通工具必须仍然超时。只检查「名字在名单里」测的是常量，不是机制；
   - 插件注册接口 `ctx.register_tool` 不暴露 `execution_timeout` 参数，`_extend_tool_timeout()` 因此拿不到插件自己声明的时长，只能回落默认值。所以“把工具自己的 timeout 调大”对外层无效，两层取的是不同来源；
   - 判断到底是哪一层超时：看返回文案是插件自己拼的（`Codex 执行超时（超过 N 秒）`，N 等于传入参数）还是框架生成的 `tool_timeout`。前者是内层杀进程，后者是外层放弃等待；
   - 要真正放宽长任务工具，只有两条路：把工具名加进豁免名单，或给插件注册接口补上 `execution_timeout` 透传。两者都属产品源码改动，须提交产品仓库主分支才不被升级覆盖；
   - 外层超时后不要立即重派：先查被调方自己的会话或日志，确认是否已跑完。
11. **`hermes update` 会把源码检出切到游离 HEAD，本地 `local:` 补丁全部失效**：
   - **排查入口是升级日志**：`grep 'Update complete' logs/update.log | tail -10`，行尾 `[main @ <sha>]` 说明走分支更新、本地提交仍在，`[detached @ <sha>]` 说明走发布更新、本地提交已离开运行代码。这比任何代码检索都快；
   - update 完成后工作区停在发布提交的游离 HEAD 上（日志里写作 `[detached @ <sha>]`），而 `local:` 补丁都提交在 `main` 分支——磁盘上的文件是上游原版，**所有本地定制都不在运行代码里**；
   - 判定方法：`git rev-parse --abbrev-ref HEAD` 返回 `HEAD` 即游离；再挑一项可观测的本地定制（提示词中文措辞、语言包译法、某个探测逻辑）在磁盘文件里检索，命中数为 0 即已失效；
   - 恢复不能直接假定为 `git checkout main`。切回本地分支前必须先比较落后量：`git rev-list --count main..HEAD`。分支常停在若干次升级之前，切回去等于把上游这段时间的修复整体倒退，属于倒退而非修复。正确做法是把 `local:` 提交重放到当前发布提交之上；Hermes 运行时禁止在活动检出上切分支，需停掉网关与桌面进程后在外部终端执行；
   - 重放前先判定每个补丁能否干净应用：比较「该提交的父版本」与「当前检出里的版本」是否相同，相同即可无冲突重放，不同则上游改过同一文件、必须人工合并。重放后本地分支应指向新的发布提交，下次升级的基准才是最新的；
   - 前端补丁要额外查安装包：源码目录里补丁在位不代表用户看到的界面带着补丁。比对 `apps/desktop/release/win-unpacked/resources/install-stamp.json` 里的 `commit` 与当前检出，再用 `grep -a -o -c '<特征字符串>'` 在 `app.asar` 内检索，命中为 0 即安装包不含该补丁；
   - 同一类事故重复出现时，人工重放不算解决，应建自动重放机制：升级落在发布提交后自动重放 `local:` 提交，冲突时停下并报出具体补丁与文件；
   - 完整判定命令、重放可行性比较法与方案取舍见 `references/local-patch-carry-over.md`；
   - **排查任何“修好的问题又回来了”类故障，先做这一步**：模型切换、界面交互、提示词措辞、工具超时豁免这些本地定制都可能在升级后静默失效。在上游原版代码里反复分析已经修过的问题，是这类排查最常见的浪费。
   - **每次 update 后逐项核验，不要假定补丁自动携带**。update 日志里连续出现多次 `detached @` 说明这是常态而非偶发；前几次没暴露只是因为事后手动切回了 `main`；
   - 补丁本身不会丢（仍在 `main` 分支上），丢的是「当前运行的代码包含它们」这一事实。汇报时要把两者分开说，不要笼统说「补丁丢了」。
   - **分支保存补丁对发布通道根本无效，长期策略必须是补丁与 Git 解耦**：源码注释原文 `A release lands detached at its exact commit, never merges into or rewrites the user's branch. Branch-policy machinery is main-only.`——按发布版本号升级时，分支策略机制整个不参与，挂在 `main` 上的补丁升级后必然失效。因此不要用「把补丁提交到某个分支」来保证存活，要按普通文件备份到仓库之外；
   - **备份同时给两种形式**：`.diff`（体量小，可 `git apply`）与补丁后的完整文件副本（不依赖 Git，但覆盖会连带丢掉官方在同一文件上的其他改动，只在确认官方未改该文件时使用）。备份目录放在仓库外，与汉化资产并列；
   - **导出 diff 前必须先 `git add -N <新增文件>`**：未跟踪的新文件不出现在 `git diff` 输出里，而补丁常带新增测试文件，漏掉就等于备份缺测试且不报错。导完用 `grep '^diff --git'` 数一遍文件数，与预期核对；
   - **备份后必须验证可应用性，验证要在独立克隆里做**：`git clone --shared` 到临时目录 → `git checkout <基线提交>` → `git apply --check <diff>`。不要在活动检出上 stash 或切分支验证（会被拦截，也会扰动运行代码）；验证完删除临时克隆；
   - **解耦用 `git reset --mixed <基线>`，绝不用 `--hard`**：`--mixed` 只清提交与索引、保留工作区文件，补丁继续作用于当前运行的版本，升级时由 update 的暂存流程处理；`--hard` 会连工作区补丁一起抹掉，等于当场丢失功能。解耦前先打备份标签并打印回退命令；
   - **升级后先观察官方是否已修复，不要默认重打补丁**：本地安装版常落后上游数千个提交，这些缺陷很可能早已修好。重打前先在新版本里检索补丁对应的代码位置；
   - 备份清单、验证命令与解耦步骤见 `references/local-patch-carry-over.md` 的「与 Git 解耦」一节。
12. **`swe-guard` 会拦截直接 `patch` 业务源码**：
   - 对业务源码调用 `patch`/`write_file` 会被拒绝并提示改用 `codex_delegate`；这是流水线门禁在起作用，不是工具故障；
   - 计划文件、文档、临时脚本不受此限。因此「改代码」与「写文档」是两条不同路径，不要因为文档能直接写就以为源码也能。重派会让两个进程同时改同一批文件。

## 五、 系统提示词源码汉化的安全边界

Hermes 向模型注入的顶层指令并非只存在于技能与工具定义中，另有十三个源码文件直接生成系统提示词正文。汉化这些文件属于源码改造，必须遵守下列铁律。

### 1. 提示词来源文件全量清单

按注入频率分两级。**每轮必注入**的文件优先处理，收益最大。

| 文件 | 生成内容 | 触发条件 |
| :--- | :--- | :--- |
| `agent/prompt_builder.py` | 平台交互指引、宿主环境说明、技能与记忆调度规约、执行纪律、看板任务协议 | 每轮必注入 |
| `agent/system_prompt.py` | 总装模块，自身也含身份行、时间行、配置档行、内嵌终端说明、模型身份说明 | 每轮必注入 |
| `agent/coding_context.py` | 代码工程角色设定、编辑格式指引、工作区快照说明 | 工作目录为工程项目时 |
| `agent/oneshot_footprint.py` | 单次查询会话的技能加载变体 | `hermes chat -q` 会话 |
| `agent/context_compressor.py` | 会话压缩摘要生成提示词、压缩标记、逐字用户消息与锚点索引章节 | 会话超长触发压缩 |
| `agent/background_review.py` | 每轮结束后台评估是否保存技能与记忆 | 每轮结束后 |
| `agent/curator.py` | 空闲时后台维护技能库 | 空闲触发 |
| `agent/onboarding_text.py` | 首次运行引导话术 | 首次运行 |
| `agent/plan_prompt.py` | 计划模式只读审查规则 | `/plan` |
| `agent/side_question.py` | 旁支提问的独立回答规则 | `/btw` |
| `agent/moa_loop.py` | 多模型协同回合的参考上下文 | `/moa` |
| `agent/title_generator.py` | 会话标题生成规则 | 会话开始 |
| `agent/micro_compaction.py` | 逐轮微压缩标记 | 默认关闭 |

模型输出的机械直译与措辞偏差，根源在这批文件注入的原文，而不在技能文档。排查此类问题的顺序是：先按上表定位注入点，再查技能与语言包。

已全部完成汉化的文件：`prompt_builder.py`、`system_prompt.py`、`coding_context.py`、`context_compressor.py`、`background_review.py`、`curator.py`，合计约 7.9 万字符。其余七个文件尚未处理。插件层（十四个插件的 `plugin.yaml` 描述、`tools.py` 与 `schemas.py` 的工具描述与参数描述）已全部完成，详见第十节。

定位方法：对目标文件做抽象语法树遍历，筛出「长度超过 60 字符、不含中文字符、且含四个以上连续英文单词」的字符串常量，并排除函数与模块的文档字符串。这一筛法能在一万行以上的文件里准确捞出面向模型的提示词，同时滤掉日志与异常消息。

### 2. 铁律：被其他模块解析的字符串锚点绝不可汉化

提示词中存在一批被其他代码用正则或前缀匹配解析的固定字符串。汉化它们不会引发语法错误，却会让解析器静默失效，属于最难发现的破坏。

- 动手前先全库检索待改字符串，确认没有第二处代码在解析它：`rg --fixed-strings "<待改字符串>" -g '*.py' -g '*.ts'`；
- 命中解析方（`re.compile`、`.startswith`、`.index`、`.split`、`in` 判断）时，该字符串保持英文原样，只汉化其后的说明文字；
- 另有一类容易漏掉的锚点：**模型约定回复标记**。提示词要求模型在特定情形下原样回复某个固定字符串，测试与后续流程据此判定，例如无内容可存时的 `Nothing to save.`、无用户轮次时的哨兵值、脱敏标记 `[REDACTED]`。这类标记必须逐字保留；
- 完整锚点清单与对应解析方见 `references/prompt-source-localization.md`。

### 3. 铁律：提示词与配套索引字典必须同步改写

部分提示词行同时充当代码字典的键，用于按会话工具集裁剪内容。只改提示词不改字典键，裁剪逻辑会静默失效，提示词里出现当前会话根本不存在的工具。改完必须实测「有该工具时保留、无该工具时剔除」两个方向。

### 4. 铁律：持久化格式常量绝不可汉化

压缩、摘要、交接类常量会被写入数据库，并被其他模块按字面做 SQL 匹配或切片。汉化它们会让历史会话无法识别、预览解析失败、旧版本兼容断裂，且不产生任何报错。这类常量包括摘要前缀、历史摘要前缀元组、摘要结束标记、合并分隔符、已裁剪工具的替代说明文本、无用户轮次哨兵值、进行中任务重放标记、章节标题等。

判别方法：`rg "<常量名>" -g '*.py'`，若命中方出现 `hermes_state_common.py`、`_sql_starts_with`、`_sql_after_marker`、`SUBSTR`、`INSTR`、`.split(`、`.startswith(`、`rsplit(`，该常量必须保持英文原样。完整清单见 `references/prompt-source-localization.md`。

### 5. 铁律：汉化后必须同步改写依赖原文的测试检查项

测试套件大量检查英文原文是否存在。汉化必然让这些检查失配，这是可预见的后果而非代码损坏。处理顺序：

1. 先在原版文件上跑一遍目标测试，记录基线失败项（区分「本来就失败」与「汉化引入」）；
2. 汉化后逐条把检查条件改为对应的中文特征词，不要删除检查、不要改成恒真；
3. 收尾时失败项数量必须回到基线水平。

### 6. 验证方法：结构守恒而非语法通过

语法编译通过不能证明文件完好。必须做四项校验，缺一不可：

1. 抽象语法树比对：函数名集合、参数签名、顶层常量名集合与原版逐一相同；类还需比对方法名与各方法参数签名；
2. 协议常量字节比对：解析锚点与持久化格式常量必须与原版完全一致；
3. 真实导入执行：`importlib` 加载模块并读取常量值，而非只做语法解析；
4. 关键函数真实调用：至少调用一个返回提示词正文的函数并检查内容。

可直接运行 `scripts/verify_prompt_localization.py` 完成上述四项。

### 7. 铁律：汉化会绕过只认英文的正则防护，必须同步扩展

源码里存在用英文正则做的语义防护，例如检测摘要是否虚构了用户归属。把摘要正文改成中文后，这类正则全部失配，防护静默失效。汉化任何被正则守护的文本，都要检查守护正则并补上中文分支，然后用「中文违规值被拦、英文违规值被拦、合法值不被误拦」三个用例实测。

### 8. 翻译质量要求

- **禁止被动句式与欧化语序**。`You are powered by the model named X` 译成「你由名为 X 的模型驱动」是错的，应译成「你实际使用的模型是 X，完整标识为 Y」。
- **禁止机械词到词替换**。同一个英文词在不同语境译法不同，须按当次语境选择恰当表述。
- **高频技术词必须先列出它在本代码库里实际指代的所有对象，再分别定译法**。做法是检索该词出现的每一处，看它周围在操作什么：同一个词在不同位置指的不是同一样东西时，统一译法必然错。四个反复踩坑的词及其分译结论：

  | 英文词 | 实际指代 | 按指代分译 |
  | :--- | :--- | :--- |
  | `hook` | 拦截工具调用的插件 | 插件拦截 |
  | | 插件注册的扩展点 | 扩展点 |
  | | 网关的事件回调 | 事件回调 |
  | `placeholder` | 被替换掉的原文留下的提示 | 简短提示／简短标记 |
  | | 模板或配置里的变量引用 | 变量引用／变量 |
  | `budget` | 轮次或迭代次数上限 | 最多 N 轮／迭代上限 |
  | | 成本额度 | 成本额度 |
  | | 摘要可占的篇幅 | 摘要篇幅 |
  | | 面板上显示的 token 消耗量 | 用量 |
  | `headless` | 无图形界面运行 | 后台运行 |

- **判定某个词该译成什么，去看渲染它的代码，不要看词本身**。界面文案里的词尤其如此：某面板分区原文写 `budget`，读源码发现该分区实际渲染的是输入输出 token 数，正确译法是「用量」。只按词面译会得到读者看不懂的标签。
- **改完必须做反向检索清零**。把该词的候选译法逐一在目标文件里检索，同时检索原译法，两者命中数都应为 0。只查新译法不查旧译法，会漏掉同一文件里残留的另一种译法。
- **先译准，再压缩**。英文长句拆成中文短句时，一个句子只说一件事，主谓宾完整。
- **保留协议字面**。工具名、参数名、路径、命令、标记语法一律原样保留，只译其周围的说明文字。
- **不造职位与机构名**。`a summarization agent` 译成「摘要专员」是生造。按实际职责写：「你负责为当前对话生成一份上下文检查点摘要」。
- **大写强调要落到中文语气上**。原文用全大写强调的词（`DATA`、`NEVER`、`MUST`）不能平译，用「只是」「绝不」「必须」这类中文语气词承接，否则强调消失、约束变弱。
- **长句里的插入语要拆成独立短句**。英文用破折号或逗号塞进的补充说明，中文应拆出来单独成句，不要把三层从句套在一句里。
- 汉化稿交付后，助手自身的回复同样受语言规范约束；不得在说明汉化成果时反复使用待清洗的行话词，否则等于当场示范违规。用户会直接指出这一点，并把它视为态度问题而非笔误。
- **交付前自查行话**。写完一段汉化稿，用《行话参照表》的词条逐条检索自己的文字，命中数应为零；再查一类隐性行话：把英文词直接换成汉字而不考虑语境的生造说法。这类词不在表内，但同样属于机械翻译，应换成符合中文习惯的说法。
- **汇报时用人话解释分支条件**。报告里不要直接搬代码术语（例如「无用户轮次场景」），要写清这个分支在什么真实情形下触发、为什么需要单独处理。用户追问某个术语是什么意思，就说明汇报已经失败。
- **用户问的是二选一时，第一句就给二选一的答案**。例如「仓库新版是本地汉化还是原版」这类问题，开头必须是「是本地汉化」或「是官方原版」，后面再展开三个版本的关系。先铺垫背景、先讲机制、先列分类，都会被当成没回答；用户会直接说「说了半天你还是没说清楚」。同理，用户问「现在是什么状态」时，第一句给状态结论，不要先讲历史。
- **禁止自造术语与缩写**。描述动作时直接用具体动词和对象，例如把「回收到工作目录」写成「把系统里那份复制回 D:\Hermes 覆盖旧的」。「回收」这类自造词读者无法从字面推出含义，用户会直接指出「中文说的太差了」。拿不准时宁可多写几个字把动作说全，也不要造一个自己觉得简洁的新词。
- **同一术语的译法要在全库保持一致**。`artifact` 在 OpenSpec 语境统一译「工件」，不要同一文件里两种译法混用；另一种常见译法还踩了行话表。改完用一次全库检索确认没有第二种译法残留。
- **中文语言包有四个变体，改一个必须同步改全部**。`zh.yaml`、`zh-hant.yaml`、`zh.tui.yaml`、`zh-hant.tui.yaml` 是四份独立文件，同一句文案在四份里各存一份。只改简体版会让繁体版与两个终端版继续输出旧译法。改完对四个文件同时做反向检索，任一文件命中不为 0 就不算完成。
- **用户层语言包会盖住仓库版，改完必须实测一次真实取值**。改语言包后不要只看文件内容就宣称完成，取一个刚改过的键调 `t()` 看返回值。用户层若放着完整副本，仓库里的新译法根本不生效。
- **同一个词在同一个文件里出现多次时，逐处看上下文再定译法**。例如支付场景的 `card` 指银行卡，看板场景的 `card` 指任务条目，界面面板的 `budget` 指 token 用量。批量替换前先把每处的上下文列出来，统一译法只适用于指代相同的那些。

### 9. 交付与生效时机

- 汉化稿先写入工作目录的 `核心配置与防线/locales/` 一类路径，与原版备份并列保存，确认无误后再覆盖线上文件；
- 系统提示词在会话开始时定型，源码改动只在下一个新会话生效，当前会话不受影响；
- 覆盖前先把线上文件备份到临时目录，便于一条命令回退。
- 原版备份集中放在工作目录下与工具库、技能库并列的独立目录（如 `原英文提示词备份/`），不要散落在配置目录里，否则配置目录会被备份文件污染，且迁移脚本难以判断哪些是资产、哪些是备份。

### 9.1 铁律：改完必须用运行时取值证明生效，文件内容一致不算证据
**宣称任何汉化改动已生效之前，必须调用一次真实的取值函数看返回值，不能只比对文件内容或哈希。**

根因：语言包有多层回落，用户层优先级高于仓库层。文件里写对了、哈希也对得上，运行时取到的仍可能是另一层的旧值，且不产生任何报错或告警。

验证命令（取一个刚改过的键）：

```python
from agent.i18n import t
print(t('gateway.hooks.command_blocked', command='test'))
```

返回新译法才算生效；返回旧译法说明被上层副本盖住。此时改的是仓库层，而运行读的是用户层，两边内容不同但都合法。

同类判据也适用于提示词源码：改完在源码里检索新字符串只能证明写入磁盘，要证明生效必须新开一个会话看模型实际收到的提示词。

**汇报时把「已写入」与「已生效」分开说。** 把两者混为一谈是本类任务最常见的误报，用户会直接指出「改了但没反应」。

### 10. 插件工具 Schema 与元数据是独立的汉化面

`agent/` 下的提示词源码之外，插件目录里的工具 Schema 与 `plugin.yaml` 同样直接进入模型上下文，但锚点与禁改边界完全不同。汉化插件时：

- **先按来源把插件分成两类，两类的汉化落点不同**。自定义插件（自己写的、无上游）直接改插件目录文件，一次性做好，不受任何升级影响；外部安装插件（有上游仓库，无论是否带 `.git`）不能用 Git 提交保存汉化，必须走与工具、核心相同的映射表机制。归类看有没有上游，不要只看目录里有没有 `.git`（判据见后文「判定插件来源」那条）。分类前先逐个数清，不要凭印象——实测本机插件里外部安装与自定义各占相当比例，远超「印象中的几个」；插件总数会随删装变化，每次清点以磁盘为准；
- **映射表生成器必须同时扫描仓库 `tools/*.py` 与插件目录，否则插件工具全部漏掉**：只扫 `repo / "tools"` 的脚本会让映射表里一个插件工具都没有，且脚本报告成功、不报错。按工具名索引的映射表天然能容纳两者，只需扩大采集范围；
- **仓库源码已回英文原版后，不能再跑「从源码生成映射表」的全量脚本，必须用增量合并**：源文件里已经没有中文，全量生成器扫出来的条目数为零，直接覆盖会把现有映射表清空。正确做法是写一个只做「读现有映射表 → 扫出新增中文条目 → 不覆盖已有键 → 写回」的合并脚本；插件层与核心层共用同一张表，按工具名去重；
- **合并后用中间件函数实测替换，不要只看 JSON 文件行数**：直接调 `_rewrite_tools()` 传入几条英文假数据，看返回的中文描述与替换计数。只验证「JSON 里有这个键」证明不了运行时生效；
- **删除插件后必须同步清理 `config.yaml` 的 `plugins.enabled` 残留，且不能靠 `hermes plugins disable`**：目录删掉后 `hermes plugins disable <名>` 会报 `No plugin named ...`，因为它按目录发现插件；而残留条目会让启动日志持续告警。`config.yaml` 受写入保护，`patch`/`write_file` 会被拒绝，正确做法是用 Python 读改写并先备份原文件；
- **删掉一个防线插件或配套采集文件后，必须回到 `SOUL.md` 检查是否有章节仍在描述它**：`SOUL.md` 是每轮注入的规范正本，里面写着各层防线的实现方式（哪个插件做强制替换、哪个文件记录候选词对）。插件删了、`config.yaml` 清了，`SOUL.md` 那段说明还在，模型每轮仍被告知「有个插件在做拦截」，与实际运行状态矛盾且不报错。判定方法：删除后用 `grep -rn '<插件名>\|<被删文件名>' --include='*.md'` 全库扫一遍，命中的 `SOUL.md` 章节要么整段删除、要么按剩余机制重写（只剩提示层时就只写提示层）；
- **判定插件来源不能只看有没有 `.git`，必须查 `plugin-catalog` 与 `.hermes-catalog.json` 两处登记**：三级判据依次为——① 查 `hermes-agent/plugin-catalog/<插件名>.yaml`，有登记即为外部插件（文件里带 `repo`、`sha`、`tier`、`maintainer`，`tier: community` 是社区插件）；② 查插件目录下的 `.hermes-catalog.json`，有 `installed_at` 说明通过插件市场装过；③ 两处都没有才是自定义（自己写的）。只看 `.git` 会误判：社区插件常以 `subdir` 方式打包安装、不带 `.git`，按「无 `.git` 即自定义」归类会把它错放进自定义插件备份目录，进而误判它能/不能 `git pull` 升级。实测 `openviking` 就是这种情形——`plugin-catalog/openviking.yaml` 登记了 `repo: github.com/volcengine/OpenViking` 与 `tier: community`，本机 `.hermes-catalog.json` 记了安装时间，但目录里没有 `.git`，只能靠 `hermes plugins install` 重装升级；
- **备份目录按来源分四类，无 `.git` 不等于自定义插件**：四类是「自定义插件/」（自己写的、无上游，源码即最终版，升级不受影响）、「外部安装插件/」（从外部源装的，含带 `.git` 可 `git pull` 与无 `.git` 需重装两种子情形）、「MCP 扩展/」（自写的 MCP 启动包装脚本，不是插件）、「插件补丁/」（对插件源码的本机改动，以 `.diff` 形式保存）。归类判据是「有没有上游」与「进不进插件系统」，不是「能不能 `git pull`」——社区插件常不带 `.git`，按「无 `.git` 即自定义」归会把它错放进自定义目录。混放会让「这个插件能不能升级」「改动在哪一层」都要现查；分开后目录结构本身就是答案。同名文件在多处出现时（运行目录、插件备份、补丁备份），算哈希确认重复只留信息最完整的一份——带 `.git` 的完整插件目录优于只有单个文件的补丁目录；
- **MCP 服务器与 Hermes 插件是两套独立机制，`plugins/mcp/` 这类目录容易误判**：MCP 服务器由 `config.yaml` 的 `mcp_servers` 直接启动子进程，不走插件系统；目录里若只有启动脚本、没有 `plugin.yaml`，它不是插件，只是给外部包套的启动入口。回答「这个目录是不是插件」时先看有没有 `plugin.yaml` 与是否登记在 `plugins.enabled`，两项都不满足就不是；
- **外部包本体不备份，给它打的启动包装脚本必须备份**：外部 MCP 包（如 `free-search-mcp`）装在 uv 缓存里（`~/AppData/Local/uv/cache/archive-v0/<hash>/`），版本钉在 `config.yaml`，新机器联网即拉，备份它没有意义；而为了绕开上游缺陷自写的入口脚本（如 `free_search_mcp_runner.py`）无上游、丢了无处可取，必须随插件备份一起保存，并在移植说明里写明「首次启动需联网拉包」；
- **「包本体不备份」必须配套部署脚本自动安装，否则移植流程是断的**：只在说明里写「需联网」等于把手工步骤丢给用户。给部署脚本加一个显式开关（如 `--install-mcp`），由脚本完成安装并自证成功：包规格从 `config.yaml` 的 `mcp_servers.<名>.args` 里读（不要硬编码版本号，改配置后会静默装错且仍报成功）；用 `uv tool run --from <规格> python -c "import <模块>"` 一条命令兼顾拉包与验证，返回码为 0 且 stdout 有输出才算成功；失败时给出三条具体排查方向（PyPI 直连、`UV_INDEX_URL` 国内镜像、`HTTPS_PROXY` 代理），且不阻断其余部署，只提示可单独重试；
- **核对 PyPI 上有无新版直接读 JSON 接口**：`curl -s https://pypi.org/pypi/<包名>/json`，`info.version` 是最新版、`releases` 是全部版本映射。发现新版不要直接升——自定义入口脚本是针对特定版本的上游缺陷写的；
- **升级前先验证包装脚本依赖的符号在新版里是否还在，不要只看版本号**：逐个 `python -c` 导入 runner 用到的每个符号（实测某个 MCP runner 依赖 `search_mcp.browser.pool`、`search_mcp.cache.cache`、`search_mcp.server.mcp` 与 `mcp.run_stdio_async` 四项），任一项缺失或改名就是接口变了、必须先改 runner 再升级。同时确认上游缺陷是否已修（跑一次 `inspect.getsource` 查旧缺陷模式还在不在）——已修则 runner 可以撤、未修则 runner 必须留；
- 升级顺序固定为「改 `config.yaml` 版本号 → 跑安装命令 → 重启网关比对日志里的 `registered N tool(s)` 条目数与工具名是否不变 → 有变化说明接口改了、回退并改脚本」；改版本号要同时改备份目录与运行环境两份 `config.yaml`，改完 `grep -o '<包名>==[0-9.]*'` 两处核对一致；
- **升级后清 uv 缓存只留当前版本，删完必须实测当前版本仍可用**：`uv tool run --from <包>==<当前版本> python -c "import <模块>"` 返回正常才算清对了；
- **验证部署脚本的新分支必须显式带 `--check`**：`--only <部分>` 这类参数看起来像试跑，实际是真实部署（只限定了范围）。只加 `--only` 而不加 `--check` 会把文件真写进去。脚本帮助文本里也要把「无 flag 即真实部署」写清楚，避免自己下次再踩；
- **uv 缓存按版本各占一个 hash 目录，升级包版本后旧版本不自动清理，要手工删旧留新**：`archive-v0/` 下同一个包会并存多个版本目录（实测某包留了 0.11.0／0.13.0／0.13.1／0.14.1 四份，共 5 MB）。判定方法：`ls <每个 hash 目录>` 看里面的 `<包名>-<版本>.dist-info`，一个目录只放一个包的版本才能整目录删。删之前先确认该目录不含其他包（同目录会并列多个 `.dist-info` 时不能删）；删后必须实测一次 `uv tool run --from <包>==<版本> python -c "import <模块>"`，确认当前版本没被误删；
- **判断「装新 Hermes 会不会自带某个东西」要查两处，不能凭目录里有没有**：仓库自带的看 `hermes-agent/plugins/`（内置插件清单）与源码里的包引用（`grep -rn '<包名>' --include='*.py' hermes-agent/`，命中 0 即非自带）；外部 MCP 的看 `hermes-agent/plugin-catalog/` 里有没有同名条目——目录里登记的是**官方审定过的外部服务**，没登记说明完全是用户自己加的。回答用户的「新装系统里有没有」必须先跑这两处，否则会把用户自加的依赖说成官方自带，或反过来;
- **回答「某个东西是不是内置」时，先查 `plugin-catalog` 清单，不要凭目录里有没有来推断**：内置插件的权威清单是 `hermes-agent/plugins/` 下的目录（`browser`、`computer_use`、`memory`、`kanban`、`model-providers` 等 19 个）；`plugin-catalog/` 里登记的反而是外部插件。两者混淆会把社区插件说成「安装 Hermes 自带」，用户会直接质疑「为什么内置的还要备份」；
- **用 `cp -a` 往已存在的同名目录复制会生成「旧版备份」子目录，不是覆盖**：`cp -a src/ dst/` 在 `dst` 已存在时把内容套进去一层，产生 `dst/src/` 这类嵌套残留。表现为磁盘上多出一个带旧内容的目录，容易误当成另一份备份。复制整个插件目录前先 `rm -rf` 目标，再 `cp -a`；复制完 `ls` 确认层级没有多出一层；
- **脚本运行产生的临时工作目录必须用完自动删除**：做差异对比、常量提取这类操作时会把源码临时落到 `_probe`／`_cmp`／`_verify` 之类的目录再 import，脚本不清理就会逐次累积（实测单次可留 2.8 MB、19 个文件）。正确写法是在 `finally` 里 `shutil.rmtree(workdir, ignore_errors=True)`；脚本自身也要把中间临时文件用 `tmp.unlink(missing_ok=True)` 清掉。收尾时对整个工作目录做一次 `find -type d -name '_*'` 确认没有残留；
- **`gateway restart` 字样会触发网关保护拦截**：在网关进程内执行含 `hermes gateway restart` 的命令会被拒（提示要从网关进程外的终端执行）。用 heredoc 批量改文档时，如果正文里恰好带着这串命令示例，整条命令会被一并拦下。改文档时改用 `execute_code` 调 Python 读写文件，或把示例里的命令拆开写，避免误触发；
- **残留的更新锁文件会让 Hermes 每次启动都报「更新未完成」并拒绝正常工作**：`$HERMES_HOME/.hermes-update-in-progress.lock`、`.hermes-update-paused-gateways.lock`、`.update_exit_code`、`hermes-agent/.git/hermes-update.lock`、`.git/hermes-pack-tidy.lock` 都可能是历史中断留下的。清理前先读锁里的 PID 并确认进程已死（`ps -p <pid>`），不能无脑删——锁里含活进程 PID 时删除会与运行中的更新冲突；
- **判断插件源码里是否真有中文残留，不能用 bash 的 `grep '[\u4e00-\u9fff]'`**：该写法在 MSYS/git-bash 下不生效，会把纯英文文件误报为含中文，导致误以为解耦没做干净。改用 Python 逐文件读文本判断字符区间；
- **仓库插件的本地改动里可能混着功能代码，撤销前必须逐文件按「新增行含中文的比例」分类**：两者相等是纯汉化，中文字数为零是纯功能改动，介于两者之间是混合。实测某插件的 122 行新增全部是 Windows 兼容功能代码、零汉化，直接撤销会连带丢掉功能修复；
- **插件自带的技能（`skills/*/SKILL.md`）不属于工具描述映射表的覆盖范围**：技能是独立文件、不进请求结构。仓库插件里的技能汉化应放用户层 `$HERMES_HOME/skills/`，靠哈希保护天然不受插件升级影响；
- **仓库插件升级后必须重跑映射表差异对比，升级必然带出工具描述变化**：插件升级等于换了一套英文描述，旧中文译文留在映射表里，模型看到的就是与新版功能脱节的说明。标准步骤：先 `git fetch origin` 看有无新提交（`fetch --dry-run` 只列不拉），`git -C <插件> log --oneline HEAD..origin/<分支>` 看改了哪些提交，`git diff --stat HEAD origin/<分支>` 看波及哪些文件。若只改 README／CHANGELOG，映射不受影响；改了 `tools.py`／`schemas.py` 则必有描述变化。升级后立即跑 `python 汉化维护.py`，看「插件工具」一栏有无变化并逐条重译；
- **插件升级前先备份整个插件目录（含 `.git`），升级后用 `merge --ff-only`**：`cp -a` 带 `.git` 完整备份到仓库之外，出问题时可用 `git reset --hard <旧提交>` 或备份覆盖两条路回退。升级用 `merge --ff-only` 而非 `pull`，避免产生意料外的合并提交；
- **插件升级后还要查插件技能与用户层汉化技能是否脱节**：插件升级若带上新的或改过的 `SKILL.md`，用户层那份汉化技能不会跟随（用户层优先，且哈希保护让它不会被覆盖），于是继续输出旧内容。需要重新对比并补译；
- **仓库已不可访问不等于插件坏了**：`git fetch` 报 `Repository not found` 或要求输入用户名，说明上游仓库已删除或改名。此时先查 `hermes-agent/plugin-catalog/<插件名>.yaml` 里锁定的 `version` 与 `sha`——官方目录锁的就是该版本，说明官方也停在旧版，无需升级也不影响使用；
- **插件加载顺序是 bundled → user → project，后者同名覆盖前者**（`hermes_cli/plugins_discovery.py` 的 `collect_directory_manifests`，注释原文 `Later sources win on key collision (project > user > bundled)`）。但用户层插件目录本身已是「user」层，不存在更上层可覆盖自己，所以想用同名覆盖思路规避插件升级冲突行不通，必须直接覆盖文件或改用新插件名；
- **先判定目录性质**。配置文件备份（例如记忆服务的 `ov.conf`）不是汉化对象——JSON 键名与取值都是服务进程读取的启动参数，汉化会导致服务无法启动。审计前先看目录里是源码还是配置，再决定是否纳入范围；
- **逐项列全工具再动手，不要抽样**。同一个 Schema 文件里常见「大部分已汉化、少数仍是英文」的混合状态，抽样必然漏；
- **保持英文的部分**：工具名、参数键名、`type`、`required`、`enum` 取值、`default`，以及 `plugin.yaml` 的 `name`／`version`／`kind`／`manifest_version`／`provides_tools`／`provides_hooks`／`requires_env[].name`；
- **拒绝机翻直译与假大空扩写**：严禁机械生硬直译（如把 artifact 直译为“工件”）和扩写大厂套话（如“前置强校验门禁”、“带缺陷结项”、“推进至待办就绪状态”、“深入推演”）；统一采用通俗自然的规范工程中文（如“规范文件”、“转为待办状态”）；
- **严防关键技术约束与上下文丢失**：必须完整保留原版中的取值限定（如 `type` 只能取 `GIVEN/WHEN/THEN/AND/BUT`）、参数别名（如 `'spec'` 为 `'specs'` 别名）、底层免 CLI 机制与无参/有参分支行为，不可因中文化而剪除调用细节；
- **契约守恒校验必查三项**：比对参数名列表、必填项（`required`）与取值列表（`enums`），三者必须与原版逐一完全一致；
- **符号表比对发现函数缺失时，先判断是否属于功能升级**：看新版本是否有函数承接了同一职责（例如把只校验 create 的函数扩展为校验 create／patch／write_file 三者），承接了就是升级，不是损坏。

- **工作目录里只应存在职责互不重叠的目录，发现重复备份就当场合并**：备份做得随意时会出同一个文件存在三份的情况（运行目录一份、插件库备份一份、补丁备份一份），用户一打开目录就会问「这两个是不是一个东西」。判定方法：对同一个文件算哈希，相同即重复；保留信息最完整的那一份（带 `.git` 的完整插件目录优于只有单个文件的补丁目录），删掉其余的；
- **删除目录或文件后，必须对全部文档做反向特征词检索并清零**：删完只改主文档会漏掉其他文档里的引用，用户看到已删路径出现在说明书里会认为没删干净。做法是把被删目录名、文件名拆成几个关键词，对 `*.md` 与 `*.py` 全库 `grep`，每一处命中都要改成新落点或整段删除；最终命中数必须为 0；
- **备份类目录被废弃时，要先确认其中唯一不可再生的内容已另存，再整个删除**：可再生的（Git 里有历史可以 `reset --hard` 回去的旧版本插件）、已存在他处的（与运行目录哈希一致的完整文件）都属于可重生。只有「本机独有且未入库的代码改动」需要事先确认存到新位置；确认完就整个删，不要拆散了到处埋坑；
- **同级部署脚本的职责边界要按目录划清，不要两份脚本都能做同一件事**：资产分散在多个目录时，根目录一份总部署脚本（全量）、每个子目录一份只负责自己的部署脚本（如 `核心配置与防线\安装部署.py`）。两个脚本都应支持 `--check` 只检查与 `--only <部分>` 只部署指定部分。两处都能部署同一内容时，用户第一个问题就是「这两个冲不冲突」；解决方法是把职责写进两边的脚本 docstring 与说明文档首段——总脚本是「含全部」，子目录脚本是「只管本目录」；
- **部署脚本不要自动打补丁，只打印应用命令**：打补丁会改动外部插件的源码，官方新版的代码结构可能已变，补丁无法干净应用；打错了还会破坏插件、需要手工回退。正确做法是部署时列出补丁文件并打印拼好的 `cd <插件目录>` 与 `git apply "<补丁路径>"`，由人判断是否执行；
- **补丁文件名开头就是目标插件名时，用前缀匹配找插件，不要按 `-` 切分拼接**：插件名本身带连字符（如 `agent-janitor`），按 `stem.split("-")[0] + "-" + [1]` 只能得到前两段，遇到三段以上的名称会拼错。写法是从已知插件清单里找 `p.name.startswith(name)` 的第一项；

完整流程、锚点清单与可复用校验脚本见 `references/plugin-schema-localization.md`。

### 11. 汉化成果提交与升级存活的检查清单

- [ ] 改语言包后，是否用 `t()` 实测过真实返回值，确认仓库版改的新译法真的生效（而不是被用户层旧副本盖住）？
- [ ] 汇报时是否把「已写入文件」与「运行时已生效」分开陈述，没有把前者当成后者？
- [ ] 用户层语言包是否只放了差异键，而不是完整副本？
- [ ] 四个语言包变体是否全部同步，且反向检索命中数均为 0？
- [ ] 回答「某层是本地汉化还是官方原版」时，是否拿官方 `origin/main`、仓库工作区、用户层三个版本对照过？
- [ ] 统计本地提交性质时，是否逐个看了改动文件，而不是只看提交标题归类？
- [ ] 提交第三方插件汉化前，是否确认过它不在游离 HEAD，并切回了主分支？

- [ ] 还原误改文件时，是否用 `git show HEAD:<路径>` 而不是 `git checkout --`？
- [ ] 取「英文原版」时，是否确认参照点不是 `origin/main`（本地安装版与开发主线常差数千个提交，同一路径可能是完全不同的代码）？

- [ ] 汇报测试结果时，是否区分了「基线就失败」与「汉化引入」两类，并给出了基线失败项集合？
- [ ] 设计升级存活方案前，是否先确认了哪些资产本来就在用户层、不受升级影响？
- [ ] 回答「某层汉化还在不在」时，是否逐层用各自判据实测并给出数字，而不是笼统答「都是中文」或「都是英文原版」？

- [ ] 需要改技能描述、工具 schema 或插件描述时，是否确认过语言包覆盖不到，并选了正确的落点（技能改 SKILL.md、工具走中间件、插件改插件仓库）？
- [ ] 设计升级存活方案时，是否优先选用户层覆盖（语言包差异键、中间件插件）而不是主仓库 Git 提交？
- [ ] 是否确认过插件目录在 `hermes-agent` 仓库之外，升级不会动它？
- [ ] 中间件映射表是否按「工具名 + 参数名」索引，而非全文替换对？

- [ ] 映射表生成时，脚本是否自动识别了英文基线（沿历史回溯找中英切换点），而不是写死提交号？
