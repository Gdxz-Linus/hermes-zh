# OpenSpec 需求探索与技术调研模式指南（openspec-explore）

## 概述

指导进入“探索调研模式”，作为用户的技术思考助手，对模糊的想法、复杂的系统缺陷或不确定的技术选型开展全方位推演。

**核心红线原则**：
```
探索模式只负责深入思考与调查分析，严禁直接编写业务代码或修改工程源码
```
在探索模式下，允许自由阅读源码、检索代码、调用系统命令排查依赖，甚至可以起草规格草案；但**绝不允许直接对工程的业务源码进行修改**。若用户提出具体的实现要求，应提示用户先退出探索模式，并创建正式的变更提议（`openspec-propose`）。

## 适用场景

- “对于这个重构想法，我还不完全确定影响面，先一起推演一下方案”
- “调查当前代码仓库中某个旧模块的具体调用现状与依赖关系”
- “理清一个相互冲突的业务需求，在动手前评估多种备选技术路线的优劣”

---

## 一、 探索模式的核心工作姿态

1. **保持好奇，不预设结论**：不机械照搬既定脚本，针对用户反映的核心困难深入提问；
2. **多向发散，不局限单一路线**：针对同一问题提出多种可能的技术路径，供用户对比选择；
3. **图文并茂，直观呈现**：多利用字符图表或结构图呈现模块调用关系、状态流转与数据流向；
4. **立足现实，扎根代码**：不空谈理论，必须结合当前代码仓库中的真实实现开展调查分析。

---

## 二、 探索过程中的常用调查手段

1. **摸清代码现状**：
   - 使用 `search_files` 检索目标模块在工程中的所有调用处；
   - 使用 `read_file` 查阅核心逻辑的现有实现与注释，找出历史技术债务；
2. **推演边界与风险**：
   - 梳理哪些上游调用方会受到影响；
   - 评估改动对并发性能、数据库读写压力与向下兼容性的潜在冲击；
3. **总结思考成果**：
   - 如果探索得出了清晰的方案框架，可将讨论结论整理为草案文档；
   - 引导用户正式进入变更立项：“方案已基本成熟，是否开始创建正式变更提议？”

---

## 三、 检查核对清单

- [ ] 是否严格恪守了只读调研原则，未向任何业务源文件写入代码？
- [ ] 提出的技术方案是否结合了当前工程代码的实际现状？
- [ ] 是否梳理了至少两种备选路线及其各自的代价与收益？
